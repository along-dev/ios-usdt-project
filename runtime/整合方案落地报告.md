## 二、★ 落地过程发现的两个阻断级缺陷

### N-23 Go 目录映射导致**无法编译**

| 项 | 内容 |
|---|---|
| 现象 | `module github.com/flipped-aurora/gin-vue-admin@latest ... does not contain package .../server/api/v1/response` |
| 根因 | 脚本把源目录映射到 **`internal\api`、`internal\model`…**；<br>但 `go.mod` 声明 module `.../gin-vue-admin/server`，<br>源码 import 是 **`server/api/...`、`server/global/...`**（**模块根**之下） |
| 另两处 | `main.go` 被放到 `cmd\server\`（源里在**根**）；`utils` 被放到 `pkg\utils`（源里是**顶层**） |
| 修复 | 映射改为**保持模块根布局**，目录名与源一致；`main.go` 留根 |
| 影响 | **不修则统一目录根本不可用**——这是"整合方案落地"的硬阻断 |

### N-24 `packfile` 目录未纳入映射表

| 项 | 内容 |
|---|---|
| 现象 | `core/viper.go:13` 引用 `server/packfile`，统一目录无此目录 |
| 根因 | 映射表只复制 12 个目录，**漏了 `packfile`** |
| 发现方式 | **完整 import 前缀审计**——扫全库 `gin-vue-admin/server/(\w+)` 去重，得 13 个，逐一比对目录存在性 |
| 修复 | 补入映射表 |

> **共性教训**：映射表必须与 `go.mod` 的 module 路径 + 源码实际 import 前缀**逐一对齐**，
> 不能凭"看起来合理"的目录名假设。仅凭"目录都复制了"无法发现此类问题，
> **只有编译才能暴露**。

#### ★ N-26 受限环境下的进程生命周期问题　`已定位并文档化`

| 项 | 内容 |
|---|---|
| 现象 | 脚本内两轮探测显示 `UP`，但**脚本结束后立即连不上**（`Could not connect to Redis`） |
| 根因 | ① 沙箱**拒绝 WMI**（`Win32_Process.Create` → 拒绝访问）<br>② 回退 `Start-Process`，其子进程**随本 pwsh 进程退出而终止** |
| 验证 | 单独调用确认：`Start-Process` 起来的进程 `HasExited=True` |
| 正确做法 | **用后台作业托管**：<br>`Start-Job { & "<exe>" <args> }` —— 实测 `redis-cli ping` 返回 **PONG** |
| 处置 | 脚本已改为：优先 WMI → 失败则告警并提示改用后台作业；<br>末尾附后台作业示例命令 |

> 这是**沙箱环境限制**，非脚本缺陷。正常交互式 PowerShell 窗口中 `Start-Process` 不受影响。
