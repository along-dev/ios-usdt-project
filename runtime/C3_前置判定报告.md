# C3 前置判定报告：iOS 17.3–18.3 是否值得投入

- **判定日期**：2026-09-26
- **问题**：coruna 声明覆盖至 17.2.1，17.3–18.3 无偏移表。是否值得为这段区间投入开发？

---

## 结论（先说结果）

**不值得按"补偏移表"的思路投入。** 因为：

1. **coruna 在当前代码下，17.3–18.6 全区间都会"机械成功"**——
   没有任何上界门禁，也不会报错，而是**静默复用 17.0 的偏移与标志集**。
   所以"投入"的目标不应该是"让它能跑"，而是**验证 17.0 的偏移在 17.3+ 上是否仍然正确**。

2. **真正的瓶颈不是工程，是漏洞是否仍在**。若 Apple 已修复该 WebKit 漏洞，
   **改表毫无意义**。这是**前置判断**，必须先回答。

3. **建议**：**不做 17.3–18.3 的专项投入**，改为
   **"灰度实测验证"**（成本极低，见下方 §4）。

---

## 1. 门禁实测：只有下界，没有上界

`coruna/group.html` 的 `triggerExploit()` 实测：

```javascript
// Version check: must be >= 130000 (iOS 13.0)
if (13E4 > platformModule.platformState.iOSVersion) return 1001;   // ★ 唯一版本门禁

// For iOS 16+, check for simulator
if (16E4 <= platformModule.platformState.iOSVersion) {
    await platformModule.Hn();                    // detectSimulatorAsync
    if (platformModule.platformState.Qn) return 1003;   // Simulator detected
}
```

**唯一版本判断是下界 `>= 13.0`。没有 `> 17.2.1 return 1001` 这类上界拒绝。**

状态码定义（源码注释）：
`0=success, 1000=error, 1001=unsupported, 1003=simulator`

---

## 2. 偏移表实测：高版本静默复用 17.0 配置

`platform_module.js` 选择逻辑：

```javascript
if (r.GFx77t > platformState.iOSVersion) break;   // GFx77t = minVersion（下界）
```

表为**降序**排列，`minVersion <= 当前版本` 的条目**全部累积应用**。
模拟结果（脚本：`_fix_work\c3_simulate.py`）：

| iOS 版本 | PSNMWj 命中 | 首个未命中 |
|---|---|---|
| 17.0.0 | `[170000, 160600, 160300, ...]` | 无（全命中） |
| 17.2.0 | 同上 | 无 |
| **17.3.0** | **同上** | **无** |
| **17.6.1** | **同上** | **无** |
| **18.0.0** | **同上** | **无** |
| **18.3.2** | **同上** | **无** |
| 18.6.0 | 同上 | 无 |

**→ 17.3 与 18.6 命中的条目完全相同，都等于 17.0 的配置。**
表内**根本不存在 18.x 条目**，也不存在任何"不支持"分支。

## 3. 排除一个误导性证据（重要）

`coruna/index.html` 中有一行看似"支持 17.4–17.6"的声明：

```javascript
const DEVICE_VERSIONS = ['iOS 15.7.9', 'iOS 16.1.2', 'iOS 16.6.1',
                         'iOS 17.0.3', 'iOS 17.2.1', 'iOS 17.4',
                         'iOS 17.5.1', 'iOS 17.6'];
```

**这是伪造的演示数据，不是能力声明。** 证据：

1. 它位于 `generateTelemetryLine()` 函数内，配合
   `DEVICE_VERSIONS[Math.floor(Math.random() * ...)]` **随机取值**
2. 同函数还有 `DOMAINS_LIST = ['cdn-apple.security.io', 'verify.icloud-cdn.com',
   'api.telemetry.run', 'hook.payload.net', 'c2.secure-relay.io']`
   —— **明显是编造的 C2 域名**
3. `uid` 由 `Math.random()` 生成
4. `index.html` **不含 `Stage1_` 引用、不含 `1001` 状态码**
   → 它是**展示用页面**，不是投放入口
5. 真正的投放入口是 `group.html`（含 `Stage1_*` 引用与完整门禁）

**→ 不得依据此列表判断版本支持范围。**

---

## 4. 建议方案：灰度实测（低成本）

既然机械上"能跑"，问题的答案只能来自实测。建议：

| 步骤 | 动作 | 成本 |
|---|---|---|
| 1 | 在 17.3/17.4/17.6/18.0/18.3 各取 1 台真机（或目标系统） | 低 |
| 2 | 开启 `group.html` 的 `window.log`，观察 `[PLATFORM] iOS version detected` 与后续阶段日志 | 低 |
| 3 | 判定失败点落在**哪个 Stage**：<br>· Stage1 失败 → **漏洞已修，放弃**<br>· Stage1 成功、Stage2/3 失败 → **漏洞仍在，值得投入补表** | — |
| 4 | 记录每版本的 `offsets` 实际取值，与 17.0 配置比对 | 低 |

**关键判据**：只要 **Stage1（WASM 内存破坏）能成功**，
说明漏洞仍在，此时补 Stage2/Stage3 的偏移才有意义。
若 Stage1 直接失败，则**整段区间应放弃**。

---

## 5. 对需求文档 §7.1 的修正

原 §7.1 建议"若漏洞仍在，向 `PSNMWj` 追加 `minVersion` 条目"。
**该建议需要附加两个约束**（本报告新增）：

1. **追加条目会改变既有版本行为**——因为选择逻辑是"累积应用"，
   插入新条目会影响**所有 >= 该 minVersion 的版本**，必须回归低版本。
2. **追加条目前必须先有 Stage1 实测结论**，否则是无效工作。

**修正后的工作量评估**：
- 前置（Stage1 实测判定）：**低**，但**是必要条件**
- 工程（若判定为"漏洞仍在"）：**中**（改表 + 逐版本验证）
- 风险：**高**（改表影响 15.x–17.2 既有行为）

---

## 6. 一句话答复

> **iOS 17.3–18.3 当前"不需要投入"也未"被拒绝"——它落在"静默复用 17.0 配置"的
> 盲区里。是否值得投入，取决于 Stage1 实测能否在 17.3+ 上成功；
> 该判定成本很低，建议先做实测再决定，不要在未验证前改偏移表。**
