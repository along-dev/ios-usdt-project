# D2-C3 [R2] 构建-源码一致性门禁（8888 由 `_i2c1_server.exe` 提供，非现编）

## 目标

建立**机械门禁**，确保 **Go 服务（8888）运行的二进制【不早于】其源码**。

## ★★ 为什么必须有这张卡（不是理论问题，是本轮已踩的坑）

**D0-C4 收口时的实证**：

| 项 | 值 |
|---|---|
| 静态判据 C1–C6 | **全绿** |
| `go build ./...` | **EXIT=0** |
| `go vet ./service/app/` | **EXIT=0** |
| **真 HTTP 断言 R2** | 🔴 **失败** |

**根因**：
```
service\app\wallet_resolver.go   mtime = 09-30 01:04:44
_i2c1_server.exe                 mtime = 09-28 22:05:44   ← 早 2 天
```

**⇒ 8888 跑的是**旧二进制**，改动**根本没生效**。**
**重新编译并重启后，R1–R6 才全部符合**。

★ **⇒ 静态判据 + 编译门【不能】替代运行时验证（P-18）；而"运行时验证"的前提是"跑的是新代码"。**
**本卡就是把那个前提变成机械门禁。**

## ★ 当前状态（调度实测，2026-09-30）

| 项 | 值 | 判定 |
|---|---|---|
| 8888 二进制 | `X:\_integration\_fix_work\_i2c1_server.exe`，mtime **09-30 01:13:56** | — |
| 8888 进程启动 | **01:14:12** | ✅ 晚于二进制 |
| **最新 Go 源码** | `wallet_resolver.go` **01:04:44** | ✅ 二进制晚于源码 |

**⇒ **当前是一致的**，但**没有任何机制保证它持续一致**。**

## ★ 规格

### (a) 新建门禁脚本 `verify_build_freshness.py`

**断言（至少覆盖）**：

| # | 断言 | 红态 |
|---|---|---|
| **F1** | 8888 的**监听进程**存在，且其可执行文件路径可读 | 无进程 ⇒ 红 |
| **F2** | ★ **二进制 mtime ≥ 全部 `01-backend-go/**/*.go` 的最大 mtime** | 源更新 ⇒ **红** |
| **F3** | ★ **进程启动时间 ≥ 二进制 mtime**（进程加载的是当前二进制） | 旧进程 ⇒ **红** |
| **F4** | `01-backend-go` 的 `go build ./...` EXIT=0（可编译） | 不可编译 ⇒ 红 |
| **F5** | ★ **运行时探活**：`GET /health` ⇒ 200（服务真活着） | 不可达 ⇒ 红 |
| **F6** | ★ **端到端否定断言**：`GET /app/wallet-status?wallet_id=999999` ⇒ **code!=0** | 返回 0 ⇒ 红（可能跑旧版无校验） |

★ **F2/F3 是本卡核心** —— 它们把 P-18 的教训变成机械判据。
★ **F6 是"改动真生效"的间接证据**（该端点的新校验是 D0-C4 引入的）。

**门禁只报红，不自动改环境**（改环境属执行者的动作）。

证明扫描有效；命中为 0 时**先怀疑量尺**。

## 不在范围

- 不改 `_manifest.sha256`

## 证据要求

- 判据动前红 / 动后绿两次真实退出码
- ★ **F2/F3 的实测数据**（二进制 mtime、源码最大 mtime、进程启动时间）
- ★ **明确说明**：门禁是否会因"源码更新但未重编"而报红（**须实测演示一次**——
  可用 `touch` 一个 `.go` 文件的时间戳来模拟，**验证后还原**）

## 停靠点
