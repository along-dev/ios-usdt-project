# W2-C7 [R3] 崩溃残留占位：**同实例自证式**回收

## 目标（★ 不变式按实际可达范围**拆成两条**，不许含糊）

| # | 不变式 | 本卡 |
|---|---|---|
| **INV-A** | 进程硬崩溃后，**同一实例**重启，**必须回收它自己留下的占位**（`progress` 1→0），使该地址可重新归集 | ✅ **本卡达成** |
| **INV-B** | **实例集发生变化**（扩容/缩容）或**跨机部署**时，无主的残留占位仍应被回收 | ❌ **本卡不达成** —— 如实登记为残余风险（见「未覆盖场景」） |
| **INV-B′** | 上述**无法自动回收**的残留，**必须产生告警**（由静默变可观测） | ✅ **本卡达成**（Owner 裁 D-12 并入） |

> **为什么要拆**：只碰 Node 侧时，「持有者已不存在」**不可判定**（见下）。
> 把它写成一条笼统的 INV，会让本卡「看起来达成了却没达成」—— 那正是本项目已犯过多次的形态。
> **拆分本身就是本卡的交付之一。**

## 缺陷事实（本轮调度实读树）

`collect-task.js:19-50` 的 `submitCollect` 用 `try/finally` 释放占位，但 **`finally` 在硬崩溃时（进程被杀）不执行**：

1. `:30-34` `acquireLock` 成功（Go 侧 `wallet.progress` 0→1）后崩溃 ⇒ **占位无人释放**；
2. 重启后 `:70` `DerivedAddress.find({ collectStatus: 'collecting' })` 找回该 doc 重新 submit；
3. `:25` `shouldCollect` 读到 `progress=1` 返 **false** ⇒ 走 `:26` `resetIdle` ⇒ **只改本地**；
4. ⇒ **Go 占位永久为 1，该地址每 2s 空转，无告警**。

## ★★ 为什么不能用 `collectPool` 当持有者判据（三条结构性理由，已实读）

`core/collect/pool.js`：`inflight = new Map()`，`has(addressId)`，`size`。
它是**本进程的并发控制器**（`collect-task.js` 用它算 `freeSlots`），**不是互斥账本**：

| # | 理由 | 锚点 |
|---|---|---|
| ① | **键空间不同**：`inflight` 键是 Mongo `addressId`，而占位键是潜客 `wallet.id` ⇒ `has(addressId)` 回答不了「wallet 42 是否有人在飞」 | `pool.js` `submit(addressId,…)` vs `collect_lock.go:43` `WHERE id=?` |
| ② | **进程局部 ≠ 全局**：占位在 **MySQL（全局共享）**，`inflight` 在**单进程内存**；worker B 的 `inflight` 为空**推不出** worker A 不持有。而**多实例是本项目默认** | `ecosystem.config.cjs:5` `instances: parseInt(process.env.WORKERS) \|\| 'max'`（`WORKERS` 未设即 `'max'`） |
| ③ | **崩溃后归零、零信息量**：硬崩溃 ⇒ `inflight` 随进程蒸发，「重启后本进程 inflight 为空」**恒真** | — |

⇒ 用 `collectPool` 作判据会得到**恒真的假阳性** ⇒ 会把活着的对端的占位释放掉 ⇒ **重复归集**（正是契约 C-2 的 409 要防的事）。

## ★ 为什么需要持有者标识

`DerivedAddress.collectStatus='collecting'` **持久在 Mongo**、不随进程消失，**是崩溃残留的可查痕迹**；
但它**只有状态、没有身份** ⇒ 无法区分「我自己的残留」与「别人正在归集」。
⇒ 必须补一个**持久化的持有者标识**。这就是本卡要扩 `derived-address.js` 的唯一原因。

## 规格（可判定）

1. `core/db/models/derived-address.js`：**纯增量**加一个字段
   `collectOwner: { type: String, default: '' }`（**不得改任何既有字段的语义或类型**）。
2. `collect-task.js`：`acquireLock` **成功后**写
   `{ collectStatus: 'collecting', collectOwner: String(process.env.NODE_APP_INSTANCE ?? '0') }`。
3. 在**既有的** `:68-70` 一次性 recovery 路径上加工：对每个 `collectStatus:'collecting'` 的 doc：
   - `collectOwner === 本实例` ⇒ **回收**：先 `releaseLock(ref)`，再复位为 `idle`（回收后允许重新归集）；
   - `collectOwner !== 本实例` ⇒ **保持现状，不释放**（不得改动其 `collectStatus`）；
   - `collectOwner` 为空（本卡上线前留下的旧数据）⇒ **保持现状不释放**，并 `logger.warn` 一条（让存量可观测）。
4. 正常释放路径（`:42-47` 的 `finally`、`resetIdle`、`handleFailure`）在释放/复位时**清空 `collectOwner`**。
5. **判据函数必须独立可测**：把「该 doc 是否应由本实例回收」写成**独立导出函数**（如 `shouldReclaim(doc, instanceId)`），
   **不得**把判据埋进 `submitCollect` 的闭包里 —— 否则本卡无法自证（见下）。

### 告警（★ Owner 裁 D-12 并入；与上面**同一次 schema 变更**）

6. **schema 同批加第二字段** `collectingAt: { type: Date }`，并加索引 `{ collectStatus: 1, collectingAt: 1 }`。
   ★ 现状：`derived-address.js` 有 `collectFailedAt`/`collectedAt`/`collectWaitingAt`，**唯独没有 `collectingAt`**
   （本轮实测全仓 `collectingAt` **0 命中**；量尺自证：同族 `collectWaitingAt`=9、`collectFailedAt`=7）。
   **没有「何时进入 collecting」的时间戳就无法判定「长期」** ⇒ 告警的可判定性直接依赖它。
7. **写入点**：`collect-task.js:141` —— 批量标记 `collectStatus:'collecting'` 的那一句 `updateMany`，
   **在同一句里**一起写 `collectOwner` 与 `collectingAt`。
   ★ 注意别写错位置：`:54` 是 `resetIdle` 把 collecting **退回** idle，**不是**写入点。
8. **告警**：每 tick 一次**本地索引查询**（走上面的索引，代价可忽略）
   `find({ collectStatus:'collecting', collectingAt: { $lt: new Date(Date.now() - 4*60*60*1000) } })`
   → `logger.warn({ addressId, chain, collectingAt }, '长期 collecting，疑似崩溃残留')`。
   ★★★ **只告警，绝不在此处 `releaseLock`** —— 这条路径**无法区分**「无主残留」与「活着的对端」，释放即重复归集。
9. **阈值 4h 的依据（不是拍的）**：`collect-confirm-task.js:8` `TIMEOUT_MS = 2*60*60*1000`（链上确认超时 2h）；
   正常归集最长生命周期 ≈ 广播 + 2h 确认 ⇒ 取 **2×** 留一倍余量，避免把「正在等确认」误报为残留。
   （同类先例：`collect-task.js:83` 的 `collectCooldownSeconds=120` / `collectWaitingMinutes=60`。）
10. **可选升级（不进本卡）**：仅对告警命中的地址再调 `/app/wallet-status` 确认潜客侧 `progress`
    —— **列为可选、本卡不做**，避免为非必需的一步引入外部依赖。

## 未覆盖场景（★ 必须逐条写进交付的证据一节，不得省略）

1. **INV-B 整体**：扩容/缩容导致某个 `NODE_APP_INSTANCE` **不再存在**时，其残留**无人认领**，无超时兜底即**永久卡死**

2. **依赖 `NODE_APP_INSTANCE` 被正确注入**：它由 pm2 **cluster 模式**注入（`ecosystem.config.cjs` 为 `cluster`）；
   若以非 pm2 方式启动，`process.env.NODE_APP_INSTANCE` 为空 ⇒ 本卡退化为 `'0'`，**多实例下所有 worker 都自称 0** ⇒ 判据失效。
3. **跨机部署**：`NODE_APP_INSTANCE` 只在**同一 pm2 集群内**唯一；不同机器上的同名值会**互相冒领**。
4. **P1-3 未修**（旁证，非本卡范围）：`app.js:185` 用 `NODE_APP_INSTANCE` 取 `instanceId`、
   `:195` 用 `WORKERS` 取 `totalWorkers`，**判据不一致** ⇒ `WORKERS` 未设时 `totalWorkers=1`，
   `instanceOnly` 守卫被跳过 ⇒ **每个 worker 都注册全部任务**。本卡**不改**它（属 P1-3），但**必须在证据里点名**。
