# F1-C11 [R2] 载荷配置缓存键不含设备维度 ⇒ 首个设备决定所有设备

## 目标

让**不同 iOS 版本（不同链）的设备各自拿到自己的载荷配置**，
而不是复用第一个请求者的缓存。

## 缺陷事实（★ 由 I1-C3 真 HTTP 实测发现）

**复现（实测，决定性对比）**：

| 条件 | iOS 16.5 | iOS 18.4 | iOS 17.5 | Windows |
|---|---|---|---|---|
| **逐次清缓存** | 1327B | **751B** | **51B(JSON unsupported)** | 51B |
| **有缓存（默认）** | 1327B | **1327B** | **1327B** | **1327B** |

★ 有缓存时 5 种 UA **返回完全相同的响应**（md5 一致）。

**根因**（`routes/config.js:16`）：

```js
const cacheKey = `payload_config:${channelCode || 'global'}`;   // ← 无设备/链维度
let buffer = await getCachedConfigBuffer(cacheKey);             // ← 命中即直接返回
if (!buffer) {
    // 只有缓存未命中才会走 pickChain(ua) 选链
}
```

**后果（逐条）**：

1. **iOS 16.5 设备访问后，后续所有设备都拿到 coruna 的载荷清单**；
2. **darksword 设备（18.4）永远拿不到自己的链** ⇒ 该链在缓存 TTL（300s）内完全不可用；
3. **空白区（17.3–18.3）永远收不到 `unsupported` 告警** ⇒
   **V0 裁决 D-3 要求的"显式告警"在端到端层面失效**；
4. 这是 **P-1 形态的变体**：HTTP 200 + 非空载荷，**看起来完全正常**，实际路由结果被缓存污染。

**★ 为何 I1-C2 没发现**：I1-C2 验证的是「`entries` 非空」（服务端同步结果），
**不经过 HTTP 缓存路径**。这正是 I1-C3（端到端）的立卡价值所在。

## 规格

### (a) 缓存键必须含设备维度

缓存的内容是「按 UA 选出的链 + 该链的 entries」，**故键必须能区分选链结果**。

**推荐做法**：把 `pickChain(ua)` 的**结果**纳入键（而非原始 UA —— 后者会导致缓存碎片化）：

```js
const route = pickChain(ua);
const routeKey = route ? `${route.chain}:${route.reach}` : 'unsupported';
const cacheKey = `payload_config:${channelCode || 'global'}:${routeKey}`;
```

★ 这样：
- 同链同 reach 的设备**共享缓存**（不碎片化）；
- 不同链/不支持**各自独立**；
- 与 `getConfigJson` 内的选链**同一判据**（`pickChain`），不会分叉。

### (b) `unsupported` 分支同样要考虑缓存

现实现中 `unsupported` **不写缓存**（`:21-26` 提前 return）—— 这本身是对的，
但**缓存键已含 `unsupported` 维度**后，需确认行为一致（可继续不缓存，或缓存短 TTL）。

**本卡采用：`unsupported` 仍不写缓存**（保持既有行为，最小改动）。

### (c) 不得改变 `config-builder` 的逻辑

`getConfigJson` 的选链与 entries 过滤**已经在 I1-C1/I1-C2 正确实现**。
本卡**只改缓存键**，不动 `services/**`。

### (d) 不得破坏既有 ETag / 304 行为

ETag 基于 buffer 的 md5 —— 键分离后**各链各自有 ETag**，行为正确。**不得改动该逻辑**。

## ★ 判据先于实现（判据 9）

`verify_f1c11_cache_key.py`：真 HTTP + **不清缓存** + 逐 UA 对比：

| # | 用例 | 断言 | 红态（改前） |
|---|---|---|---|
| **C1** | 不清缓存，依次请求 iOS 16.5 → 18.4 → 17.5 | 三者响应**互不相同** | 三者**相同** ⇒ 红 |
| **C2** | 先请求 Windows（unsupported），再请求 iOS 16.5 | 后者仍能拿到**载荷**（不受前者污染） | 后者拿到 JSON unsupported ⇒ 红 |
| **C3** | 同链设备（iOS 16.5 vs 16.6）连续请求 | 响应**相同**（防缓存碎片化） | 绿（防改过头） |
| **C4** | 清缓存后三条路径 | 与 I1-C3 结果一致 | 绿 |

★ **C2 是关键的顺序污染用例**：它证明「缓存的隔离方向」是双向的，不只是"先 coruna 污染别人"。
★ **C3 是防改过头用例**：不能为了隔离而把同链设备也拆开（那是缓存碎片化，会让 TTL 形同虚设）。

## 不在范围

- 不改 `invalidations` 的调用方（`payloads.js` / `payload-params.js` / `app.js`）——

  ★ **这是本卡最容易改错的地方**：前缀必须保持 `payload_config:`
