# I3-C1 [R1] 文档时效门禁

## 目标

让**「报告过期」这件事自动被发现**，而不是靠人读。

## 背景（本轮实测）

本轮审核发现：`09-docs/reports/全量审核结论与优化方案.md`
把**4 条已修复的 P0** 仍列为"当前缺陷"，且**无时效标注**
⇒ **下个会话会去"修"已修好的代码**（**P-9** 形态）。

## 规格

### (a) 每份报告必须声明时效

报告头部须含：
`编制日期` + `**时效截止：<某事件>**` + `**当前状态：有效 / 已过期（指向新文档）**`。

### (b) 建立「文档 → 被后续改动」的登记

`09-docs/reports/文档时效索引.md`：逐份列
`文档` / `编制日期` / `有多少条结论已被后续卡片改动` / `当前是否仍可作依据`。

★ **本轮已手工建立两份实例**（作为格式基准）：
- `全量审核结论与优化方案.md` —— 已加时效声明（4 条 P0 已划掉）
- `需求文档.md` §3.3 —— 一期范围裁决留痕

### (c) 门禁脚本

`verify_doc_freshness.py` 断言：
- ★ **不得有报告声称"当前缺陷"而其对应修复卡已标记完成**
- 每份 `09-docs/reports/*.md` **必须含时效字段**（缺字段即红）

## 证据要求

- `verify_doc_freshness.py` 的真实退出码
- `文档时效索引.md` 的实际内容
- ★ 脚本能**实际抓到**至少一处已知过期
  （用前置断言：拿本轮改动**前**的状态验证它能报红）

## 停靠点

1. 若需改 `09-docs/` 下**其他文档**（非本卡 allowed_paths）⇒ 停下升级
2. 若发现无法机械判定"某结论是否已过期" ⇒ 停下升级（说明该判据需人工）
