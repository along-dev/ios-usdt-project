## 十 · 追加（⌛2026-10-03T20:27:09+0800）：**间歇假红的根因 = 并发运行**（本线自造的运行器缺陷，已修）

### 10.1 现象（两次同一自相矛盾形态）

- `verify_f1c9`：`R1 公域 + 正确地址(平台,trx): code=7 bill=3(应3) roles=['1','2','3']` —— **报错却落了 3 笔**
- `verify_money_path`：`(c) 并发同 tx_hash 幂等: 第一次 code=7 第二次 code=0 bill行数=2(应2) duplicated=True`

### 10.2 根因（服务端日志实证）

`_wbe01d_ws/_svc_iso.out` 显示**同一 `tx_hash` 的两次请求相隔 1 毫秒**到达（`20:17:43.503` / `.504`），服务端报：
```
Error 1062: Duplicate entry 'i2c1-f1c9-R1-1' for key 'uk_txhash_role'
```
⇒ 两个客户端**双双越过预检** ⇒ 撞复合唯一键 ⇒ **落败方得 `code=7`**，而**赢家的 3 笔已提交** ⇒ 这正是 `code=7` 与 `bill=3` 并存的原因。
★ 而当时**只有一个实例在听 8900** ⇒ **两个 `iso_run` 进程并发**（实测查到遗留的 `python.exe` PID 12564 正在跑）。

### 10.3 为什么危害被放大

两个 `iso_run` 各自的 `finally` 都会 `stop_iso()` —— 而它们**共用 8900** ⇒ **后结束的那个会把对方正在用的实例杀掉** ⇒ 另一方涌现**大面积假红**（实测某轮 `state2` 的 `f1c8` 5 项红、`money_path` 16 项红）。

### 10.4 修法与验证

| 项 | 内容 |
|---|---|
| 互斥 | `iso_run.py` 加**单实例锁**（`_iso_run.lock` 记持有者 PID）：持锁者活着 ⇒ **拒绝并发**；已死 ⇒ **自愈接管** |
| 附带修 | `_pid_alive` 的**假阳性**（`tasklist` 无匹配时把 `INFO:…` 打到 stdout ⇒ 只看"有没有输出"会让**任何** PID 都算存活 ⇒ 锁永久卡死）—— 已按"解析结构（首字符是否 `"`）"修，并记入 `E-360` |
| 验证 | 清掉遗留进程后，`iso_run` **连续 `ISO_RUN=OK`**（两态 6/6 全绿）＋ **跑后无锁残留** |

### 10.5 两条如实登记的边界

1. ★ **本日我前后启动过多次 `iso_run`（含后台）** —— 互斥锁只能防"以后"，**防不了"已经并发的"**。⇒ 建议今后**同一时刻只允许一条 `iso_run`、且不并行启动**；**发现假红先查是否有并发实例**。
2. ⚠️ **`verify_money_path` 的幂等用例本身是"与设计赛跑"**：它并发打两次同 `tx_hash` 并要求**两次都 `code==0`**，但产品的并发兜底恰恰是**让落败方报错**（`uk_txhash_role` ⇒ 1062）。⇒ 只在两次请求**串行**时才通过。**该断言的期望值是否应放宽**，请复核方/调度裁。
