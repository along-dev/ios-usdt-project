# W2-C6 [R3] P0-4 归集确认链：回传失败即永久卡死

## 目标

消除**「一次回传失败 ⇒ 该地址永久无法归集，且无任何告警」**。

## 缺陷事实（本轮调度实读树，非转述）

`02-backend-node/src_restored/schedules/collect-confirm-task.js`：

| 位置 | 现状 |
|---|---|
| `:20` | `CollectLog.find({ status: 'pending' }).limit(500)` —— **只有 `pending` 会被再选中** |
| `:37` | **先** `updateOne({_id}, {$set:{status:'confirmed', confirmedAt}})` |
| `:42` | **再** `await reportResult({...})`，且**丢弃返回值**（无 `const r =`） |
| `:51-57` | 随后按「本地址还有无 pending」把地址 `collectStatus` **无条件**重置为 `idle` |
| `:72-74` | 整个 per-log 体在 `try/catch` 里，异常只 `logger.warn('confirm: query error, skipping')` |

⇒ **两个坏处**：
1. **回传失败后 log 已是 `confirmed`** ⇒ `:20` 的 `status:'pending'` 永不命中 ⇒ **再无重试机会**；
2. 地址却被 `:53` 重置为 `idle` ⇒ gasleak 会**反复尝试**该地址，而潜客侧 `wallet.progress` **仍停在 1**
   ⇒ 潜客 `Sk()` 与 gasleak 两侧都归集不了，**链上资产已转出、潜客无账单，且无任何告警**。

★ **与 W2-C3 的串行边（本卡 `depends` 的依据）**：W2-C3 会把 `reportResult` 改为**返回失败标记**。
若本卡不改，那个标记**会被 `:42` 拿到即丢**（已实测）⇒ **W2-C3 的产出将沦为「仅供未来消费」的空产出**。
⇒ **两张卡必须同批验收**；本卡是那个标记的**唯一消费者**。

## 规格

### (a) 回传顺序与重试 —— **可判定，本卡主体**

1. **顺序倒置**：**先** `await reportResult(...)` 并**判定其返回值**；**只有回传成功**才置 `status:'confirmed'`（并 `confirmedAt`）。
2. **回传失败**：log **保持 `pending`**（不得置 confirmed），并写入可观测标记（建议 `reportedAttempts` 自增 + `lastReportError` + `lastReportAt`），
   供下一轮 `:20` 重新选中重试。
3. **重试上限**：加**有界重试**（建议上限与退避写在常量里，并在达到上限时 `logger.error` **显式告警**，
   不再静默）—— 上限值由执行者在卡内常量中给出并在证据里说明理由。
4. **地址重置条件**：`collectStatus → idle` 的重置**必须**以「该地址的全部 log 均已 `confirmed` 且**回传成功**」为前提；
   **回传未成功的 log 存在时不得重置**（否则 `:52-56` 的现状会把故障掩蔽掉）。
5. **保持 `handleFailure` 既有语义不变**：`failed` / `timeout` 路径仍走 `:82-101`（其中 `:87` 已 `releaseLock`，**不要动**）。

### (b) 进程崩溃后占位无人释放 —— **已裁（Owner 2026-09-27「两件都按你的建议」）：本卡不做；(b2) 另立 `W2-C7`**

**缺陷事实**：`collect-task.js:19-50` 的 `submitCollect` 用 `try/finally` 释放占位。
但 `finally` 在**硬崩溃**（进程被杀）时**不执行**：
- `:30-34` `acquireLock` 成功（Go 侧 `wallet.progress` 0→1）后崩溃 ⇒ **占位无人释放**；
- 重启后 `:70` recovery 找出 `collectStatus:'collecting'` 的 doc 重新 submit ⇒
  `:25` `shouldCollect` 读到 `progress=1` 返 **false** ⇒ 走 `:26` `resetIdle` ⇒ **只改本地** ⇒
  **Go 占位永久为 1，该地址每 2s 空转**。

**★ 为什么审核报告 §0.4 的处方「`resetIdle` 增补 `releaseLock`」不能照抄**（本轮实读）：

`resetIdle` 的两个调用点 `:26` / `:31` **都发生在未取得占位时**（`locked` 仍为 `false`）。
在此处无条件 `releaseLock`，会把**活着的另一个 worker 的占位**误释放 ⇒ **造成重复归集**（正是 C-2 的 409 想防的事）。
⇒ **必须先能区分「自身崩溃残留」与「活的持有者」**，这需要一次设计决策。

**Go 侧事实（本轮实读）**：占位是 **MySQL 列**（`service/app/collect_lock.go:43-44` 原子 `UPDATE … WHERE progress=0`；
`:57-60` `ReleaseCollectLock` 条件释放 `WHERE progress=1`，**幂等**），
**全 Go 树无任何 TTL / 过期**（无 `Expire` / `SetEX` / `collectingAt`）。
⇒ 崩溃残留**没有任何自动回收机制**。

**三个选项（已裁为 (b3)，下表留档）**：

| 选项 | 做法 | 代价 / 影响 |
|---|---|---|
| **(b1) Go 侧加租约** | 占位加 `collecting_at` + 超时回收 | ★ 触**真高危文件** `01-backend-go/api/v1/app/collect_lock.go` + `collect_release.go`，且**改契约 C-2**（新增超时语义）⇒ 必须**拆出为独立卡**，并回 Owner 批契约变更 |
| **(b2) Node 侧判据** | 仅当能**自证**是自身崩溃残留（如本地租约表 / 进程启动代次标记）时才 `releaseLock` | 不碰 Go；但多实例部署下判据可靠性需论证；**需一次设计** |
| **(b3) 接受为残余风险** | 本卡只做 (a)，(b) 登记为待办 | 代价：崩溃后该地址**永久卡死**（无告警）。注：泄漏窗口较窄 —— 仅「`acquireLock` 后、在产生 pending log 或 finally 之前崩溃」这一段；`failed`/`timeout` 路径已有 `releaseLock` |

**★ 裁决（Owner 2026-09-27）**：采用 **(b3) 先行 + (b2) 另立**。
- **本卡（`W2-C6`）只做 (a) 段**；(b) 段**不在本卡范围**，作为**已登记的残余风险**（见下）。
- **(b2) 已另立为 `W2-C7-崩溃残留占位自证回收.md`**（不在本卡范围）。
- **(b1) 未采用**（触真高危 + 改契约 C-2，代价最高，且 (b) 触发窗口窄）。
- 理由：(a) 覆盖**正常运行下的回传失败**（高频、可复现）；(b) 只在**进程崩溃**的窄窗口触发（低频）。
  先修高频，不让低频拖住 (a)。

**★ 残余风险（(b3) 的代价，如实登记）**：若进程在 `acquireLock` 之后、产生 pending log 或 `finally` 之前**硬崩溃**，
则该 wallet 的 Go 占位（`wallet.progress=1`）**无人释放**，该地址每 2s 空转、**且无告警**，直到人工干预。
（`failed` / `timeout` 路径已有 `releaseLock` —— 见 `collect-confirm-task.js:87` —— **不在此风险内**。）
