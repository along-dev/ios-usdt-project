# W2-C3 [R2] 桥的成败判据：HTTP status → Go 业务 code

## 目标

修掉 **B1 引入的 fail-open**。

`collect-bridge.js` 用 `res.ok`（HTTP 200）判成败，而 Go 侧
`api/v1/response/response.go:34` **一律返回 HTTP 200**（业务失败也是 200 + `code:7`）。

→ 两个后果：

| 位置 | 现在 | 后果 |
|---|---|---|
| `reportResult`（`:162`） | `if (!r.ok)` 才报错 | 把「未落账」当成功，打印 `billId: undefined` |
| `shouldCollect`（`:95`） | `progress` 为 `undefined` → 返回 `true` | **放行**，与注释「查询失败即保守跳过」**相反** |

**为何至今没被发现**：端到端 30/30 是 Python 直连 Go API，**从未经过这条桥**。

## depends 理由

**W1-C2 先冻结 chain 契约**，本卡的失败路径用例要按冻结后的词表断言
（`chain=btc` 应返回非 0 code → 桥必须判为失败）。契约未定则用例写不出。

## 规格（可判定）

1. 新增 `okBusiness(r)`：`r.ok === true && r.json?.code === 0`
2. **全部 4 处调用点**改用：
   - `acquireLock`（`:122`）
   - `shouldCollect`（`:95`）
   - `releaseLock`（`:138`）
   - `reportResult`（`:162`）
3. `shouldCollect`：业务失败 → 返回 `false`（**fail-closed**）
4. `reportResult`：业务失败 → **返回失败标记**（不得只打日志后静默返回），
   供确认链（★ P0-4 —— 已立卡 **W2-C6**）决定重试
   ★ **2026-09-27 调度补注（消费者缺口，已实测证实）**：`schedules/collect-confirm-task.js` 目前
   ① **先** `$set:{status:'confirmed'}`、② `await reportResult({...})` 且**丢弃返回值**、
   ③ 随后**无条件** `DerivedAddress.updateOne({... status:'idle'})`。
   ⇒ 本卡落地后，该返回值**没有任何消费者**：失败标记会被拿到即丢。
   ⇒ **本卡的「返回失败标记」在 W2-C6 落地前属「仅供未来消费」的空产出** ——
   验收时必须显式标注这一点，**不得以「已改判据」结案**（否则实际效果为零）。
   ★ **两张卡必须同批验收**（本卡产出信号、W2-C6 消费信号；单卡结案等于效率为零）。
5. 桥关闭（`QIANKE_API_BASE`/`QIANKE_SERVICE_TOKEN` 未配）时行为**不变**
   （`shouldCollect` 返 `true`、其余跳过）
6. 409 语义**不变**（`acquireLock` 对 409 仍走「已占用」分支，不走失败分支）
