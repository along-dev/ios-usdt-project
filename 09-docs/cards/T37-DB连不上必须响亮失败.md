## 一 · 缺陷（**已由受控实验确证，非推理**）

`gorm.Open` 失败（**库连不上／口令错／库名错** —— 生产最常见的启动故障）时：

```
gorm.Open 失败 ⇒ GormMysql() `return nil` ⇒ global.GVA_DB == nil
  ⇒ ensure_seed.go:36-39 只 Warn 后 return（不阻断）
  ⇒ core.RunWindowsServer() 里【无条件】blockchain.LoadRpcList()
  ⇒ scan.go:17 `global.GVA_DB.Find(&RpcList)` ⇒ nil 接收者 panic
  ⇒ 进程 exit 2，栈顶指向 blockchain/scan.go:17
```

★ **实验证据**（调度 ⌛2026-10-04 亲跑）：隔离 ws 的 `config.yaml` DB 端口 `13306`→`13399`（连不上）、保留 `resource/`、用从 HEAD 重编的件起 ⇒ **`PROBE_EXIT=2`**、栈顶 = `scan.go:17`、**8900 从未绑定**。留盘 `_fix_work/_t35dsn_probe_result.txt`（`98687a37…`）。

**危害**：**崩溃是 fail-closed ✓，但<ins>栈顶指向错误的模块</ins>** —— 运维看到"链上扫描模块崩了"，而真因是 **DB 配置/连通性** ⇒ **排查方向被带偏**。

## 二 · 目标
**「DB 连不上」必须由它自己<ins>指名道姓</ins>地响亮失败**，且**早于**任何依赖 `GVA_DB` 的调用；
★ **不得**把"库连不上"与"业务表尚未迁移"混为一谈（后者**是有意的降级**——见 §三 ⛔）。
