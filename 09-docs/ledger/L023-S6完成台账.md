## 2 · ★★★ 执行者纠正了我的判据量尺（**P-5 第 N 次**）

### 它指出的问题

> **判据打印的 `N=13` 是量尺正则放大，不是真实 N**。
> judge 在 `dump_all` 后取 1200 字符窗口，同时命中了 `sub_commands` 字面量数组（3/4 项）
> 与 `steps` 字面量（3/4 项）并累加 ⇒ **13 = 3+3+3+4**。
> **真实 N 由运行时的 `steps.length` 决定，即 3 与 4**，且已写入回执字段
> `n_commands` / `manual_n`。**M9 的数值不宜直接引用为业务事实。**

### 我的复核（**确认它说得对**）

```
M9 dump_all 展开为 N=13 条子命令
   子命令 ['keychain','exfil','exfil', 'keychain','exfil','exfil','exfil',
           'keychain','exfil','exfil', 'keychain','exfil','exfil']
   ← ★ 明显是 4 组重复（3+3+3+4），确认量尺放大
```

### 我的修正（**分两步**）

**第一步**：只解析 `steps` 数组（而非窗口内所有子命令名）
⇒ `dump_all` 报 **N=3** ✓（与执行者一致）

**第二步**（**发现仍有偏差**）：
`collect_all` 我的判据仍报 **N=3**（执行者说 **4**）
⇒ **根因**：两个复合命令共用
`var steps = cmd.cmd === 'dump_all' ? [...] : [...]` 三元表达式，
**静态正则只能确定性抓到第一个分支**。

**⇒ 最终处置**：**承认静态解析的固有局限**，判据**改为**：
- 只断言「**存在展开且 N ≥ 2**」
- **不断言确切数值**
- **输出中明确声明**：
  > **真实 N 应以【运行时 `steps.length`】为准**（执行者已写入回执字段
  > `n_commands` / `manual_n`）。本项的数值【不构成业务事实】。

### ★ 这是本轮**最有价值的方法论修正**

| 教训 | 内容 |
|---|---|
| **静态正则无法完整解析三元表达式** | 多个分支共用一个赋值语句时，只能抓第一个 |
| **判据不该断言"静态无法可靠计算的值"** | 应断言"存在性/下界"，而非"确切值" |
| **判据应如实声明其局限** | 明确"本项数值不构成业务事实" |

★ **这比"修对正则"更根本** —— 它承认了**静态分析的能力边界**。

## 3 · ★ 本轮新增 P 条目

建议补入 `开发规则与调度说明.md`：

> **P-29**：★★ **判据不得断言"静态无法可靠计算的值"** ——
> 本轮实证（S6 判据 M9）：多个分支共用 `var x = cond ? [...] : [...]` 时，
> 静态正则只能确定性抓到第一个分支 ⇒ 报出**低估值**（`collect_all` 报 3，实际 4）。
> ★ **正确做法**：① 只断言**存在性/下界**（如「N ≥ 2」）；
> ② **在输出中声明局限**（「真实值以运行时为准，本项不构成业务事实」）；
> ③ 若必须在静态层面验证确切值 ⇒ **须用 AST 解析**（本项目无 JS 工具链 ⇒ 不可行）。
> ★ 这是 **P-5 / P-13 的同族**（量尺的有效性边界）。
