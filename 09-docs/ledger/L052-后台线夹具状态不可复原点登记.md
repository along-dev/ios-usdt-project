## 1 · 发生了什么（时点与读数）

| 时点 | 动作 | `wallet(1,2)` 状态 |
|---|---|---|
| WBE01-C 实施前（多轮实测） | — | `id=1: region=0, progress=0`（两地址在位）· `id=2: region=0, progress=0`（两地址为 NULL） |
| **第一版 wallet 快照测试** | 我跑了 `UPDATE wallet SET region=9, progress=9 WHERE id IN (1,2);` 模拟"脚本改坏 wallet"，然后调用当时**有 bug** 的恢复函数 | `id=1` 恢复了；**`id=2` 未恢复** ⇒ 留在 `9/9` |
| 发现后 | 逐层排查（见 §2） | 确认 `id=2` 被遗漏的原因 |
| 处置 | `UPDATE wallet SET region=0, progress=0 WHERE id=2;` | `id=2` 回到 `0/0`（**按夹具约定态**，非"原值"） |

**⇒ 不可复原点**：`wallet(id=2)` 的 `region` / `progress` **在被覆写之前的值，不可考**。
（**两地址列未受影响**：实测 `btc_address`/`trx_address` **均为 NULL**，我的 UPDATE 未触及它们。）

## 2 · 为什么会漏（根因，两处，均已修）

1. **`if len(r) >= 5` 过滤会静默丢行** —— mysql 批处理对**含 NULL 的列会少输出**（实测 `['2','9','9','NULL']` 只有 4 个元素）⇒ `id=2` 整行被丢弃 ⇒ 快照漏行 ⇒ **恢复也漏行**。
2. **批处理区分不了 NULL 与空串** ⇒ 即使取到，恢复也会把**空串**写成 **NULL**。
⇒ 两个 bug 的**共同教训**：**用 shell 结构化输出承载"结构化语义"本身就脆**（NULL / 空串 / 少列三样都会骗人）。
⇒ **设计已改简单**：不做"任意原值快照"，改为**退出时复位到夹具约定态**，仅 `e2e_test_api.py` 额外用 `IFNULL(col,'<NULL>')` 哨兵存/恢复它覆写的两列地址。

## 3 · ★ 使用纪律（**本条是这份登记的主要用途**）

> **凡引用 `wallet(id=1,2)` <ins>历史状态</ins>的结论，必须标注：「该行状态曾<不可精确复原>（见 `L052`）」**

理由：`id=2` 的 `region`/`progress` 在 ⌛2026-10-03 的一段时间内**处于被覆写后的值**，且**原值不可考**。
⇒ 任何"某时点 `wallet(1,2)` 是 X"的断言，**在 ⌛2026-10-03 附近不可靠**。
⇒ 反之，**当前值可信**（已按约定态还原：`1: 0/0` ＋ 两地址在位；`2: 0/0` ＋ 两地址 NULL）—— 且已在动工前后**多次实读一致**。
