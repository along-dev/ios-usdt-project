## 3 · R2-C1 诊断（★ 真因与方案描述不符）

### 方案称

> `R2-C1` 卡片基线脚本定位修正（**10 张 PARSE_FAIL**）

### 调度实测（时点 2026-09-30 01:2x）

```
TOTAL base 记录 78 条；不符 56 条；PARSE_FAIL 卡 11 张
```

### ★ 真因：判据的解析假设不成立（三种合法形态只认一种）

`verify_card_baselines.py:21-27` 的 `ENTRY_RE` **要求四字段齐全**：

```
-\s*path: ...\n
\s*sha256:\s*([0-9a-f]{64})\n     ← ★ 必须是 64 位 hex
\s*bytes:\s*(\d+)\n                ← ★ 必须是数字
\s*eol:\s*([A-Za-z]+)
```

**而实际卡有三种形态**：

| 形态 | 例 | 为何不匹配 |
|---|---|---|
| **① 占位符** | I1-C3：`sha256: 由 I1-C2 产出后由调度重取` | `sha256` 非 hex、`bytes` 非数字 |
| **② 单行列表** | F1-C7 / I3-C3：`- 02-backend-node\README.md` | 无四字段结构 |
| **③ 完整四字段** | D0-C1/C2/C4/C5、I1-C1 等 | ✅ 正常解析 |

**⇒ 判据把"合法的卡形态差异"误报为"解析失败"。**

★ **判据自身已提示「先怀疑正则坏了」** —— 该自检写得正确。

### ★ 另：56 条"不符"是**预期**，非缺陷

卡基线**必然过期于其自身产出的改动**（卡写完 → 执行者改文件 → 基线自然不符）。
⇒ 这 56 条**不含有效信息**，反而**淹没**真正的基线异常。

### 停靠点判定

**按调度规则「任何改判据脚本的卡 ⇒ 停下升级」** ⇒
**本卡的"修判据"须 Owner 裁决**（见 L012 §5 裁决 A）。
