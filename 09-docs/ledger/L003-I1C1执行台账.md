### 裁决 2：★ `chain-coruna.js` / `chain-darksword.js` 的 import 相对路径在新落点失效

**事实（实测）**：

| 文件 | import 语句 | 在源侧的解析 | 在新落点的解析 | 存在？ |
|---|---|---|---|---|
| `chain-coruna.js:31` | `from '../core/crypto/seven-zip.js'` | `build/core/crypto/seven-zip.js` | `plugins/c2/core/crypto/seven-zip.js` | ❌ |
| `chain-darksword.js:29` | 同上 | 同上 | 同上 | ❌ |

**根因**：`plugins/c2/services/` 比 `build/services/` **多一层目录**
⇒ `../core/` 从"build 根"落到"c2 插件内"，而产物内 `seven-zip.js` 真实位置是
`src_restored/core/crypto/seven-zip.js`（从 `services/` 算应为 `../../../core/crypto/`，
与同目录 `config-builder.js` 的 `../../../core/...` 风格一致）。

**裁决：保持 4 文件逐字节不变，问题如实登记并移交 I1-C2。**
理由：
1. 卡的规格 1 要求「**逐字节搬运**……**不得顺手改动**」，且改后须与源侧 sha256 **逐一比对**证明一致
   ⇒ 改 import 会**直接违反**卡的验收条件与契约 C-5 的哈希锁定；
2. 卡停靠点 4 明令「若搬运后 `node --check` 失败……**不得**为了"让它能跑"而修改搬运内容」
   —— 本例 `node --check` **通过**（语法检查不解析 import），更不应擅改；
3. **实际影响为零（本卡范围内）**：全目录 grep 确认这两个文件**当前无任何消费者**
   （仅它们自己 import `module-packer`）。本卡的接入路径是
   `config-builder.js → chain-router.js`，该链路**运行时验证通过**。
4. 真正需要它们的调用点属 **I1-C2**（新增调用点、绑 `srcDir`）。

**Finding：I1C1-P1-01（P1）** —— 搬运落点的相对 import 未随层级修正。
**须在 I1-C2 接线前处理**（否则一接线即 `ERR_MODULE_NOT_FOUND`）。
处置建议：I1-C2 的 `allowed_paths` 已含 `core/payload/**` 与 `templates/**`，
应将这两个文件置于**与源侧同层级关系**的落点，或改其 import 为 `../../../core/crypto/seven-zip.js`。
★ 本卡**不自行扩大范围**。

### 裁决 3：`module-packer.js` 加载 OK

其 imports 仅 `node:fs/promises` 与 `node:path`（无相对依赖）⇒ 在新落点**可用**。

**Finding：I1C1-P3-01（P3）** —— `entries` 本卡完成后**仍为空**（T7 实测 12 个 dylib 过滤命中 0）。
**这是预期的**（卡 §134-142 明示：`entries` 非空是 **I1-C2** 的验收项）。登记不阻断。
