## 1 · 为什么必须有这张卡（不是理论问题）

**D0-C4 收口时的实证坑**：

| 项 | 值 |
|---|---|
| 静态判据 C1–C6 | **全绿** |
| `go build ./...` | **EXIT=0** |
| `go vet ./service/app/` | **EXIT=0** |
| **真 HTTP 断言 R2** | 🔴 **失败** |

**根因**：
```
service\app\wallet_resolver.go   mtime = 09-30 01:04:44
_i2c1_server.exe                 mtime = 09-28 22:05:44   ← 早 2 天
```

**⇒ 8888 跑的是**旧二进制**，改动**根本没生效**。
**重新编译并重启后，R1–R6 才全部符合。**

★ **⇒ 静态判据 + 编译门【不能】替代运行时验证（P-18）；
而"运行时验证"的前提是"跑的是新代码" —— 本卡把该前提变成机械门禁。**

## 5 · ★ F6 的设计要点（一次自查修正）

**初版 F6 【未带 `X-Service-Token`】** ⇒ 得：
```
HTTP=401  {"code":7,"msg":"invalid or missing X-Service-Token"}
```
**⇒ 那是【鉴权层】拒绝，根本没到业务层 ⇒ 该断言证明不了"新校验生效"。**

**修正**：
- **带 token**（契约 C-2）⇒ 触达业务层 ⇒ `{"code":7,"msg":"wallet_id=... 与 device_id/address 不一致"}`
- **同时保留对照**：不带 token ⇒ **401**（证明 token 是触达业务层的前提）

**⇒ 两条合起来才有意义** ✓

★ **这是 P-5 的又一实例**（量尺构造错误 ⇒ 断言无效）。
