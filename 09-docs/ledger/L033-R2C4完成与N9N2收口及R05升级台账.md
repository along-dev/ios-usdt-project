## 2 · ★★★ 执行者的**重大发现**：它推翻了我卡里的**预期**

### 我在卡里写的（**基于推测**）

> ★ `sys_captcha.go:6` 的 tag 语法错**可能导致该字段 JSON 序列化行为异常** ⇒
> 修完须**验证 captcha 接口行为未变**。

### 它实测的（**基于实证**）

> ★★ **重要发现（与卡文的预期相反）**：卡文预期「修复前序列化行为异常」。
> **实测 `encoding/json` 是容错的** ——
> 原因是 `reflect.StructTag.Get`/`Lookup` 在遇到语法错时**整段跳过**该 specifier，
> 返回的**已是干净值** `captchaLength`
> （Go 源码 `reflect/type.go` Lookup：遇 `"` 语法错即 break），
> **多余的引号根本传不到 `json.parseTag`**。
>
> ⇒ **结论：本卡 tag 修复是「纯防御性」的，不改变任何 API 响应**
> （BEFORE/AFTER wire **逐字节一致**）。
>
> 修复价值在于消除 `StructTag.Get` 的 **UB**
> （官方文档明言非规范格式返回值 ***unspecified***）
> —— **不同 Go 版本/编译器可能不同**。

**⇒ 这是 P-22 / P-24 的同族**：
**"知道风险"不等于"风险已发生"** ⇒ **须实测，不得凭推测写判据预期**。

★ **且它做了正确的对照实验**（V4 探针构造改前/改后两份 struct 比对）。
