## 2 · 本轮自查发现并修复的缺陷（配合全局账 `E-313`）—— 含审核一轮与平台边界

**缺陷**：我给 W-AD-04 的 APK `sha256` 校验加了「`size:mtimeMs` 缓存」，理由是端点匿名公开、重算 16 MB 哈希太贵。
**实测可绕**：把 APK 换成**等长**且 `mtime` **还原到逐位相同**的替换件 ⇒ 缓存键不变 ⇒ **命中缓存、跳过校验、200 分发替换件**。
而那条校验的唯一目的就是「防目录被塞入非登记文件」⇒ **缓存恰好只对它失效**。

**修法演进（两版，第二版是终版）**

| 版本 | 做法 | 结果 |
|---|---|---|
| A（首修） | 删缓存，**每请求流式重算** | 校验可靠，但匿名端点每请求 ≈57 ms 主线程 CPU（审核方实测 冷 110 ms / 暖 57.5 ms；本机复核 冷 65.1 / 暖 46.3 ms），而 **3000 是全线条共用进程** ⇒ CPU 缓解被撤掉 |
| **B（终版）** | 键扩为 **`ino:size:mtimeMs:ctimeMs`** ＋ **fd 复用**（`open` → 同一 fh `stat` → 同一 fh 算哈希 → 同一 fh 送流） | 正常情形命中缓存（省那 57 ms）；原地改写动 ctime、rename 动 ino ⇒ 未命中；**fd 复用同时闭合残余 TOCTOU**（校验的、发出的、取键的是同一份内容） |

**无句柄泄漏**：`Get-Process.Handles` 下载 12 次前后 **285 → 285**（差 0）。

### ★★ 平台闸（总调度 ⌛2026-10-03 裁定，**已实现**）

**判据**：`process.platform === 'linux'` 才启用该缓存；**非 Linux 一律每请求重算**。
**为什么**：该键的保证依赖 Linux 的 `ctime` 语义（内核置位、**用户态改不了**）；**非 Linux 上 `ctime` 是创建时间，原地覆写不更新它** ⇒ 键不变 ⇒ 缓存命中 ⇒ 那个优化**不构成保证**（本机 Windows 实测确实如此）。
**采纳它的代价（不得当成"已验"）**：**prod(Linux) 的缓存分支在本地完全不被覆盖**。

| 平台 | 该攻击的实测 | 判定 |
|---|---|---|
| **Linux（部署形态：Docker / `08-infra/compose/docker-compose.yml`）** | 闸 **ON**（走缓存）；键的成立靠 ctime 语义 | **本机无法验证**（无 docker / podman / WSL，三条命令实测均落空）⇒ 见下方**部署期验证项** |
| **Windows（本机 dev，win32）** | 闸 **OFF**（每请求重算）⇒ 攻击应被拒 | **可判 PASS**（加闸后实测 503，见 §2 末读数） |
