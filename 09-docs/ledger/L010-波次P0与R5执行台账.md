| `06-android\tools\bstage3.py` | `d8493156c990452ce632f4bb10a4ac24790e4823e96037d47561ddc287be7000` | 2,383 | LF |

### ★ 缺陷事实（调度实跑确证）

**它已经解出了正确的 mode，却不用**：

```
mode   = 'AES/CTR/NoPadding'      ← 实测（由 :22-23 的 xhfvif 还原）
parts  = ['AES', 'CTR', 'NoPadding']
len(parts) == 3  ⇒  现有代码选 CBC
但 parts[1] 实际是 CTR            ← 应为 CTR
```

**分支只看段数，不看算法段** ⇒ **算法选错，解出乱码且不报错**（静默出错）。

**铁证对照**：`bstage.py:13-14`、`bstage2.py:12`、`bstage3.py:12` **三个全用 `MODE_CTR` + `Counter.new(128, initial_value=iv)`**，
**唯独 `bdecrypt.py:46` 用 `MODE_CBC`**。

### 判据：`verify_d0c1_aes_mode.py`

**红态（改前）**：**3 项失败** —— B2（无 CTR）、B3（无 Counter）、B6（残留 CBC 兜底）

### ★★ 我的弱断言与自查（P-13）

**初版 B1 判"`parts[1]` 是否出现"** ⇒ 匹配到 `:47` 的 `parts[1] == "ECB"` ⇒ **假绿**。

**但 `:47` 只在 `len(parts)==2` 时才看它**；真实的 `AES/CTR/...`（`len==3`）**根本不到 `parts[1]`**
⇒ **这才是缺陷本体**。

**已修正**为「必须存在**能选中 CTR** 的算法分派」（`dispatch_ctr or dispatch_generic`），
**修正后 B1 正确转红**（`dispatch_ctr=False dispatch_generic=False`）。

⇒ **固化为 P-13 的新实例**（第 2 次自查发现弱断言）。

### Finding

- **D0C1-P2-01（P2，待执行者确认）**：`bdecrypt.py` 的**解析格式**与 `bstage.py` **不同**
  （`[int32 count]`+N×`[...]` vs 重复 `[int32 size][int16 nameLen][name]`）

## 5 · 判据脚本的性能缺陷与修复

**现象**：`verify_d0c2_ankr_key.py` **两次超时（>280s）**，输出 0 字节。

**根因**：`iter_files` 遍历全仓时**逐文件 `read()`**，
把 `.apk`/`.ipa`/`.wasm`/`.png` 等**数百 MB 二进制**读进内存 ⇒ 假死。

**修复**：

1. **扩展名白名单**（只扫文本类：`.go/.js/.md/.json/.sql/...`）；
2. **单文件上限 8 MB**；
3. **目录剪枝**（跳过 `node_modules`/`reference`/`dist`/`build`）；
4. **一次性读取复用**（A4 的 8 个 provider 不再重复 open）。

**修复后**：自检 **1.4 秒**（此前 >280s）；全量 **118.6 秒**。

★ **验证未漏检**：对照值「含 `rpc.ankr.com` 的文本文件数 = 6」**修复前后一致**。

**另**：`go test` 在缓存失效后**全量重编译 >280s** ⇒
判据新增 `--skip-go`（**SKIP 不计为 PASS**，P-13），A6 由后台 job 单独验证。
