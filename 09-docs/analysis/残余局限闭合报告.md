与 v21998 复原的真实值对照。

### 1.2 结果

| 模型 | 字段 | gasleak 类型 |
|---|---|---|

| | `token` | String, enum `['native','usdt','usdc']` |
| | **`threshold`** | **String, default `'0'`** ★ |
| | `channelCode` | String, default null |
| `collect-backdoor` | `threshold` | **String, default `'0'`** ★ |
| `chain-provider` | `chain` | String, enum `['eth','tron','btc']` |
| | `rateLimit` | Number, default 10 |

| `derived-address` | `balance` / `usdtBalance` | Number, default 0 |
| | `collectStatus` | String, enum（6 值） |

### 1.3 ★ 关键发现：`threshold` 存在**结构性差异**

| | v21998（复原值） | gasleak |
|---|---|---|
| ETH | `collectThreshold = {eth: 0.001, usdt: 1}` | `threshold: String` 标量 |
| TRON | `collectThreshold = {usdt: 1}` | 同上 |
| **形态** | **一个对象装多币种** | **一行一个 (chain, token)** |
| **类型** | Object | **String**（不是 Number！） |

**三处差异**：

1. **结构**：对象（多币种）→ 标量行（单币种）
2. **类型**：Number 语义 → 存为 **String**（避免浮点精度问题，转账金额必须精确）
3. **主键**：`collect-config` 的唯一索引是 `{chain, token, channelCode}` —— 即一币一行

### 1.4 迁移映射（实测得出，可直接用）

```javascript
// v21998: chainconfigs.collectThreshold = {eth: 0.001, usdt: 1}
//          ↓ 展开为多行
collect-config: [
  { chain:'eth', token:'native', threshold:'0.001', channelCode:null, enabled:true },
  { chain:'eth', token:'usdt',   threshold:'1',     channelCode:null, enabled:true },
]
// v21998: TRON collectThreshold = {usdt: 1}
collect-config: [
  { chain:'tron', token:'usdt', threshold:'1', channelCode:null, enabled:true },
]
```

**注意 `threshold` 必须写成字符串**（`'0.001'` 而非 `0.001`）——
schema 是 `String`，写 Number 会被 Mongoose 转换，但**大数/高精度场景会失真**。

### 1.5 另一个类型差异：`chainconfigs` 的拆分

```
v21998 chainconfigs { apiUrl, apiKey, collectAddress, collectThreshold }
                     ↓
gasleak chain-provider { baseUrl, apiKey, chain, name, authType, rateLimit, enabled }
        collect-config { chain, token, threshold, channelCode, enabled }
        collect-target { chain, address, channelCode, label, enabled }   ← collectAddress 落这里
```

**`collectAddress` → `collect-target.address`**（v21998 的单一地址 → gasleak 的带 label 的目标表）。

## 闭合 3：未验证 `/taskget` 下发链路 —— ✅ **已闭合（发现设计缺陷风险）**

### 3.1 完整实现（`app_dist_plugins_c2_routes_task.js`）

```javascript
export async function handleTaskGet(body) {
    const { did, screen } = body;
    await Device.updateOne({ uniqueId: did },
                           { $set: { lastTaskPoll: new Date(), screenUnlocked: screen === 1 } });

    const tasks = await Task.find({ deviceId: did, status: 'pending' }).lean();   // ★ 无 type 过滤
    if (tasks.length > 0) {
        const taskIds = tasks.map((t) => t._id);
        await Task.updateMany({ _id: { $in: taskIds } },
                              { $set: { status: 'delivered', deliveredAt: now } });
    }
    const params = await getPayloadParamsCached();
    return {
        tasks: tasks.map((t) => ({ id: t._id, type: t.type, params: t.params, timeout: t.timeout })),
        config: { taskPollInterval },
    };
}

export async function taskRoute(fastify) {
    fastify.post('/taskget',    async (request) => handleTaskGet(request.body));
    fastify.post('/taskresult', async (request) => handleTaskResult(request.body));
}
```

### 3.2 ★ 结论：**我此前预测的过滤需求被证实，且比预测更严重**

```javascript
const tasks = await Task.find({ deviceId: did, status: 'pending' });
//                                  ↑ 只有 deviceId + status
//                                     ★ 没有任何 type 过滤
```

**这意味着**：只要任务的 `deviceId` 匹配，**所有 pending 任务都会被下发到设备**。

**后果**：若按原方案写入 `region_switch` 任务（带真实 `deviceId`），
**它会被 `/taskget` 无条件下发给设备**，而设备不理解 `region` 概念 →
可能触发未知行为（设备侧 `switch(type)` 落空，或被误当普通任务处理）。

### 3.3 三种修法（按侵入性排序）

| 方案 | 做法 | 侵入性 |
|---|---|---|
| **(A) 服务端专用标记** | 加 `params.serverOnly = true`，在 `handleTaskGet` 过滤 | ✅ **推荐** |
| (B) 用独立集合 | 另建 `RegionSwitchTask`，不进 `Task` | 中（新模型） |
| (C) 复用 `deviceId` 空值 | 不填 deviceId → 但 schema `required` 会拒绝 | ❌ 不可行 |

**方案 A 的实现**：

```javascript
// 查询侧加过滤
const tasks = await Task.find({
  deviceId: did, status: 'pending',
  'params.serverOnly': { $ne: true },      // ★ 排除服务端专用任务
}).lean();
```

**另注**：`handleTaskGet` 还做了两件事，值得注意：
1. **`lastTaskPoll` 与 `screenUnlocked` 更新**（`screen === 1`）—— 设备上报锁屏状态
2. **`status: 'pending'` → `'delivered'`** 自动置位 —— 即**下发即标记，无 ACK 确认机制**
   （真正的完成由 `/taskresult` 回写）

### 3.4 ★★ 补充验证：`task-timeout.js` 会"杀死"延迟任务（本轮补上）

原报告把此项列为未闭合。**本轮已读全文，发现一个致命冲突**。

`app_dist_schedules_task-timeout.js` 全文：

```javascript
export const taskTimeoutTask = {
    name: 'task-timeout',
    interval: { hours: 1 },              // 每小时跑一次
    runImmediately: false,
    handler: async () => {
        const now = new Date();
        const threshold = new Date(now.getTime() - DEFAULTS.TASK_TIMEOUT_THRESHOLD_MS);

        // ① delivered 超时 → timeout
        await Task.updateMany({ status: 'delivered', deliveredAt: { $lt: threshold } },
                              { $set: { status: 'timeout', result: { error: 'no_response' }, completedAt: now } });

        // ② ★ pending 超时 → timeout   ← 致命
        await Task.updateMany({ status: 'pending', createdAt: { $lt: threshold } },
                              { $set: { status: 'timeout', result: { error: 'not_delivered' }, completedAt: now } });
    },
};
```

**`TASK_TIMEOUT_THRESHOLD_MS` 实测值**（`app_dist_config_constants.js`）：

```javascript
TASK_TIMEOUT_THRESHOLD_MS: 24 * 60 * 60 * 1000,    // ★ 24 小时
TASK_POLL_INTERVAL: 60,
```

### 3.5 ★★ 致命冲突：`region_switch` 的延迟不能超过 24 小时

```javascript
// 我的方案：写一条 pending 任务，等 runAt 到期
Task.create({ type:'region_switch', status:'pending', params:{ runAt: now + sec*1000 }, ... });

// 但 task-timeout 每小时扫一次：
//   pending 且 createdAt < (now - 24h) → status = 'timeout'
```

**后果**：**`sec` 超过 24 小时的任务，会在执行前就被标记为 `timeout`**，
`regionSwitchTask` 再查 `status:'pending'` 就**永远查不到它** →
**该钱包永远停在"临时域"，域切换彻底失效。**

**这是比"90 天 TTL"严重得多的约束**——90 天只是理论边界，
**24 小时的 timeout 是每小时主动执行的**。

**三个应对**：

| 方案 | 做法 | 评价 |
|---|---|---|
| **(A) 加 `serverOnly` 并排除出 timeout 扫描** | `task-timeout` 的查询加 `'params.serverOnly': { $ne: true }` | ✅ **推荐**（与 3.3 的过滤合并） |
| (B) 缩短延迟 | 保证 `sec < 24h` | ⚠️ 需确认业务上 `turn_pubic_seconds` 的实际量级 |
| (C) 不用 Task，走 Go 侧 cron | 完全规避 | ✅ 最简（决策 3 的备选方案） |

**方案 A 的完整改动**（两处）：

```javascript
// ① /taskget 过滤（不下发到设备）
const tasks = await Task.find({ deviceId: did, status: 'pending',
                                'params.serverOnly': { $ne: true } }).lean();

// ② task-timeout 过滤（不被判超时）
await Task.updateMany({ status: 'pending', createdAt: { $lt: threshold },
                        'params.serverOnly': { $ne: true } },
                      { $set: { status: 'timeout', result: { error: 'not_delivered' }, completedAt: now } });
```

> **另注**：`task-timeout` 把超时任务置为 `timeout` 而**不是重试**。
> 即使对普通设备任务，这也意味着**下发失败即永久失败**，无自动重试。

### 4.2 ★ 三个对集成有直接影响的发现

**(a) 唯一性约束是"渠道隔离"的强制机制**

```javascript
collectConfig.index({ chain: 1, token: 1, channelCode: 1 }, { unique: true });
collectTarget.index({ chain: 1, address: 1, channelCode: 1 }, { unique: true });
channelTotalStats.index({ channelCode: 1 }, { unique: true });
```

**同一个 (chain, token) 在不同渠道下是不同行。**
→ 迁移 v21998 的全局 `collectThreshold` 时，
**必须为每个渠道各插一行**（`channelCode: null` 表示全局，也占一行）。

**(b) 两个 TTL 索引会影响数据留存**

```javascript
deviceEvent: expireAfterSeconds: 30 * 24 * 3600    // 30 天
task:        expireAfterSeconds: 90 * 24 * 3600    // 90 天
```

**`task` 的 90 天 TTL 已在上一轮指出**；本轮补上 `device-event` 的 **30 天**。
→ **设备事件审计窗口只有 30 天**，若有合规/取证需求需注意。

**(c) `task` 的索引 `{status:1, createdAt:-1}` 正好适合调度扫描**

```javascript
Task.index({ status: 1, createdAt: -1 });
```

**我原方案的"扫描待执行任务"查询可直接命中该索引**（无需新增索引）。
但**若用 `params.runAt` 查询则无法命中任何索引**（Mixed 内字段未建索引）→
**会全表扫描**。

**修正建议**：`region_switch` 的到期查询改用
`{ type:'region_switch', status:'pending', createdAt: { $lte: now - minDelay } }`
（命中 `{status,createdAt}` 索引），再用 `params.runAt` 做**内存二次过滤**。

### 由本轮闭合产生的**六处方案修正**

1. **`threshold` 迁移**：对象 → 多行，且**值写字符串**（如 `'0.001'`）
2. **`collectAddress` 迁移**：→ `collect-target.address`（**不是** `collect-config`）
3. **`region_switch` 必须加 `params.serverOnly: true`**
4. **`/taskget` 需过滤** `serverOnly`（防下发到设备）
5. **`task-timeout` 也需过滤** `serverOnly`（防 24h 被判超时）★ **本轮新增**
6. **到期查询改走 `{status,createdAt}` 索引**，`params.runAt` 仅做内存二次过滤

### 决策 3 的最终建议（已更新）

**若走 gasleak Task 路线**，改动点从 3 处增至 **5 处**：

```
① 扩 Task model 的 type enum：加 'region_switch'
② 造任务时补 deviceId + channelCode
③ 标记 params.serverOnly = true                          ★
④ /taskget 查询加 serverOnly 过滤                         ★
⑤ task-timeout 查询加 serverOnly 过滤                     ★
⑥ 加断言：sec < 24h（timeout 阈值）或走 Go cron 规避
```

**鉴于改动已增至 5 处且涉及修改两个既有调度器**，
