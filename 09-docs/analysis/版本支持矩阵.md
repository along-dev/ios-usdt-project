## 二、coruna：15.2 – 17.3（已验证）

### 2.1 versionOffsetTable 实测

`platform_module.js:146` 起，三个 runtime 分组：

| runtime | 条目数 | minVersion 范围 |
|---|---|---|
| `LTgSl5` | 13 | 100000 (iOS 10.0) – **170300 (iOS 17.3)** |
| `PSNMWj` | 19 | 100000 – 170000 (iOS 17.0) |
| `RoAZdq` | 5 | 100000 – 150000 (iOS 15.0) |

### 2.2 关键修正：`GFx77t` 是下界，不是上界

```js
// platform_module.js:534-540
const t = versionOffsetTable[platformState.runtime].reverse();
let n = Object.assign(platformState.versionFlags, t[0]);
for (const r of t.slice(1)) {
  if (r.GFx77t > platformState.iOSVersion) break;   // ★ 下界比较
  n = Object.assign(n, r);
}
```

注释明确写 `/* minVersion */GFx77t`。逻辑是「从低到高累积，遇到 minVersion 超过
当前版本的条目就停」——**表内最高条目 170300 之后没有任何条目**，
意味着 17.3 及以上会**继续复用 17.3 的标志集**，且**没有任何门禁拒绝高版本**。

`iOSVersion` 解析（`:968`）用 `iPhone OS (\d+)_(\d+)(?:_(\d+))?`，
任意版本都能解析，**无版本校验**。

### 2.3 为何上界仍取 17.3 而非「无上限」

17.3+ 复用 17.3 条目**是表的默认行为，不等于该行为经过验证**。
`SUPPORTED_IOS.md` 也明确提示「iOS 17.3+ may require additional Stage modules
not bundled here」。

因此路由取**保守值 17.3**：17.4 及以上走 `unsupported`，
避免把未验证的路径当成可用能力下发。

> 若后续真机验证 17.4/17.5 可行，只需改 `CHAINS.coruna.max` 一处。

### 2.4 机型覆盖：不限机型

**coruna 全库无任何机型字符串**（`grep iPhone\d|device_model|chipset` 零命中）。
它按 **runtime + iOS 版本**选择偏移，与机型无关。

即：iPhone 11 到 iPhone 17，只要版本落在 15.2–17.3，走的是同一套偏移逻辑。

## 三、darksword：18.4 – 18.6.2（分级）

### 3.1 linkedit_to_device 实测

`rce_module.js:147125` 起，**6 个版本键 × 23 机型**：

| 版本键 | build | 机型数 |
|---|---|---|
| `18,4` | 22E240 | 23 |
| `18,4,1` | 22E252 | 23 |
| `18,5` | 22F76 | 23 |
| `18,6` | 22G86 | 23 |
| `18,6,1` | 22G90 | 23 |
| `18,6,2` | 22G100 | 23 |

机型列表（23 个，**无 iPad/iPod**）：
```
iPhone11,8  iPhone12,1  iPhone12,8  iPhone13,1  iPhone13,4
iPhone14,2  iPhone14,3  iPhone14,4  iPhone14,5  iPhone14,6
iPhone14,7  iPhone14,8  iPhone15,2  iPhone15,3  iPhone15,4
iPhone15,5  iPhone16,1  iPhone16,2  iPhone17,1  iPhone17,2
iPhone17,3  iPhone17,4  iPhone17,5
```

`pthread_create_auth_stubs_offset` 与 `pthread_create_offset` 同样是这 6 个版本键，
**前段覆盖到 18.6.2**。

### 3.2 精确失败点：为什么 18.5+ 只到前段

`sbx0_main_18.4.js:6608`：

```js
var MessageName = sbx0_offsets[device_model];
```

而 `sbx0_offsets` 实测**只有 52 个键**：

```
26 个机型 × 仅 2 个 build（22E240, 22E252）
```

18.5 的 `22F76`、18.6 的 `22G86`、18.6.1 的 `22G90`、18.6.2 的 `22G100`
**都不在表内** → `MessageName = undefined` → Mach 消息构造失败 → 沙箱逃逸挂。

代码里甚至保留了诊断（`:6594-6606`）：

```js
var __keys = Object.keys(sbx0_offsets).length;
var __hit = (sbx0_offsets && sbx0_offsets[device_model]) ? 'YES' : 'NO';
print('DBG sbx0 device_model=' + device_model + ' offsets_keys=' + __keys + ' lookup=' + __hit);
if (__hit === 'NO') {
  var __sample = Object.keys(sbx0_offsets).slice(0, 3).join(',');
  print('DBG sbx0 offsets sample keys: ' + __sample);
}
```

说明**目标方已知这个限制**。

### 3.3 分级结论

| 版本 | 前段（JSC RCE → PAC → fcall） | sbx0 沙箱逃逸 | 后段（内核/注入/窃取） |
|---|---|---|---|
| 18.4 / 18.4.1 | ✅ | ✅ | ✅ |
| 18.5 – 18.6.2 | ✅ | ❌ **缺 build 偏移** | ❌ |

路由对 18.5+ 返回 `partial: true` + `build` 字段，供上层决策。

## 四、空洞区：17.4 – 18.3.x

两条链都不覆盖：

- coruna：表内最高 170300，且本方案保守截断在 17.3
- darksword：最低版本键 `18,4`

**路由行为**：`unsupported: true`，`entries: []`，**不回退旧链**。

> 这是**刻意设计**：静默回退到 coruna 会让 18.x 设备加载完全不匹配的偏移，
> 大概率崩溃或长时间挂起，比直接拒绝更糟。

---

## 五、机型支持总结

| 链 | 机型依赖 | 说明 |
|---|---|---|
| coruna | **无** | 按版本+runtime 选择，全 iPhone 通用 |
| darksword | **有** | 按 `机型_build` 查表，23 个 iPhone 型号 |

**两链均不支持 iPad / iPod**：

- coruna 无机型表，但依赖的 Safari/WebKit 行为与偏移表按 iPhone 校准
- darksword 机型列表**明确无 iPad/iPod 条目**

路由层对非 iPhone UA（含 iPad、Mac）一律 `unsupported`。

## 七、如需扩展覆盖

| 目标 | 需要做的事 |
|---|---|
| 放开 17.4+ 到 coruna | 改 `CHAIN.coruna.max`，并真机验证 17.3 条目在 17.4/17.5 是否仍适用 |
| 补 18.5–18.6.2 全链 | 需要 `sbx0_offsets` 补 `22F76`/`22G86`/`22G90`/`22G100` 四个 build 的偏移（**需从对应固件提取**，非改配置可得） |
| 支持 iPad | 两条链都缺 iPad 偏移，需另行获取 |
| 支持 17.4–18.3.x | 两链均无，需新链 |

> 唯一「改配置即可」的是第一项；其余都依赖**新的偏移数据**，
> 不是路由层能解决的。
