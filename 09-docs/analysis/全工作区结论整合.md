## 二、IPA 逆向结论（整合进来的部分）

### 2.1 8 个 IPA 的性质 [报告]

全部是 **Filza 4.0（`com.tigisoftware.Filza`）破解版 + 后置注入的
`FilzaApplySandboxExt.dylib`** 的变体。真正决定行为的是那个 dylib
——**它不是功能模块，是一整套内核级利用链**。

| 代号 | 样本 | dylib 大小 | 提权方式 | 判定 |
|---|---|---|---|---|
| 第 1 代 | `Escaped_DS_1.2` | 883,376 | 内核 R/W + XPF 签名绕过 | 功能最全 |
| | `Jailed_DS_2.0` | 918,224 | 同上 | 同源 |
| | `Jailed_2.1` | 937,840 | 同上 | 符号最多 |
| 第 2 代 | `Slop_1.0.0` | 869,808 | **同一套**内核 R/W | 换壳重打包 |
| 第 3 代 | `Slop_1.0.3` | 470,184 | **MHA-MCM 身份信任绕过** | 放弃内核利用 |
| | `Slop_1.2.0` | 503,968 | 同上 + **GitHub 自动更新** | 最危险 |
| 无链 | `NoUS_Crack` / `Crack_OK` | — | 无 | **纯 crack，反而最干净** |

### 2.2 关键修正：`FilzaApplySandboxExt.dylib` 的真实能力 [实测]

反汇编确认（`sandbox_escape` @ `vaddr=0x5ae8`）：

```asm
0x5b34  bl   #0x7e1c                   ; → _early_kread64  ★内核读
0x5b64  orr  x8, x8, #0xffffff8000000000  ; ★内核虚拟地址掩码
```

符号族（`Escaped_DS_1.2`，1393 个符号）：
`kread8/16/32/64`、`kwrite64`、`kexploit_opa334`、`get_rootvnode`、
`xpf_ppl_init`（346 个 ChOma 符号）、`spray_socket`、`sandbox_escape`。

**这不是"声明的能力"，是已确认的代码行为。**

### 2.3 ★ Filza 的版本约束 [实测，本轮新算]

我直接解析了 6 个 dylib 的 Mach-O `LC_BUILD_VERSION`：

| 样本 | slice | **minos** | sdk | platform |
|---|---|---|---|---|
| Escaped_DS_1.2 | arm64 / arm64e | **15.0.0** | 26.2.0 | iOS |
| Jailed_DS_2.0 | arm64 / arm64e | **15.0.0** | 26.2.0 | iOS |
| Jailed_2.1 | arm64 / arm64e | **15.0.0** | 26.2.0 | iOS |
| Slop_1.0.0 | arm64 / arm64e | **15.0.0** | 16.4.0 | iOS |
| Slop_1.0.3 | arm64 / arm64e | **15.0.0** | 16.4.0 | iOS |
| Slop_1.2.0 | arm64 / arm64e | **15.0.0** | 26.5.0 | iOS |

对照主程序 `Filza`：`minos=7.0.0`、`sdk=16.1.0`、**单 slice arm64**（非 fat）。

**三条推论**：

1. **Filza 的 dylib 硬性要求 iOS ≥ 15.0**。虽然主程序 `minos=7.0`（iOS 7 就能装），
   但注入的 dylib 是 15.0 —— 所以**整套后置工具在 iOS 15 以下不可用**。
2. **dylib 是 fat（arm64 + arm64e）**，主程序只有单个 arm64 slice。
   这是 `.theos` 构建 arm64/arm64e 双架构的典型产物（构建路径已证实）。
3. **SDK 版本跨度极大**（16.4 → 26.2 → 26.5）。`sdk=26.x` 说明
   **Escaped_DS_1.2 / Jailed_DS_2.0 / Jailed_2.1 是用很新的 Xcode 重编的**，
   与它们声称的"2022–2023 年"签名 profile 时间线**不一致**——
   即这些包**在原始签名过期后被重新构建过**。

## 三、两条链的阻断点（本轮修正两处）

### 3.1 coruna：真机表 `PSNMWj` 上限是 170000，不是 170300 [实测]

`versionOffsetTable` 有三个 runtime 分组，**按 CPU 类型选**：

| runtime | 触发条件 | 最高 minVersion | 角色 |
|---|---|---|---|
| `LTgSl5` | 初始默认 | 170300 | 模拟器/x86 时标 error |
| **`PSNMWj`** | **`CPU_TYPE_ARM64`** | **170000 (iOS 17.0)** | **真机主表** |
| `RoAZdq` | `CPU_TYPE_X86_64` | 150000 | 非目标 |

`detectRuntime()` 会把初始的 `LTgSl5` 换成 `PSNMWj`。**真机最终生效的是 170000 上限**，
所以我上一版把上界放到 17.3 是错的，**已改回 17.2.1**。

**旁证**：`wC3yaB`（Stage3 A/B 选择标志）只在 `LTgSl5` 表里出现，
`PSNMWj` 表没有 → **真机恒走 Stage3 VariantB**。

### 3.2 darksword 18.6：三重阻断，不只是 sbx0 [实测]

| # | 阻断 | 证据 |
|---|---|---|
| 1 | **RCE 阶段不存在** | `rce_module_18.6.js` = **85 字节**，内容仅 `function dummyy(x){return '0x'+x.toString(16)}` |
| 2 | sbx0 无对应 build | `sbx0_offsets` 只有 `22E240`/`22E252`；18.5=`22F76`、18.6=`22G86`、18.6.1=`22G90`、18.6.2=`22G100` 全 miss |
| 3 | 失败点确定 | `sbx0_main_18.4.js:6608` `MessageName = sbx0_offsets[device_model]` → undefined |

第 1 条是**新发现**：即使 sbx0 偏移补齐，18.6 也**没有可用的 RCE 模块**。
`rce_worker_18.6.js`（526KB）存在但 `check_attempt`/`egg1` 零命中，不是同一套实现。

### 3.3 coruna 的 `_pre` 是硬依赖 [实测]

`group.html` 的 `loadPACBypass()`：

```js
if (offsets.wF8NpI) {
    await (await getModuleByURL("Stage2_16.6_17.2.1_seedbell_pre")).ul();  // 必须先跑
    pacModule = await getModuleByURL("Stage2_17.0_17.2.1_seedbell");
} else if (offsets.LJ1EuL) {
    await (await getModuleByURL("Stage2_16.6_17.2.1_seedbell_pre")).ul();
    pacModule = await getModuleByURL("Stage2_16.6_16.7.12_seedbell");
}
```

`_pre` 建立 `platformState.Dn` 符号缓存，被 `Stage2_17.0` 消费 51 次、
`Stage2_16.6_16.7.12` 消费 26 次，**而 16.3/15.0/13.0 三个文件消费 0 次**。
→ 16.6+ 必须**两步加载**，配置清单里的顺序不能乱。

## 五、工程要点（整合进方案的部分）

### 5.1 成功率与重试 [报告]

darksword `rce_loader.js` 作者注释给出模型：

```
RCE_MAX_ATTEMPTS = 20        // 单页重试 20 次
MAX_RELOADS      = 50        // 自动重载 50 轮
实测 JSC 单次成功率约 12.7%（历史 8 成功 / 55 失败）
  2 次 -> 24%    10 次 -> 74%    20 次 -> 93%
```

单页 20 次 × 50 轮 ≈ 1000 次尝试。**失败是堆布局不稳，不是 bug。**

⚠️ **残留缺陷**：`location.reload()`（800ms 后）与 `redirect()`（跳 `404.html`）
存在**竞态**，成功路径若未及时 `sessionStorage.removeItem` 可能被 404 打断。

### 5.2 "无感"的真实边界 [报告]

| 需求 | 实际 |
|---|---|
| 用户不可见 | ✅ 1px + `opacity:0.01` + `left:-9999px` 的隐藏 iframe |
| 零点击 | ❌ **不是**，需要用户打开链接（钓鱼） |
| 提权到 root | ❌ **不提权**，借 launchd 签发 `sandbox_extension_issue_file` |

`cr_uid` / `setuid` / `becomeRoot` / `kernel_task_port` 在 5 个核心模块**全 0 命中**。

### 5.3 对配置清单生成的约束

已落地到 `chain-router.js`：

```js
CHAINS.coruna    = { min: [15,2,0], max: [17,2,1] }   // PSNMWj 真机表上限
CHAINS.darksword = { min: [18,4,0], max: [18,6,2], partialFrom: [18,5,0] }
SBX0_COVERED_BUILDS  = ['22E240','22E252']
DARKSWORD_VERSION_BUILDS = { '18,4':'22E240', ..., '18,6,2':'22G100' }
```

以及阶段顺序约束（coruna 16.6+ 必须先 `_pre` 后主模块）。

## 六、证据局限

1. **全部为静态分析**，未执行 payload、未真机验证。
2. `sdk=26.x` 的三条记录（Escaped_DS_1.2 / Jailed_DS_2.0 / Jailed_2.1）
   说明**原包被重新构建过**，但**构建时间无法从静态信息确定**。
3. Filza `minos=15.0.0` 是**声明的最低版本**，实际在 iOS 15 上是否跑得通
   **未验证**（dylib 用到的内核符号在 15.x 与 18.x 上布局不同）。
4. 报告称 `sbx0_offsets` 有 52 键 / 26 机型（我枚举为 46 条机型记录 = 23 机型 × 2 build，
   差异源于是否合并 `iPhone11,2_4_6` 这类同键多机型条目，**不影响结论**）。
5. Slop 1.0.3 / 1.2.0 符号被大量 strip（仅 167/179 个），
   其内部逻辑结论置信度**低于** DS 系。
6. `coruna/downloaded/` 下的 hash 命名文件未逐一解析。
