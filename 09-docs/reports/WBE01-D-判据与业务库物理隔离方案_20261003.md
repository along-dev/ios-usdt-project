## §0 · 一句话

**隔离的最小单元不是"库"，是"服务 ＋ 库"这一对。**
被测者是**独立进程**（Go 服务用自己的连接写库），它写哪个库由**它自己的 `config.yaml`** 决定
⇒ **只把判据脚本的 `DB` 变量改成测试库，等于没隔离** —— 脚本打的服务照样写业务库。
★ **这是本方案的第一结论**；不先钉死它，就会做出一个"看起来隔离、实则没隔离"的东西。

---

## §1 · 为什么必须做（第一手依据，非推演）

| 事实 | 出处 |
|---|---|
| **主回归集里 4 个脚本会 `DELETE`/`UPDATE` 业务表 `bill`/`settlement`/`token`/`wallet`** | WBE01-C §2 逐行清单（全仓搜索确认，无第二种来源） |
| **已经因此出过一次事故**：一次迁移依赖的 `bill` 行被删 ⇒ 存列派生值当场陈旧、不变量由绿转红 | WBE01-C §1（时间线 ＋ 两次数值） |
| **WBE01-C(甲) 只解决了"跨脚本互删／整表删"**，**没有**解决"跑一个脚本就改业务库"这一根本形态 | WBE01-C §3 结论 |
| **护栏（WBE01-C 同批）能<发现>，但不能<阻止>** —— 它按设计只在跑完后报警 | `run_regression_v2.py` 新增 `db_snapshot/db_compare` |

⇒ 结论：**只要判据仍连业务库，(甲) 之后仍需"每次回归都改一次业务表、再由护栏报红"** —— 这是**靠人守规矩**，不是**由结构保证**。
（与 X3 那份 `BIND_HOST` 加固同型：**能力先就位，默认不变**。）

## §2 · ★ 决定性约束：隔离必须"服务 ＋ 库"成对

**证据链（逐条带 `file:line` / 机制）**：

1. 判据脚本直接用 mysql 客户端连库：`DB = 'qk_e2e'`（`verify_money_path.py:41` 一带，5 个脚本同形）
   —— **这一半**改个变量就能切。
2. 但脚本还**打服务**：`verify_money_path.py` 的 `API`（8888 族）、`e2e_test_api.py:33` 的 `API='http://127.0.0.1:18888'`
   —— 而 **服务写哪个库，由它的 `config.yaml` 的 `mysql.db-name` 决定**（运行实例在 `_i2c1_ws/config.yaml`）。
3. ⇒ **脚本切到测试库、服务仍写业务库** ⇒ 隔离**只做了一半**：读的是测试库、写的是业务库 ⇒
   **比不隔离更坏**（读写分裂，出现"脚本看不见自己刚写的东西"这类**最难查**的假象）。
★ **所以：(乙) 的落地物 = 「第二服务实例 ＋ 第二库」，且两者必须切到同一套。**

## §3 · 候选

| 候选 | 内容 | 优 | 劣 | 评价 |
|---|---|---|---|---|
| **(丁) 只切脚本的 DB 变量** | 脚本 `DB` 改成测试库 | 一行 | ⛔ **半隔离、读写分裂**（§2） | **排除** |
| **(乙-1) 第二实例 ＋ 第二库 ★推荐** | 起 Go 实例 B（独立端口 ＋ 独立 config，`mysql.db-name = qk_e2e_test`）＋ 判据的 `DB` 指 `qk_e2e_test` | **物理隔离**：业务库**不可能**被碰到；"行数一致"变成**结构性成立**；与 **卡B 的 8899 隔离实例同一套基建** | 需播种器（起库/建表/种夹具）；需管两套配置；占端口与磁盘 | ★ **推荐为方向** |
| **(乙-2) 跑前快照/跑后还原** | 跑回归前把四张夹具表 dump，跑完还原 | 改动小、不需要第二实例 | ⚠️ **窗口内业务库仍是脏的**（并发会话会读到）；且"还原"本身是写业务库 | **补丁式**，可作 (乙-1) 落地前的过渡 |
| **(乙-3) (乙-1) ＋ 复用已有护栏** | (乙-1) 之上，把护栏**指向业务库**（证明"一个字都没碰"） | 护栏从"发现伤害"变成"**证明隔离有效**" | — | **与 (乙-1) 同批** |

### 3.1 ★ 为什么 **不** 用"只切库"（要写进方案，避免白做一轮）
同 WBE01-C 里排除"(丙) 事务回滚"是同一条纪律：**把"看起来最省事的方案"主动排掉**。
本条的证据是 §2 的第 2、3 点 —— **被测者是独立进程**。

## §4 · (乙-1) 的落地形态（枚举改动点，**均为"默认不变"的可注入式**）

> 一律沿用本项目已被验证过的形态：**环境变量可注入 ＋ 默认值 = 现状**（同 E-03 的 `DSH_VERIFY_TMP`、同 `BIND_HOST` 加固）。

| # | 改动点 | 形态 |
|---|---|---|
| 1 | **5 个判据脚本的 `DB`** | `DB = os.environ.get("DSH_DB", "qk_e2e")` —— **默认仍是 `qk_e2e`**，不设环境变量则行为逐字不变 |
| 2 | **判据脚本的 `API`** | 同理 `os.environ.get("DSH_API", "<现默认>")`，默认不变 |
| 3 | **第二实例（"实例 B"）** | 独立端口（与卡B 的 8899 **合并规划**，避免占两个端口）＋ **独立 config 副本**（`mysql.db-name = qk_e2e_test`） |
| 4 | **播种器** | 从**基线**建 `qk_e2e_test`：建库 → 用实例 B 的 AutoMigrate 建表 → **只种判据需要的夹具行**（`wallet(1,2)` / `settlement` / `token` / `machine` / `agent` / `packet` / `custom`）。★ **不种 `bill`**（判据自己会种） |
| 5 | **运行入口** | 一条命令：起实例 B → 播种 → 跑回归（带 `DSH_DB`/`DSH_API`）→ 停实例 B |
| 6 | **护栏** | **指向业务库**：跑完断言业务库四张表**逐字节未变** ⇒ 把"隔离有效"变成**可机检的绿** |
| 7 | **响亮提示** | 脚本启动时打印**它连的是哪个库 / 哪个 API**（防"我以为在测测试库"） |

### 4.1 一条**必须先验证**的前提
实例 B 必须**能只靠 config 指向另一个库** —— 即 Go 侧读 `mysql.db-name` 而不是硬编码库名。
★ **本方案不假设它成立**：落地第一步是 `grep` Go 侧 `db-name` 的读取点并实测（与"P-5 用真实路径实测，不猜"同法）。

## §5 · 与卡 B 的基建复用（避免两套隔离实例）

| 项 | 卡 B（develop 后门） | 本卡 (乙-1) |
|---|---|---|
| 需要的第二实例 | ✅ 8899（`Env=develop`） | ✅ 实例 B（`db-name=qk_e2e_test`） |
| 可合并 | ★ **是** —— 同一台实例可同时满足"独立端口 ＋ 独立 config（develop ＋ 测试库）"，**但**卡B 需要 `develop`、本卡需要 `production` 语义（`Env` 影响 casbin 旁路）⇒ **两个 config 副本、同一个端口池规划** | |

★ **建议**：**统一规划一个"隔离实例端口段"**（如 8899/8900），两卡各用一份 config 副本，**避免将来第三、第四个需求又各占一个端口**。

## §6 · 风险与边界

| 项 | 说明 |
|---|---|
| **最坏失败模式** | **半隔离（读写分裂）**（§2）⇒ 所以 §4-6 的护栏**必须指向业务库**、§4-7 的响亮提示**必须有** |
| **播种漂移** | 测试库的 schema 若与业务库不同步 ⇒ 判据"通过"但**与真实环境无关**。⇒ 播种器**必须**用实例 B 的 AutoMigrate（同源），并在启动时**核一次关键列存在性** |
| **磁盘/端口** | 多一个库 ＋ 一个实例；端口用统一端口段规划 |
| **不涉及** | 本方案**不动** `07-db/**` 的业务迁移、不动 `contracts.md`、不动任何生产配置 |
| **提交** | 单独一批；**不得与 WBE01-C 或其他卡混批** |
| **本件不改历史提交** | ✓ |
