## §F · ★★ 更正：我把"漏记"错报成了"双计"（**在我自己的报告里已发出，此处更正**）

### F.1 更正内容

| 项 | 我在上一封报告里说的（**错**） | **实测后的更正** |
|---|---|---|
| 风险 | "进程在**「链上转账已成功」与「`Status` 置 1」之间**重启 ⇒ 该 bill 仍 `status=0`、会被重跑 ⇒ **再累加一次（双计）**" | **该路径不成立**（理由见 F.2）。真正的窗口是 **漏记**：中断发生在 **`Status=1` 已 Save** 与 **`usdt_num` 累加** 之间 ⇒ 该 bill **永久不再被选中**（查询条件是 `status=0`）⇒ **客户/代理利润少记一次，且不可自愈** |

### F.2 为什么"双计"不成立（两步各自排除）

1. **重启路径不成立**：查询是 `Where("status=0 and bill.batch_id=? and transfer_hash!=?")`（`scan.go:298`），而写入顺序是**先** `billOrder.Status = 1; Save(...)`（`:320-321`）**再**累加（`:329`）。
   - 若中断在**置 1 之前** ⇒ `status` 仍 0 ⇒ 重跑会**置 1 并累加** ⇒ 结果**恰好一次**（**正确**，不是双计）；
   - 若中断在**置 1 之后、累加之前** ⇒ `status` 已是 1 ⇒ **不再被任何一次扫描选中** ⇒ **累加永不发生** ⇒ **漏记**。
2. **并发路径不成立**：`batchId := time.Now().UnixMilli()`（`scan.go:46`）——**每次 `Sk()` 各生成一个毫秒级批次号**；核验查询带 `bill.batch_id = ?` ⇒ 两个并发的 `Sk()` 定时器扫的是**不同批次** ⇒ **不重叠**。

⇒ **结论：在我能枚举的路径里，`custom.usdt_num` 的双计<不可达>；可达的是漏记。**

### F.3 我的错因（**与 `E-318` 同族，务必点明**）

我在上一封里写"进程在转账成功与置 1 之间重启 ⇒ 会被重跑"时，**依据是"查询按 status=0 过滤"这一条**，
却**没有同时核"置 1 与累加语句之间的<顺序>"** —— 而**顺序恰恰决定了窗口的方向**（先置 1 ⇒ 得漏记；先累加 ⇒ 才得双计）。
⇒ 与 `E-318` 同形：**用一个局部读数（查询条件）推出了整条因果链的结论**，而链条的另半段（语句顺序）我没读。

★ **机械落点（针对本类）**：**断言"存在竞态/时序窗口"之前，必须把该窗口<两侧的语句>都读出来并写明先后**；
仅凭"存在某个过滤条件"不得推断窗口方向。

### F.4 ★ 对调度裁定的影响（**重要，请不要误撤**）

**你裁定「加幂等守卫」——该裁定<依然正确>，只是<理由要换>**：
- 原理由（双计）**不成立**；
- **真理由（两条，都成立）**：① **防漏记** —— 把"置 1"与"累加"放进**同一事务**，二者要么都成、要么都不成；② **防将来** —— 若日后有人把并发引入（例如把 `batchId` 改成按批次共享），**条件更新（compare-and-set）** 是唯一不依赖调用方纪律的守卫。
- ⇒ **§I 的守卫设计不变**，仅把"为什么"改写为 F.2/F.4 的版本。**若你认为应据此重裁，我照办**；我不自行改你的裁定。

## §G · 新发现：**API 路径落下的 bill 永远不会被累加**（影响 §C 的口径结论）

**两条 bill 创建路径的 `status` 取值相反**：

| 路径 | 创建处 | 创建时 `Status` | 会被 `scan.go:298` 的 `status=0` 查询选中吗 |
|---|---|---|---|
| **A · 扫描/兜底（`Sk`）** | `blockchain/scan.go:106 / 124 / 142 / 230` | **`0`** | ✅ 会 ⇒ 核验成功后被累加 |
| **B · API（gasleak 回传）** | `service/app/collect_result.go:214`（`mkBill`） | **`1`** | ❌ **不会** ⇒ **永远不累加** |

且全仓 `custom.usdt_num` 的**唯一累加点**就是 `scan.go:329`（`agent` 同构于 `:335`）——已按"两种模式 × 不限目录"复搜确认。

**⇒ 后果（口径层）**：`custom.usdt_num` **只包含 A 路径**的已核验金额；
`SUM(bill.usdt_num WHERE role=2)` 则**同时包含 A 与 B**。
⇒ **R1 §C.1 里"二者是同一笔钱的两个时刻"这个说法<不完备>**，应改为：
`custom.usdt_num` ⊆ `SUM(bill role=2)`，**差额 = B 路径的全部金额**（不被累加的那部分）。

**★ 这条我标为"待判"而非"缺陷"**：B 路径是 gasleak 已链上确认才回传，**可能是有意不再复核**；
但若是这样，**客户利润口径就必须明确"以哪个为准"**，否则两个数会对不上。**请裁：**
- **(甲)** B 路径也应累加 ⇒ 需在 B 路径补累加（且与 A 共用同一幂等守卫）；
- **(乙)** 有意不累加 ⇒ **对外只呈现 `SUM(bill role=2)`，停用 `custom.usdt_num` 作展示口径**（注意：这与 R1 撤回的"停用"不同——那是基于"死字段"的错前提，本条是基于"两条路径口径不一致"的实测）；
- **(丙)** 维持现状 + 在文档里明写差额来源。

★ **在裁定前，§E-3 与 §E 的 `GetIndexInfo` 口径**应**暂以 `SUM(bill role=2)` 为准**（它覆盖两条路径），并在件里标注该选择是可翻转的。

## §I · 幂等守卫设计（落裁定 2；真理由见 §F.4）

### I.1 现状（`blockchain/scan.go:318-336` 骨架）

```go
var billOrder app.Bill
global.GVA_DB.Where("id=?", transInfoList[i].ID).First(&billOrder)
if billOrder.ID > 0 {
    billOrder.Status = 1
    global.GVA_DB.Save(&billOrder)                  // (a) 独立事务/独立语句
    switch billOrder.Role {
    case 2: … global.GVA_DB.Model(&custom).Update("usdt_num", gorm.Expr("usdt_num + ?", …))  // (b) 与 (a) 不同事务
    case 3: …
    }
}
```
**(a) 与 (b) 之间存在漏记窗口**（§F.2）。

### I.2 建议形态（**条件更新 + 单事务**）

```go
err := global.GVA_DB.Transaction(func(tx *gorm.DB) error {
    var b app.Bill
    if err := tx.Where("id = ?", id).First(&b).Error; err != nil { return err }

    // ★ 条件更新：只有"前值仍为 0"的执行者才获得处理权（compare-and-set）
    res := tx.Model(&app.Bill{}).Where("id = ? AND status = 0", b.ID).Update("status", 1)
    if res.Error != nil { return res.Error }
    if res.RowsAffected != 1 { return nil }        // 已被处理过（或并发者抢先）⇒ 幂等跳过

    // 同一事务内累加 ⇒ 与置 1 同生共死，消除漏记窗口
    switch b.Role {
    case 2:
        return tx.Model(&app.Custom{}).Where("user_id = ?", userId).
            Update("usdt_num", gorm.Expr("usdt_num + ?", b.UsdtNum)).Error
    case 3:
        return tx.Model(&app.Agent{}).Where("user_id = ?", userId).
            Update("usdt_num", gorm.Expr("usdt_num + ?", b.UsdtNum)).Error
    }
    return nil
})
```

★ **语义变化须写明**：现状是"**先**置 1 **再**累加"（漏记窗口）；改后是"**条件置 1 ＋ 同事务累加**"（原子）。
★ 本设计**只给形态，不落码**（卡未放行）。

### I.3 反向断言设计（调度指定的"模拟置 1 前中断再重跑"）

| # | 步骤 | 期望 |
|---|---|---|
| 1 | 取一条 `role=2`、`status=0` 的 bill，记 `custom.usdt_num` 前值 `V0` | — |
| 2 | **正常跑一次**核验流程（`suc=true`） | `usdt_num = V0 + bill.UsdtNum`，且 `bill.status = 1` |
| 3 | **再跑一次**（同一 batch） | `usdt_num` **不再变化**（`status=1` ⇒ 查询不再选中） |
| 4 | **模拟中断**：手工把该 bill 的 `status` 置回 `0`（等价于"置 1 前被打断"），记 `V1` | — |
| 5 | 跑一次核验 | **`usdt_num` 恰好再 +1 次**（`V1 + bill.UsdtNum`），**不是 +2**；且 `status` 回到 1 |
| 6 | 再跑第三次 | `usdt_num` 不变 |
| ★ 负控 | 把 `status` 置 1 **但不动** `usdt_num`（模拟"置 1 后中断"）⇒ 跑若干次 | `usdt_num` **永不变**（证明漏记窗口**不会**自发补记 —— 这正是本守卫要消除的形态；修好后此负控应改为"由同一事务保证不会出现这种中间态"） |
