## §A · 证伪与我的错因（**自己复现，不采信转述**）

### A.1 证伪成立（我已独立复现）

本信道 A 侧 指出 `blockchain/scan.go:322-331`：收割核验成功（`suc`）且 `billOrder.Role == 2` 时，
```go
global.GVA_DB.Model(&custom).Update("usdt_num", gorm.Expr("usdt_num + ?", billOrder.UsdtNum))
```
**我已逐字复现该行**（`scan.go:329`），并已按它给的两模式法**全仓**重搜：

```
$ grep -rn '"usdt_num"' --include=*.go .        # snake_case（覆盖 gorm 字符串列名写法）
  ./blockchain/scan.go:329   Update("usdt_num", gorm.Expr("usdt_num + ?", billOrder.UsdtNum))   ← 客户
  ./blockchain/scan.go:335   Update("usdt_num", gorm.Expr("usdt_num + ?", billOrder.UsdtNum))   ← 代理
  (+ 若干 json tag，非写入)
$ grep -rn "UsdtNum" --include=*.go .           # CamelCase（覆盖结构体字段写法）
  ./service/system/sys_user.go:44    custom.UsdtNum = "0"      ← 初始化
  ./service/system/sys_user.go:74    agent.UsdtNum  = "0"      ← 初始化
  ./blockchain/scan.go:329 / :335                              ← 累加（同上）
```

⇒ **`custom.usdt_num` 的写入点共 2 处**：注册时置 `"0"`，**收割成功时按 `user_id` 累加**。
**v1 §③「死字段 / 此后从不更新」为假。** `agent.usdt_num` 同构（`scan.go:335`）。

### A.2 ★ 我的错因（**根因，不是"没看见"**）

我当时的检索命令是：
```bash
grep -rn "UsdtNum" --include=*.go service/ api/        # ← ⚠️ 只搜了 service/ 与 api/
```
**而写入点在 `blockchain/`。**
但我把结论写成 **"全仓只有注册时一处写入"** ⇒ **量尺的<范围>与结论的<范围>不一致**。

★ 注意：**即使只搜 `UsdtNum` 一个模式，只要不限定目录，也会命中 `scan.go:329`**（该行含 `billOrder.UsdtNum`）。
⇒ **真正的根因不是"少搜了一种模式"，而是"缩窄了搜索范围却扩大了结论范围"**。两种模式法是**第二道**保险，**第一道**是"量尺范围必须等于结论范围"。

### A.3 机械落点（我自己的，已生效）

1. **凡写「全仓／无引用／从不 X」类结论 ⇒ 检索命令<不得带任何目录参数>**；若确需限定范围，则结论必须写成**同一范围**（如"在 `service/`、`api/` 内未见写入"），⛔ 不得升级为"全仓"。
2. 声称「某字段无写入／某表无引用」时，**两种模式各跑一次**（`"snake_case"` 列名 + `CamelCase` 字段名），因 gorm 允许字符串列名写法。
3. **逐条判读命中**，不只看计数。

## §B · 重做 §三·③（`custom.usdt_num` 的定性）

### B.1 修正后的定性

| 项 | v1 §③（**作废**） | **修订版（本件）** |
|---|---|---|
| `custom.usdt_num` | "死字段，从不更新" | **活字段；写入点 2 处**：注册置 `"0"`（`sys_user.go:44`）+ **收割成功时按 `user_id` 累加**（`scan.go:329`，`bill.Role==2`） |
| 是否按客户分户 | （未论） | ✅ **天然分户**：累加用 `Where("user_id=?", transInfoList[i].UserId)`，而 `UserId` 来自 `settlement.user_id`（join 到 `bill.settlement_id`）⇒ **每个客户各自的 settlement 行 → 各自的 user_id** |
| 结论 | "应停用，改用 bill 派生" | **不停用**（见 §C） |

★ **与多租户的关系（重要）**：该写入路径**本来就是按 `user_id` 定位客户的** ⇒ 多租户下**它天然正确**，
**前提是分账端能把 `bill.settlement_id` 选对客户** —— 而这正是 v1 §5.1（`customSettlementId` 的 `Limit(1)`）要修的地方。
**⇒ 两处必须成对修：分账端选出正确客户 ⇒ 累加端自然跟着正确。只修一处会出现"记到对的行、累加到错的行"或反之。**

## §C · 重做 §四·4.4（客户利润的权威口径）

### C.1 两个口径的**关系**（回答调度问的"是否重复计入 / 哪一个是真值"）

| 口径 | 载体 | 语义 | 何时写 |
|---|---|---|---|
| `SUM(bill.usdt_num) WHERE role=2` | `bill` | **已分账**的客户应收 | 归集落账时（`collect_result.go:274-281`，`mkBill`） |
| `custom.usdt_num` | `custom` | 其中**已收割核验成功**的累计 | `scan.go:329`，仅当 `bill.Role==2` **且** 该 bill 由 `status=0` → `1` **且** 链上核验 `suc=true` |

**⇒ 二者不是"两个互相矛盾的源"，而是同一笔钱的<两个时刻>**：
`bill.role=2` = 应收（含未收割）；`custom.usdt_num` = 已落袋（已核验）。

### C.2 **重复计入**：正常路径不重复，但**有一个窄窗口**

- **查询侧有前置过滤**：`scan.go:296` → `Where("status=0 and bill.batch_id=? and transfer_hash!=?")` ⇒ **只取未处理过的 bill**；
- **且写入顺序是"先置 1、再累加"**（`scan.go:323-329`：`billOrder.Status = 1; Save;` 之后才 `Update(usdt_num+…)`）；
⇒ **单次运行内每笔恰累加一次** ✓

- ★ **风险（应登记）**：整个核验逻辑跑在 `time.AfterFunc(2*time.Minute, …)`（`scan.go:275`）里。
  若进程在**「链上转账已成功」与「`Status` 置 1」之间**重启 ⇒ 该 bill 仍是 `status=0`、会被重跑，
  重跑时 `TransferTrxSuccess/TransferErcSuccess` 对**已成功的**转账仍返回 `suc=true` ⇒ **再累加一次**（**双计**）。
  ⇒ **口径性建议**：累加前应加**幂等判据**（例如以 `bill.status` 的**前值**为准：`if billOrder.Status == 0 { … }` 再置 1 并累加，同一事务内），
  或改用以 `bill` 为唯一事实源的**派生口径**。**本件只登记，不改代码。**

### C.3 结论（取代 v1 §4.4）

- **`custom.usdt_num` 不停用**（v1 "停用" 的前提已随 §A 作废）。
- **但它与 `bill.role=2` 的差异必须写进口径说明**：前者=已收割、后者=已分账；**对外呈现时须注明是哪一种**，⛔ 不得混用同一标签。
- 客户利润的**自域**口径（多租户）在**两者上任一**都成立，因为它们都已按 `user_id` 分户；
  **但都要先修 v1 §5.1 的 `customSettlementId`**，否则分账端会把所有客户的 `bill.settlement_id` 指向同一个客户 ⇒ **两个口径会一起错**。
- **`GetIndexInfo` 的 321 分支**（v1 §5）：`zlrUsdt` 当前取 `custom.usdt_num`（`sys_qianke.go:819`）——
  **在 `customSettlementId` 修好之前，它取到的是"第一个客户的已收割累计"**；修好后自然变成"本客户的已收割累计"。⇒ **无需改口径，只需修 §5.1。**
