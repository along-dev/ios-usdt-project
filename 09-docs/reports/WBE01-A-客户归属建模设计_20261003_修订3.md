### L.2 ★★ **存量上就已全额缺口**（`custom.usdt_num` 恒为 0，实际应收 613165）

```
$ SELECT b.status, COUNT(*) n, SUM(b.usdt_num) FROM bill b WHERE b.role=2 GROUP BY b.status;
status  n   sum_usdt
1       14  613165            ← 14 条 role=2 的 bill，**全部 status=1**

$ SELECT c.user_id, c.usdt_num AS accumulated,
         COALESCE((SELECT SUM(b.usdt_num) FROM bill b JOIN settlement s ON s.id=b.settlement_id
                    WHERE s.user_id=c.user_id AND b.role=2 AND b.status=1),0) AS sum_role2_status1
    FROM custom c;
user_id  accumulated  sum_role2_status1
201      0            613165          ← ★ 缺口 = 全额

$ SELECT s.user_id, COUNT(*) FROM bill b JOIN settlement s ON s.id=b.settlement_id WHERE b.role=2 GROUP BY s.user_id;
user_id  n
201      14                           ← 全部付给同一个客户（单租户）
```

**⇒ 三条结论（都由上表直接得出，非推断）**：
1. **缺口不是"将来会发生"，而是"当下已发生且是全额"** —— `0` 对 `613165`（100%）。
2. **成因与 §G 的判定完全吻合**：14 条 role=2 bill **全部 `status=1`** ＝**B 路径的形状**（A 路径创建时 `status=0`）⇒ **它们从未被 `scan.go:298` 的 `status=0` 查询选中过 ⇒ 从未累加**。
3. **`custom.usdt_num` 是 `varchar(32)`**（实测列型）⇒ ① `gorm.Expr("usdt_num + ?")` 靠 MySQL **隐式转换**（若出现非数字串会**静默变 0**）；② 不变量 SQL **必须显式 `CAST`**。

## §O · 裁定② 条件④：**不变量（可跑 SQL）**

### O.1 修复后的**目标不变式**（含 `CAST` —— L.2 实测该列是 `varchar(32)`）

```sql
-- 对每个客户：已累加值 应等于 其域内 role=2 且 status=1 的 bill 之和
-- ★ 仅在【修复时刻之后新增的 bill】上成立；存量见 §N.3
SELECT c.user_id,
       CAST(c.usdt_num AS DECIMAL(30,10))                                  AS accumulated,
       COALESCE(SUB.role2_status1, 0)                                      AS sum_role2_status1,
       COALESCE(SUB.role2_status1, 0) - CAST(c.usdt_num AS DECIMAL(30,10))  AS gap
  FROM custom c
  LEFT JOIN (
        SELECT s.user_id, SUM(b.usdt_num) AS role2_status1
          FROM bill b JOIN settlement s ON s.id = b.settlement_id
         WHERE b.role = 2 AND b.status = 1
         GROUP BY s.user_id
  ) SUB ON SUB.user_id = c.user_id;
-- 修复后（新数据）期望：gap = 0
-- 存量上（修复前）：gap = 613165（L.2 实测），见 §N.3
```

### O.2 条件④ 要求的**差额口径断言**（改后差额应只剩"未收割"）

```sql
-- 改后：差额 应恰等于「role=2 且 status=0」的部分（= A 路径中尚未核验通过的）
SELECT
  COALESCE((SELECT SUM(b.usdt_num) FROM bill b WHERE b.role=2 AND b.status=1),0)   AS confirmed,
  COALESCE((SELECT SUM(b.usdt_num) FROM bill b WHERE b.role=2 AND b.status=0),0)   AS pending,
  COALESCE((SELECT SUM(CAST(c.usdt_num AS DECIMAL(30,10))) FROM custom c),0)       AS accumulated;
-- 期望（新数据）：accumulated == confirmed  且  pending 单独存在
```

### O.3 多租户收口版（与 §E.1 / 候选 B 同链）

```sql
-- 客户 C 域内：
--   visible_bills(C) = { b | b.role=2 AND b.wallet_id 所属 wallet→machine→agent→packet.custom_user_id = C }
--                      ∪ { b | b.role=3 AND 同上（本域代理）}
-- 与 §E.1 同式；下面给出 role=2 的"钱包链"版本（不再只靠 settlement 归属）
SELECT b.id, b.role, b.usdt_num
  FROM bill b
  JOIN wallet  w ON b.wallet_id = w.id
  JOIN machine m ON w.machine_id = m.id
  JOIN agent   a ON m.agent_id = a.id
  JOIN packet  p ON a.packet_id = p.id
 WHERE p.custom_user_id = @c AND b.role IN (2,3);
```
> ★ **注意口径分叉（须在实现时统一，否则两个数又对不上）**：
> `customSettlementId` 走的是 **`bill.settlement_id → settlement.user_id = custom.user_id`**；
> 而 §E.1/§O.3 走的是 **`bill.wallet_id → … → packet.custom_user_id`**。
> **两条链在建模后应当一致**（因为收款方也按域分），但**它们不是同一条**。
> ⇒ **实现时必须选一条作为"唯一事实源"**，另一条仅供交叉校验。**我建议以 `wallet_id` 链为准**（它是设备/资金的天然归属，且与"自见"口径同构），把 `settlement` 链降为交叉校验。**此点请并入裁定。**
