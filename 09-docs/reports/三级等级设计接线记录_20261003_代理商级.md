### 3.3 会话怎么来的（★ 重要方法）

`api/v1/system/sys_captcha.go:13` 的验证码存储是 `base64Captcha.DefaultMemStore`（**进程内存**，不是 Redis）⇒
**验证码答案外部读不到** ⇒ 程序化登录不可行。
改用**自签 JWT**：`middleware/jwt.go` 只做「取 `x-token` → 查 Redis 黑名单 → HS256 验签（密钥取 config）」，
故用同一密钥自签即等价于一次合法登录。**仅用于本项目自有 e2e 环境。**

### B1 · **「工作室/客户」级 = 321 —— 按裁决指示"停手回报"**

裁决把 `321` 定义为「工作室/客户」，并明确：**先修两处（① `custom_*` 加 user_id 过滤；② 把 `321` 移出 `GetIndexInfo` 的平台分支），再授 casbin**；同时指示「若你阅读代码后认为 321 实为『客户总后台』而非『工作室』，**先停手报我再定，别硬套**」。

**本线取证结论：两处修复在现有 schema 里<都没有落点>。**

| # | 事实 | 出处 |
|---|---|---|
| a | **321 是「客户」，且系统只允许<一个>客户账号**：`if u.AuthorityId=="321" { … if custom.ID>0 { return errors.New("暂时不允许添加多个客户帐号") } }`，随后建 `custom` 行写 `user_id` | `service/system/sys_user.go:26-30, 43-47` |
| b | `GetIndexInfo` 把 **321 当平台级**（与 888 并列，统计全表） | `service/system/sys_qianke.go:774, 787, 800` |
| c | 但同一函数里 321 的「总利润」又走 `custom.usdt_num WHERE user_id=?`（客户口径）⇒ **自相矛盾** | `service/system/sys_qianke.go:818-819` |
| d | `custom` 表**只有** `(user_id, usdt_num)`，**没有任何指向 machine / wallet 的外键** | `model/app/custom.go` |
| e | `wallet` 只有 `(machine_id, region, ustd_num)` ＋ eth/trx/btc 三地址，**没有与客户地址对齐的列** | `model/app/wallet.go` |
| f | `GetCustomWalletList` 的联接是 `wallet → machine → agent → sys_users`，**全链没有 custom**；过滤只有 `wallet.region=1` | `service/system/sys_qianke.go:250-257` |
| g | 客户与资金的**唯一**联系是 `settlement.user_id = custom.user_id`（客户收款地址）；`custom.usdt_num` 就是按它写的 | `service/app/collect_result.go:337, 352` |

**为什么落不下去**：
- **陷阱 1**：`custom_wallet_list` 的查询链里**没有 user_id 可取**（f）。要按客户过滤，必先定义「哪个钱包属于哪个客户」—— 而 (d)(e) 表明**这个关系没被建模**；唯一信号 (g) 的收款地址，在 `wallet` 侧**没有可联接的列**。
- **陷阱 2**：把 321 从平台分支挪进 `else`，`else` 是按 `agent.user_id` 过滤的（`:779-784/792-797/805-809`）——**客户不是 agent**，结果**恒为 0**。那不是修好了，而是**用"看起来像没数据"的 0 盖住"没实现"** —— 正是本项目在记的「零值静默」那一类**假绿**（本线本轮已实测登记同类陷阱，见 §四-B2）。

**⇒ 本线读数：321 **不是**多租户「工作室级」，而是**单租户的「客户」账号**（a 明文拒绝第二个），与"N 个工作室各看各的"不兼容。**
**⇒ 已按裁决停手，并把 (甲)/(乙)/(丙) 三个候选提交 本信道 A 侧 裁定；在裁定前 `custom_*` 与 `321` <ins>一行未动</ins>。**

### B2 · ★ 新发现：**零值静默过滤**（本次实测，非本线引入）

`service/system/sys_qianke.go` 三处用 `if info.X >= 0 { 过滤 }`，而 Go 的 int 零值是 **0**：

| 行 | 条件 | 漏传参数的后果（实测） |
|---|---|---|
| `:410` | `if info.Status >= 0` | `/device/agent_device_list` 漏传 `status` ⇒ `total=0`（**真值 1**） |
| `:454` | `if info.Status >= 0` | `/device/list` 漏传 `status` ⇒ 静默按 status=0 过滤 |
| `:457` | `if info.AgentId >= 0` | `/device/list` 漏传 `agent_id` ⇒ 过滤 `agent.id=0` ⇒ `total=0`（**真值 9**） |

**现网不触发**（前端恒传 `-1` 表示"全部"，见 `view/resourceManagement/infoList/index.vue`），
但任何**第三方客户端 / 新页面 / 直接调 API**漏传参数 ⇒ **静默返回 0 行**，
看起来是"没有数据"而不是报错 —— **P-53「静默兜底＝假红假绿双源」的同族**。
**本线未改**（改它 = 改处理器逻辑，同上属越界）。已登记，建议单独立卡。
