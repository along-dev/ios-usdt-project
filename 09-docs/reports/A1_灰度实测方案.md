# A1 灰度实测方案：coruna 在 iOS 17.3–18.3 上的可行性判定

- **编制日期**：2026-09-27（T4 / R3）
- **上游判定**：`09-docs/reports/C3_前置判定报告.md`（2026-09-26，135 行）
- **性质**：★ **方案文档** —— **本方案【不含真机执行】**（Owner 裁决：真机验证先不做）
- **依据**：`group.html:553/558/571`、`platform_module.js:269-435/533-541`

---

## 0. 为什么需要实测（方案的前提）

`C3_前置判定报告.md` 的机械结论是：

1. `group.html` **只有下界门禁** `:553`（`13E4 > iOSVersion ⇒ return 1001`）；
   `:558` 的 `CORUNA_MAX_IOS` 仅 `window.log` + `console.warn` + `reportTelemetry`，★ **不含 `return`**。
2. `PSNMWj` 偏移表最大 `minVersion = 170000`，**表内无 17.3+ 条目，也无任何上界拒绝分支**。
   ⇒ iOS 17.3 / 17.4 / 17.6 / 18.0 / 18.3 / 18.6 **命中的条目完全相同 = 17.0 配置**。

**⇒ 推论**：代码层面 17.3+ **会"机械成功"地跑完**，不会报错、不会拒绝——
所以"能不能跑"不是问题，**"17.0 的偏移在 17.3+ 上是否仍然正确"才是问题**。
这个问题**只能靠实测回答**，本方案即为该实测的可执行定义。

## 1. 步骤一：设备选取

| 维 | 要求 |
|---|---|
| **版本覆盖** | **17.3 / 17.4 / 17.6 / 18.0 / 18.3 各 1 台**（共 5 台；若不可得，取 Owner 目标系统版本的最近邻） |
| **硬件** | ★ **必须为真机 ARM64**（`CPU_TYPE_ARM64 = 0x0100000C ⇒ runtime = PSNMWj`）。**模拟器会走 `:571`/`:578` 分支返回 `1003`，无判定价值** |
| **对照锚点** | ★ **额外 1 台 17.0.x 真机**作为**已知可用对照**（用于确认测试手法本身有效） |
| **状态** | 未越狱、Lockdown Mode 关闭（`:581` 的 IndexedDB 检测失败会 `return 1001`，干扰判读） |
| **网络** | 可访问投放入口（`group.html` 由 `serve.py` 提供） |

★ **判定价值**：5 台 ≥17.3 的机器用于**回答"漏洞是否仍在"**；1 台 17.0 用于**证明测试链路本身无缺陷**。
若无 17.0 对照机，任何失败都**无法区分**"漏洞被修"与"测试环境搭错了"。

## 3. 步骤三：判定规则

★ **这是本方案的核心判据，只有两条**：

| 情形 | 判据 | 结论 | 后续动作 |
|---|---|---|---|
| **A** | ★ **Stage1 失败**（`:630` 触发 `ABORT` / Stage1 模块未匹配 / WASM 原语未建立） | ★ **漏洞已修** | ★ **整段 17.3–18.3 放弃**。**不得补表**（补表无意义） |
| **B** | ★ **Stage1 成功，但 Stage2 或 Stage3 失败** | ★ **漏洞仍在** | ★ **值得补表**：补 Stage2/Stage3 对应 `minVersion` 条目 |
| **C** | Stage1/2/3 全成功 | 漏洞在且现有配置已够用 | 记录为"17.0 配置向上兼容"，**仍不改表** |

**关键判据原句（引自 C3 报告 §4）**：
> 只要 **Stage1（WASM 内存破坏）能成功**，说明漏洞仍在，此时补 Stage2/Stage3 的偏移才有意义。
> 若 Stage1 直接失败，则**整段区间应放弃**。

★ **排除项**：`PLATFORM_VERSION_OUT_OF_RANGE` 告警本身**不是失败**——
它是 `:558` 的 WARN，程序**继续执行**。**不得把 O2 告警当作情形 A 的证据**。

## 5. ★ 步骤五：回归约束（若判定为"值得补表"）

**前置事实（C3 报告 §5 + `platform_module.js:533-541` 实读）**：
选择逻辑是**累积应用（cumulative）**——

```javascript
const t = versionOffsetTable[platformState.runtime].reverse();
let n = Object.assign(platformState.versionFlags, t[0]);
for (const r of t.slice(1)) {
  if (r.GFx77t > platformState.iOSVersion) break;   // ← 下界比较，非上界
  n = Object.assign(n, r);
}
```

⇒ **插入一个新 `minVersion = 173000` 的条目，会同时影响所有 `iOSVersion >= 173000` 的设备**，
**且不会**（也不该）影响 `< 173000` 的设备——但**必须实测确认**这一点。

**⇒ 回归约束（硬性）**：

1. ★ **若补表，改表后【必须】回归 15.x–17.2 全区间**（不得只测 17.3+）。
2. **回归点建议**：`15.0 / 15.4 / 15.6 / 16.0 / 16.3 / 16.6 / 17.0 / 17.2.1`（覆盖表内每个 `minVersion` 边界）。
3. **回归判据**：每个回归点的 `versionFlags` **必须与本方案步骤四记录的原值逐字段相同**。
4. ★ **累积语义的副作用**：新条目一旦 `minVersion` 设得过低（如误设 `160000`），
   会**污染 16.x–17.2** 的既有行为 —— 这是**风险最高**的失误模式，回归即以捕捉它为目的。

★ **本方案不改表**。上述仅为"若将来 Owner 决定补表"时**必须遵守**的约束。
