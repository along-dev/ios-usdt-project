## 一 · 缺陷（**实读原文，非转述**）

三份判据件在**读环境变量**处各写了一个**落在最危险轴上**的默认值：

```python
# verify_f1c9_toaddress_guard.py:51-52      （sha 5708c0cb… / 20888 B）
# verify_f1c8_amount_guard.py:41-42         （sha fe5889df… / 10033 B）
# verify_money_path.py:45-46                （sha 0a1aaeaa… / 24235 B）
DB_NAME = os.environ.get("DSH_DB", "qk_e2e")
API     = os.environ.get("DSH_API", "http://127.0.0.1:8888")
```

**直读命令**（原样可复跑）：

```bash
cd "E:/ios漏洞/_integration/_fix_work"
grep -n -E 'DSH_DB|DSH_API' verify_f1c9_toaddress_guard.py verify_f1c8_amount_guard.py verify_money_path.py
```

**后果（fail-open）**：不设 `DSH_*` 直接 `python verify_money_path.py` ⇒

| 轴 | 默认落点 | 为什么是"最危险"的那一端 |
|---|---|---|
| `DSH_DB` | `qk_e2e`（**业务库**） | 判据会写入（账单/结算/分账夹具）⇒ 误跑直接**打业务库** |
| `DSH_API` | `http://127.0.0.1:8888`（**共享实例**） | 打在四卡共用的主栈实例上，而非隔离实例 `8900` |

⇒ **默认值恰好落在"写坏业务库"＋"打公共实例"这两个最危险轴的同一端** ⇒ 这是 `fail-open`（缺省即放开），不是 `fail-closed`。

### 1.1 同一套件内**已有**正确形态（对照，说明这不是"没法做"）

播种器**同一个目录**，写法不同 —— 它有硬闸：

```python
# seed_test_db.py:34-35
SRC_DB = os.environ.get("DSH_SEED_FROM", "qk_e2e")          # 业务库（来源，只读）
DST_DB = os.environ.get("DSH_DB", "qk_e2e_test")            # 测试库（目标）
# seed_test_db.py:42
print(f"⛔ 拒绝：DSH_DB({DST_DB}) == 来源库({SRC_DB}) —— 播种器不得写业务库")
```

同类硬闸**另有两处**在册先例：`09-docs/reports/verify_t27_v2_negative_control.py:44`（`assert env["DSH_DB"] != SRC`）
与 `01-backend-go/blockchain/billing_test.go:33-34`（DSN 含 `qk_e2e` ⇒ `t.Fatal`）。

⇒ ★ **结论**：护栏**在本项目已有成型写法**，恰恰是**三个最核心的判据**（且都是写路径）漏了这一层。

### 1.2 谁在掩护它（⚠️ 别把运行器当缺陷）

运行器 `iso_run.py:312` 会给子进程**注入**安全值：

```python
env = {**os.environ, "DSH_DB": DST_DB, "DSH_API": ISO_API}   # DST_DB="qk_e2e_test" / ISO_API="…:8900"
```

⇒ **只要走 `iso_run.py`，默认值就不会生效**（被注入覆盖）⇒ 缺陷**只在"绕过运行器直接跑判据"时暴露**。
所以本件的定性与修法都**不指向 `iso_run.py`**（它是对的），指向**判据自身的默认值**。

## 二 · 影响面

- **触发条件**：任何人（含自动化）在 `_fix_work/` 里直接 `python verify_*.py`、或复用这三件的**头部约定**去写新判据（新判据会照抄 `qk_e2e` / `8888` 两行）。
- **有没有真发生过**：本件**未找到**裸跑污染的事故记录 ⇒ 按**潜在缺陷**登记，**不主张**已发作（守「未发现≠不存在」的同理）。
- **在册旁证**：`09-docs/reports/T27-V2负控补做_20261003.md` 的前提风险条已记过同一口径（"不带隔离变量直接跑会污染业务库护栏对象"）⇒ 本件是把它**升级为独立方案件**。

## 三 · 方案

### 方案 A ★ 推荐：读 env 后**就地加硬闸**（与在册 `seed_test_db.py:42` 同型）

```python
DB_NAME = os.environ.get("DSH_DB", "qk_e2e")
API     = os.environ.get("DSH_API", "http://127.0.0.1:8888")
# ★ AD-02 硬闸：判据只许经 iso_run.py 注入 DSH_DB/DSH_API 后运行
assert DB_NAME != "qk_e2e",   "⛔ 拒绝裸跑：DSH_DB 落回业务库 qk_e2e（须经 iso_run.py 注入 qk_e2e_test）"
assert ":8888" not in API,    "⛔ 拒绝裸跑：DSH_API 落在共享实例 8888（须经 iso_run.py 注入 8900）"
```

**为什么这样就对了**：
1. 断言在**模块级、任何 DB/HTTP 连接之前** ⇒ 裸跑**在产生副作用之前**就退出（不是"跑到一半才拦"）；
2. **默认值保留**（`os.environ.get` 的第二参不动）⇒ 不改调用约定、不动 `iso_run.py`；
3. 与同目录 `seed_test_db.py:42`、`verify_t27_v2_negative_control.py:44`、`billing_test.go:33` **同一形态** ⇒ 一致性最好、评审成本最低。

### 方案 B：把默认值**翻转**到安全侧（`"qk_e2e_test"` / `8900`）
**代价**：改变"裸跑"语义，且**运行器未注入时会静默打隔离库** —— 从"静默打业务库"变成"静默打测试库"，**更难发现**（一个错误的物种换另一个）。⇒ **不推荐**（fail-safe 不等于 fail-loud）。

### 方案 C：**去掉默认值**，强制显式（`os.environ["DSH_DB"]` ⇒ 缺省 `KeyError`）
**优点**：最响亮（缺变量立即崩）。**代价**：改了三件的"可直接跑"体验，且报错信息不如 A 明确。⇒ 可作 A 的替代，**建议 A**（信息更指向根因）。

### 不推荐：加 `run_criteria.sh` 包装器
它**治不了**"有人直接 `python verify_*.py`"这条路（这正是漏洞触发路径）⇒ 只加门不堵洞。
