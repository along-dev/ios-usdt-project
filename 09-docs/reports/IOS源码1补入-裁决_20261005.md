## 一、裁决 ①：`auto-collect` —— ⛔ 不补入（构成架构冲突）

**适用判据**（Owner 原提示词 §2.3）：
> 冲突 = 补入后导致【同一能力存在两套并行的、语义重叠的实现】，且 USDT 已明确弃用其中一套

**`auto-collect` 恰有<ins>两半</ins>能力，<ins>两半</ins>都撞上 —— 三条独立证据：**

### 证据 1 · 阈值判定重叠（USDT 已有，且是 DB 驱动）

`auto-collect` 的判定函数做的事：**余额 ≥ 阈值 ⇒ 归集**，阈值来自 `config.collectThreshold.{eth,usdt}`，比对 `address.balance` / `address.usdtBalance`。

USDT 侧**已经这么做**，在 `01-backend-node/src_restored/schedules/collect-task.js`：

```js
// :231-232（每 2 秒一轮）
const threshold = parseFloat(config.threshold);
return DerivedAddress.find({ chain: config.chain, collectStatus: 'idle',
    [balanceField]: { $gte: threshold } }, {...})     // balanceField ← config.token 映射
```

其中 `balanceField` 由 `config.token` 映射为 `balance` / `usdtBalance` / `usdcBalance` —— **与 `shouldCollectEth` 用的字段逐一同名**。
⇒ **同一能力、同一判据、同一字段**,USDT 版还多出：`enabled` 开关、backdoor 配置、冷却、`waiting` 超时重置。

### 证据 2 · 执行重叠，且**签名信任模型对立**

| | USDT（既有，活体） | `auto-collect`（拟补） |
|---|---|---|
| 执行入口 | `core/collect/executor.js` `executeCollect(doc)` | `collectTronUsdt()` / `collectEth()` |
| 签名 | **本地签名** —— `core/collect/eth-collector.js:79` `new Wallet('0x'+privateKey, provider)` | **第三方代签** —— `POST https://tronapi.org/api/v1/{tron,eth}/transfer`，**body 带 `privateKey`** |
| 密钥出口 | 不出本机 | **私钥经 HTTP 出网** |
| RPC 来源 | `chainProviderPool.pick(chain)`（多 Key 池） | 第三方固定端点 |

⇒ 不是"两套写法"，是**两套互斥的信任模型**。补入即等于**在本地签名体系旁开一条私钥出网的旁路**。

### 证据 3 · USDT 侧已有一整套更成熟的同族设施

`collect-task.js` 内已含：**归集互斥**（`core/collect-bridge.js` 的 `shouldCollect`/`acquireLock`）、**崩溃残留回收**（`collectOwner` ＋ W2-C7 三判据）、**并发池**（`collectPool`）、**确认任务**（`collect-confirm-task.js`）。
`auto-collect` 一个都没有。

### 附带（不作为主证据，但同向）

- `auto-collect.ts` 的 `checkEthGas` 硬编码占位 key：`apikey=**YourApiKeyToken**`。
- 它调 `getTronAddressBalances(null, …)` / `getEthAddressBalances(null, …)` —— **在 USDT 会崩**（见 §三）。
- `collectTronUsdt` 的 gas 阈值写死 `requiredGas = 15`（TRX）。

### 裁决

⛔ **不补入。** 它**同时**踩了"两套并行实现"与"USDT 已弃用其一"两条。
★ **若仍需要它的判定语义** ⇒ **另立卡**做**改写**（把 `shouldCollect*` 的语义并进 `CollectConfig` 体系），⛔ **不属本任务**（本任务边界是"保义搬运"）。
★ **本项目钱包为测试数据**（Owner 已明示）⇒ **本裁决不按安全事件升级**；此处只作**架构取舍**，不作事故处置。

### 裁决

## 三、★ 连带发现 ③：`balance-refresh` **不是"纯搬迁"**（须 2 行适配）

**这是裁决过程中实读发现的，原提示词与我的需求件都**未**标出。**

`E:\IOS源码1\server\src\schedules\balance-refresh.ts`：

```
:112   result = await getEthAddressBalances(null, address.address);
:115   result = await getTronAddressBalances(null, address.address);
```

传 **`null`** —— 在 IOS源码1 里这是**约定**（其 `core/tatum/eth.ts:36` 签名 `client: TatumClient | null`，注释自述*"使用 null 让它自动使用 chainConfigClient（轮询 Key + 配额限制）"*）。

**但 USDT 侧没有 chainConfigClient，且 `client` 无 null 保护**：

```
02-backend-node/src_restored/core/tatum/eth.js:3-4
export async function getEthBalance(client, address) {
    const data = await client.ethRpc('eth_getBalance', ...);   // ← 直接解引用
```

⇒ **原样转成 .js 后，在 USDT 上 ETH / TRON 两条分支运行必 `TypeError: Cannot read properties of null (reading 'ethRpc')`。**

**USDT 的既有惯例是传 `tatumClient`**（`schedules/balance-init.js:44,47` 即如此；`core/tatum/client.js:187` 导出该单例）。

### 适配项（唯一需要改逻辑的地方）

| 行 | 原 | 改为 |
|---|---|---|
| `balance-refresh.ts:112` | `getEthAddressBalances(null, …)` | `getEthAddressBalances(tatumClient, …)` |
| `balance-refresh.ts:115` | `getTronAddressBalances(null, …)` | `getTronAddressBalances(tatumClient, …)` |

⇒ 需求件 §四 的"保义转换"必须**增列这一条例外**；`balance-refresh` 因此**不是零逻辑改动**。

### 为什么它仍值得补（不是冲突）

`balance-refresh`（12 小时一轮，取**全部**地址）与 USDT `balance-init`（**5 秒**一轮，**只取 `monitorStatus: 0` 且 `checkRetries < 3`**）**互补**：

| | `balance-init`（USDT 已有） | `balance-refresh`（拟补） |
|---|---|---|
| 间隔 | 5 秒 | **12 小时** |
| 取哪些 | **仅未纳入监控的新地址**（`monitorStatus: 0`） | **全部地址** |
| 作用 | 把新地址**纳入监控** | **已监控地址的周期性复算** |
| 含归集逻辑 | 无 | 无（实测 `threshold\|collect` 命中数 = **0**） |

⇒ **USDT 目前<ins>缺</ins>"已监控地址的定期复算"** —— 地址一旦 `monitorStatus: 1` 就再不复算（除非走归集路径）。`balance-refresh` 正好补这个洞。**✅ 不构成冲突。**
