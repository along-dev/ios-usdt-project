### 决策 1：`/app/*` 鉴权（N-12）—— **裁决：仅 `collect-result` 立即加鉴权**

| 选项 | 评价 |
|---|---|
| A. 全部加鉴权 | ❌ 会**立即打断现有投放链** —— `/app/device`、`/app/wallet` 是 gasleak→潜客 的写入通道，加鉴权须先给设备侧分发 token，涉及改动 gasleak 的桥接 |
| **B. 仅 `collect-result` 加鉴权** | ✅ **采纳** —— 该端点是**新增的**，无既有调用方，加鉴权零破坏；且它是唯一能**污染分账数据**的写入口 |
| C. 保持现状 | ❌ 任何人可伪造归集结果写入 `bill`，直接导致资金账目错误 |

**裁决理由**：
- **风险不对称**：`/app/device`/`/app/wallet` 的未鉴权是**既有设计**（写入的是本就被窃取的数据，伪造无收益）；
  而 `/app/collect-result` 写入的是**分账结果**，伪造可直接获利。
- **改动成本不对称**：新端点加鉴权 = 1 行 `.Use()`；既有端点加鉴权 = 需先解决设备 token 分发。

**落地要求**：

```go
// initialize/router.go —— 拆分路由组
AppPublicGroup := Router.Group("")                       // 保持裸奔（既有行为）
AppAuthGroup   := Router.Group("").Use(middleware.AppJWTAuth())   // ★ 新增

appPublicRouter.InitPublicRouter(AppPublicGroup)          // device / wallet
appAuthRouter.InitAuthRouter(AppAuthGroup)                // collect-result / wallet-status
```

> ⚠️ **注意**：§3.2 原写"鉴权：AppJWTAuth"是错描述，已在本报告更正。
> 同时须在方案 §3.2 补充「**当前实际未挂载**」的现状说明。

**遗留**：`/app/device`、`/app/wallet` 的鉴权**列入 P2**，待设备侧 token 分发方案确定后再评估。

### 决策 2：`Sk()` 的 `custom.ratio` bug（N-11）—— **裁决：改为残差法，与 `collect-result` 一致**

| 选项 | 评价 |
|---|---|
| A. 给 `custom` 表补 `ratio` 列 | ❌ **语义错误** —— `ratio` 是**代理**的属性（`agent.ratio`）；客户是**残差方**，本就不该有 ratio |
| **B. 改为残差法** | ✅ **采纳** —— `customAmount = total - systemAmount - agentAmount` |
| C. 不改 | ❌ `Sk()` 的客户分成查询**必然失败**（`Unknown column 'custom.ratio'`） |

**裁决理由（语义层面）**：

```
分账模型：
  平台 = packet.technical_service_fee   （固定比例，项目级配置）
  代理 = agent.ratio                     （代理级配置）
  客户 = 残差                            （100% - 平台% - 代理%）★ 客户不是比例方，是兜底方

→ 客户不存在独立的 ratio，补列会引入"三方比例之和可能 ≠ 100%"的不一致风险
```

**与已验证实现的一致性**：`collect-result`（P4.2 已通过 16/16）就是用残差法，
实测 `70 = 100 - 10 - 20` 正确。**`Sk()` 应与之一致。**

**落地要求**：

```go
// blockchain/scan.go 的 Sk()
// 修改前（错误）：
Select("settlement.id, settlement.address, custom.ratio, custom.user_id")
// 修改后（残差法）：
Select("settlement.id, settlement.address, custom.user_id")
// 且 customAmount 计算改为：
customAmount := totalAmount - systemAmount - agentAmount
```

**验证方法**：用 P4.2 已有的 e2e 数据集（`packet.technical_service_fee=10`, `agent.ratio=20`, `amount=100`），
期望 `10 / 20 / 70`。

### 决策 3：归集互斥实现位置 —— **裁决：gasleak collect 前 + 潜客侧加锁（双端）**

| 选项 | 评价 |
|---|---|
| A. 仅 gasleak collect 前检查 | ⚠️ 不完整 —— 潜客 `Sk()` 手动触发时不经过 gasleak |
| B. 仅潜客侧加锁 | ⚠️ 不完整 —— gasleak 侧的自动 collect 不经过潜客 |
| **C. 双端都做** | ✅ **采纳** |

**裁决理由**：**两条归集路径并存**（gasleak 自动 + 潜客 `Sk()` 手动兜底），
**任一单点互斥都会被另一条路径绕过**。

**落地要求**：

| 端 | 机制 | 说明 |
|---|---|---|
| **潜客侧** | 复用 `wallet.progress` | **已存在**（`ShouGe` 已检查 `progress==1`）；<br>但需**扩展为通用状态机**：`0=空闲 / 1=归集中 / 2=已归集` |
| **gasleak 侧** | collect 前查潜客 | 调 `/app/wallet-status` 确认 `progress==0` 才执行；<br>执行前置 `progress=1` |

**★ 关键**：**gasleak 侧必须先读潜客状态，再写** —— 否则两端各自检查本地状态，
存在**检查-执行窗口（TOCTOU）**。

**建议的原子化**：

```
gasleak collect 流程：
  1. POST /app/wallet-status { wallet_id }  → 若 progress != 0 则跳过
  2. POST /app/collect-lock   { wallet_id }  → ★ 新增：原子置 progress=1（乐观锁）
  3. 执行链上归集
  4. POST /app/collect-result { wallet_id, tx_hash, amount } → 写入 bill + 置 progress=0
```

> **`/app/collect-lock` 是新增端点**（决策 1 的鉴权组内）。
> 用 `UPDATE wallet SET progress=1 WHERE id=? AND progress=0` 的行锁语义保证原子性，
> 受影响行数 = 0 则说明已被占用。

### 决策 4：manifest size 不符（P1-7）—— **裁决：以磁盘实际大小为准**

| 选项 | 评价 |
|---|---|
| A. 修 manifest | ⚠️ 需改动**载荷原始素材**（规则：素材只读）；且 14 处都是同一模式，改源风险高 |
| **B. 构造容器时以磁盘为准** | ✅ **采纳** —— 不改素材，在 `buildContainer` 实现层规避 |

**裁决理由**：
1. **素材只读原则** —— `coruna/payloads/manifest.json` 属原始素材
2. **磁盘是权威** —— 磁盘上是**真实要投递的字节**；manifest 的 `size` 只是元数据
3. **14 处全部是 `entry3_type0x07.bin`（44 vs 49，差 +5）** —— 高度一致的偏移，
   推测是打包工具对某个固定结构的计数差异

**落地要求**：

```javascript
// Stage3_VariantB.js 的 buildContainer() / payload_cdn.py 的实现层
// ❌ 不要用：
const size = ent.size;                       // manifest 声明值（可能错）
// ✅ 要用：
const data = fs.readFileSync(filePath);
const size = data.length;                    // ★ 磁盘实际大小（权威）
// 并在构造后校验：
if (ent.size && ent.size !== data.length) {
    logger.warn({ file: ent.file, manifest: ent.size, disk: data.length },
                'manifest size mismatch — using disk size');
}
```

**★ 附带要求**：构造容器后**必须做完整性自检**（`verify_f00dbeef()` 已有），
校验 magic + 条数 + 偏移不越界。

**验证方法**：`python _integration\_fix_work\verify_manifest_sizes.py`
—— 修正后应显示"全部以磁盘为准，0 处越界"。

### 决策 6：`config.yaml.example` 的 `signing-key`（N-2）—— **裁决：按"真值"处理，纳入脱敏**

| 选项 | 评价 |
|---|---|
| A. 先确认再决定 | ⚠️ 无法确认 —— `signing-key` 是**服务端自用**，无法从外部验证其有效性 |
| **B. 按真值处理，直接脱敏** | ✅ **采纳** —— **安全默认**：不能证实为假值，就当它是真值 |
| C. 忽略 | ❌ 若为真值，等于**交付了一份含真实密钥的配置** |

**裁决理由**：
- 该字段是文件中**唯一**呈真实 UUID 形态的凭证（其余均为 `yourAccessKeyId`/`xxxxxxxx`/空串）
- **形态高度可疑** + **无法证伪** → 按最坏情况处理
- **脱敏成本为零**（加一条替换规则）

**落地要求**：

```powershell
# build_unified.ps1 的 $SANITIZE_REPLACEMENTS 增加：
'signing-key: ${SIGNING_KEY}' = 'signing-key: ${SIGNING_KEY}'

# $SANITIZE_PLAINTEXT_PATTERNS 增加自检特征：
'${SIGNING_KEY}'
'${SIGNING_KEY:0:8}'
```

**★ 附带改进**：把 N-2 的类型（**"无法证伪的疑似真值"**）写成脱敏规则，
避免以后每个可疑字段都需人工裁决。
