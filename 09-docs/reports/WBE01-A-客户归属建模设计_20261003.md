## 〇 · 一句话结论

**`custom`（客户）与「钱包/设备」之间<没有任何联接列>；多租户的归属必须新建。**
建议采用**候选 B：`packet` 增 `custom_user_id`** —— 它与现网已有的链 `wallet → machine → agent → packet` **只差最后一步**，且因 `packet.custom_user_id` 是**单值**，**行集不相交是结构性成立的**（不是靠断言碰运气）。
**并且**：本次取证另发现 **`custom.usdt_num` 是死字段（从不被写）** —— 归属建模必须同时决定「客户利润」的口径来源（建议改用 `bill` role=2 派生），否则会"接了一个从不更新的数"。

## 一 · 现状取证（逐条带 `file:line`，均为本轮实读）

### 1.1 归属链的**断点**在哪

| 环节 | 现网是否有联接 | 出处 |
|---|---|---|
| `packet → agent` | ✅ `agent.packet_id` | `model/app/agent.go` |
| `agent → machine` | ✅ `machine.agent_id` | `model/app/machine.go` |
| `machine → wallet` | ✅ `wallet.machine_id` | `model/app/wallet.go` |
| `agent → 结算地址` | ✅ `settlement.user_id = agent.user_id` | `service/app/collect_result.go:125-130` |
| 平台 → 结算地址 | ✅ `settlement.user_id = 0` | `collect_result.go:134-136` |
| **`custom → 上述任何一个`** | ❌ **不存在** | 见 1.2 |

### 1.2 客户侧的联接是**空的**（三条独立证据）

1. **`custom` 表只有三列**：`(id, user_id, usdt_num)` —— `model/app/custom.go`；DB 实测 3 列 / 1 行 `(1, 201, 0)`。
   全库 `information_schema` 中**没有任何**指向 custom 的外键列（唯一含"客户"字样的列是 `bill.role` 的注释：`角色 1平台， 2客户， 3代理, 4私域`）。
2. **`GetCustomWalletList` 的联接链不含 custom**：
   `wallet → machine → agent → sys_users`，过滤只有 `wallet.region=1` —— `service/system/sys_qianke.go:250-257`。
3. **★ 分账里的客户是"全局单例"（这是最强的证据）**：
   ```go
   // service/app/collect_result.go:330-341  customSettlementId
   tx.Model(app.Custom{}).
       Where("settlement.chain LIKE ?", "%"+chain+"%").
       Joins("left join settlement on settlement.user_id = custom.user_id").
       Select("settlement.id").Limit(1).Find(&row)
   ```
   **`Model(app.Custom{})` 后面<没有任何 custom 过滤>，直接 `Limit(1)`** ⇒ 语义是"取表里第一行客户"。
   即：**当前所有设备的客户分成都付给同一个客户**。这不是"默认值"，这是**单租户的结构性体现**。

### 1.3 相应的单租户守卫（须去除，但要换成幂等保护）

```go
// service/system/sys_user.go:26-30
if u.AuthorityId == "321" {
    global.GVA_DB.Find(&custom)          // ← 无任何条件
    if custom.ID > 0 {
        return errors.New("暂时不允许添加多个客户帐号"), userInter
    }
}
```
⇒ 按 Owner 裁定**去除**；**但不是无脑删**，应改为「同一 `sys_users.id` 不得重复建 `custom` 行」的**幂等保护**（否则并发注册会造出重复 custom 行，归属立刻歧义）。

### 1.4 ★ 附带发现（卡里未提，但**直接影响本设计**）：`custom.usdt_num` 是**死字段**

全仓 grep `UsdtNum` 且含 custom 的写入点**只有一处**：

```go
// service/system/sys_user.go:44   —— 注册时置 "0"
custom.UsdtNum = "0"
```

**此后没有任何代码更新它**。而它被**读**两处：`sys_qianke.go:819`（321 的"总利润"）、以及客户财务页。⇒ **该字段恒为 `0`（存量 1 行实测就是 `0.000`）**。
**客户利润的权威来源实际是 `bill`（`role=2`，且 `bill` 带 `wallet_id`/`settlement_id`/`usdt_num`）** —— `collect_result.go:274-281` 落 `role=2` 时写的就是客户侧金额。

⇒ **结论**：归属建模**必须同时决定客户利润的口径来源**。若沿用 `custom.usdt_num`，等于"给多租户接了一个从不更新的数"——客户端永远看到 0，且**看起来像"没数据"而不是"没实现"**（本项目在记的那类假绿）。

## 二 · ★ 归属口径：候选与取舍

> 评判轴：① 与既有链的**距离**（改动面）；② 是否**天然保证行集不相交**；③ 对**存量数据**的处置难度；④ 是否**越权扩张**现有语义。

| 候选 | 内容 | 联接表达 | ①距离 | ②不相交 | ③存量 | ④语义 | 取舍 |
|---|---|---|---|---|---|---|---|
| **B ★推荐** | **`packet` 增 `custom_user_id`** | `p.custom_user_id = <claims.ID>`，且 `wallet→machine→agent→packet` 已存在 | **最短（只差一步）** | ✅ **结构性成立**（packet 单值 ⇒ 每个 wallet 最多属一个客户） | 易：默认 `0`＝未绑定，存量 1 行保持 0 并登记 | ✅ "项目归谁"是业务上最自然的归属点（域名/落地页/技术服务费都在 packet 上） | **采用** |
| A | `custom` 增 `packet_id` | 同 B，方向相反 | 同 | ✅ | 同 | ⚠️ 只能表达"一客户一包"；要多包得再建关系表（反而更重） | 否 |
| C | 新建 `custom_agent` 关系表 | N:M | 最远（新表 + 新查询路径） | ❌ 需额外约束才不相交 | 中 | ⚠️ 与 `agent.packet_id` 形成**双重归属**，可能冲突 | 否 |
| **F**（我补的候选） | `agent` 增 `custom_user_id` | `a.custom_user_id = <claims.ID>` | 短 | ❌ N:M 风险（agent 属 packet 又属客户） | 中 | 更贴"客户＝渠道方拥有代理商" | 备选 |
| **D'**（我补的候选） | `wallet` 增 `custom_user_id`（直接打标） | 直接 | 最短 | ✅ | 难：wallet 由归集自动创建，须**归集时**就知道客户 | ⚠️ 归属**冗余**到 wallet 上 ⇒ 与 packet 归属**漂移**风险 | 不推荐 |
| D（原候选） | 复用 `settlement.user_id` | — | — | — | — | **不可行**：`wallet` 只有自身三地址（`eth/trx/btc_address`），**没有指向客户 settlement 的列**；只用一个自定义收款地址，无法区分租户 | **证否** |
| E（我补的候选） | 复用 `packet.group_id` | — | — | — | — | **不成立**：`group_id` 标识的是"包"（设备上报带的），**不承载客户身份** | **证否** |

★ **卡里未列、我补上的候选 = F（`agent` 侧）与 D'（`wallet` 侧）**；另有 D/E 两条被**证否**（列在上表以备复核）。

### 推荐 **B** 的理由（一句话版）

**`wallet → machine → agent → packet` 这条链现网已经存在且被 `collect_result.go:111-114` 实际使用**；
多租户只需在这条链的**末端加一列**，而不是新建一条平行链 —— 改动面最小、**不相交由数据结构保证**、且不动 `custom` 表（现仅 3 列）。

## 三 · 迁移方案 + 回滚（**两条都要能一条命令跑完**）

> ⚠️ **本卡要求：迁移脚本在未经调度放行前<不得对库执行>。** 以下 SQL **尚未对 `packet` 表执行**。
> ⚠️ 另按卡的要求，脚本须**自证"非注释态"**（前车之鉴：`40-prod-db-hardening.sql` 全是注释、执行等于空操作）。

### 3.0 ★ SQL **已实跑自证**（在一次性 scratch 表上，非 `packet`）

为满足卡的"非注释态"要求，上述 up/down **模式**已在一片**一次性 scratch 表**上真跑一遍（**未触碰 `packet`**）：

| 步骤 | 实跑读数 |
|---|---|
| `ADD COLUMN IF NOT EXISTS custom_user_id ...` | `UP-CHECK col_exists = 1` ✓ |
| 生效自证（未绑定行数） | `UP-CHECK2 unbound = 1` ✓ |
| **幂等**：同一句 `ADD COLUMN IF NOT EXISTS` 再跑一次 | `IDEMPOTENT OK 重复执行未报错` ✓ |
| `DROP COLUMN IF EXISTS custom_user_id` | `DOWN-CHECK col_exists = 0` ✓ |
| 清理 | `CLEANUP leftover = 0`（scratch 表已删，**零残留**）✓ |

⇒ 结论：**该 SQL 模式可跑、幂等、可逆**（MariaDB 11.4.4 支持 `ADD/DROP COLUMN IF (NOT) EXISTS`）。**但 `packet` 表本身仍未被触碰。**

### 3.1 向前（up）— `07-db/migration/50-custom-ownership.sql`（拟）

```sql
-- WBE01-A 卡 A：客户/工作室归属建模（packet.custom_user_id）
USE qk_e2e;

-- 幂等：已存在则跳过（MariaDB 10.4+ 支持 IF NOT EXISTS）
ALTER TABLE `packet`
  ADD COLUMN IF NOT EXISTS `custom_user_id` int NOT NULL DEFAULT 0
  COMMENT '归属客户(system.sys_users.id)；0 = 未绑定（无主项目）';

-- ★ 存量处置：**不猜**。现仅有 1 行 packet(id=1,'E2E测试包')，
--   其真实归属**未知** ⇒ 保持 0（未绑定），并登记为待运营/ Owner 绑定。
--   ⛔ 不写 "UPDATE packet SET custom_user_id=201" —— 那是把"当前唯一客户拿到全部"的
--      单租户行为当成业务意图去固化，属凭空造数据。

-- ---- 生效自证（非注释：真跑真回显）----
SELECT 'SELF-CHECK' AS section,
       COUNT(*) AS col_exists
  FROM information_schema.columns
 WHERE table_schema = DATABASE() AND table_name = 'packet' AND column_name = 'custom_user_id';
-- 期望 col_exists = 1

SELECT 'UNBOUND' AS section, COUNT(*) AS unbound_packets
  FROM `packet` WHERE `custom_user_id` = 0;
-- 期望 unbound_packets = 1（存量 1 行；绑定后应降为 0）
```

### 3.2 向后（down）— `07-db/migration/50-custom-ownership-rollback.sql`（拟）

回滚前**先核该导出件在**。**这一条不在本设计的自动范围内，是人工步骤** —— 明写，不假装已自动化。

## 四 · 不变量（**可断言的 SQL**）

### 4.1 定义式：客户 C 可见的钱包

```
可见钱包(C) = { w | w.machine_id → machine m → agent a → packet p , p.custom_user_id = C }
            ∩ { w | w.region = 1 }          ← 与现网 GetCustomWalletList 的 region 口径一致
```

```sql
-- 参数：@c = 客户用户的 sys_users.id
SELECT w.id
  FROM wallet w
  JOIN machine m ON w.machine_id = m.id
  JOIN agent   a ON m.agent_id   = a.id
  JOIN packet  p ON a.packet_id  = p.id
 WHERE p.custom_user_id = @c
   AND w.region = 1;
```
> ★ 与现网 `GetCustomWalletList`（`sys_qianke.go:250-257`）**只差 `JOIN packet` 与最后的 `WHERE`** —— 这是"最小改动"的具体形态。

### 4.2 不变量 A：**行集互斥**（多租户的核心保证）

```sql
-- 断言：不存在"同时归属两个不同客户"的钱包（期望 0 行）
SELECT w.id AS wallet_id, COUNT(DISTINCT p.custom_user_id) AS owners
  FROM wallet w
  JOIN machine m ON w.machine_id = m.id
  JOIN agent   a ON m.agent_id   = a.id
  JOIN packet  p ON a.packet_id  = p.id
 WHERE p.custom_user_id <> 0
 GROUP BY w.id
HAVING owners > 1;
-- 期望：0 行
```
**结构性理由**：`packet.custom_user_id` 是**单值列** ⇒ 每个 packet 恰属一个客户；而 `machine.agent_id → agent.packet_id` 是**函数**（一个设备一条链）⇒ 每个 wallet 最多落一个客户。**故本不变量由数据结构保证，不是靠运气。**

### 4.3 不变量 B：**未绑定 ≠ 可见**

```sql
-- 断言：未绑定项目下的钱包，对任何客户都不可见（期望：对任意 @c 均为 0 行）
SELECT COUNT(*) FROM wallet w
  JOIN machine m ON w.machine_id=m.id JOIN agent a ON m.agent_id=a.id
  JOIN packet  p ON a.packet_id=p.id
 WHERE p.custom_user_id = 0 AND w.region = 1 AND p.custom_user_id = @c;
-- 期望恒 0（`p.custom_user_id = 0` 与 `= @c` 互斥）
```

### 4.4 不变量 C：**客户利润的口径**（替代死字段）

```sql
-- 客户的权威利润 = 其名下钱包产生的 role=2 bill 的 usdt_num 之和
-- （依据：bill.wallet_id 已存在；collect_result.go:274-281 落 role=2）
SELECT COALESCE(SUM(b.usdt_num), 0) AS custom_profit
  FROM bill b
  JOIN wallet  w ON b.wallet_id = w.id
  JOIN machine m ON w.machine_id = m.id
  JOIN agent   a ON m.agent_id   = a.id
  JOIN packet  p ON a.packet_id  = p.id
 WHERE b.role = 2 AND p.custom_user_id = @c;
```
⇒ 与 `GetIndexInfo` 的 321 分支（现读 `custom.usdt_num`，`sys_qianke.go:819`）**口径必须改为本式**。

## 五 · 对 `GetIndexInfo` 的处置（★ **顺序纪律**）

`service/system/sys_qianke.go:774 / 787 / 800` 三处把 `321` 当**平台级**（与 `888` 并列、统计全表）。

**★ 硬性顺序（卡里已明示，这里给出理由与落点）**：

| 步 | 动作 | 若顺序颠倒会怎样 |
|---|---|---|
| 1 | 完成 §三 的建模 + 回填 | — |
| 2 | 三处**移出平台分支**，并为 321 新增**客户口径分支** | ⛔ 若在建模前就移出：`321` 会落进现有的 `else` 分支，而该分支按 **`agent.user_id`** 过滤（`:779-784 / 792-797 / 805-809`）——**客户不是 agent** ⇒ **恒 0**，正是"用假绿盖住没实现" |

**321 分支的实现口径（三项）**：

| 指标 | 现在的取法 | 建模后的取法 |
|---|---|---|
| `azNum`（安装数） | 平台分支：全表 `Count(machine)` | `machine JOIN agent JOIN packet WHERE packet.custom_user_id = <c>` |
| `sqNum`（授权数） | 平台分支：`machine.status=1` 全表 | 同上 + `machine.status=1` |

### 5.1 `customSettlementId` / `customSettlementAddr` 的签名必须变（代码改动登记）

现签名只带 `(tx, chain)`，**无法知道"这一笔属于哪个客户"**（`collect_result.go:330-341 / 343-357`）。
建模后必须**带上钱包（或 packet/custom）**，例如 `customSettlementId(tx, chain, walletId)`——由 `wallet → machine → agent → packet → custom_user_id` 解出客户，再去其 `settlement`。
**调用点**：`collect_result.go:275`（落 `role=2`）。★ **这是本卡落地阶段最需要注意的一处**：若漏改，分账会继续把**所有客户的分成付给第一个客户**。

### 5.2 去除单客户守卫（§1.3）

`sys_user.go:26-30` 的 `Find(&custom); if custom.ID > 0 { 报错 }` ⇒ 改为**幂等保护**（按 `user_id` 查重），不是删除。
