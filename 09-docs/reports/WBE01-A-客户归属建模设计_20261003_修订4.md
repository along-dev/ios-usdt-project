## §R · 裁定④ 落地：存量补记（一次性、独立迁移件）

### R.1 ★ 设计要点：用 **`SET = 权威和`** 而不是 **`ADD 差额`** ⇒ **幂等由构造保证**

```
补记动作（每个客户一次）：
  UPDATE custom c
     SET c.usdt_num = (
           SELECT COALESCE(SUM(CAST(b.usdt_num AS DECIMAL(30,10))), 0)
             FROM bill b JOIN settlement s ON s.id = b.settlement_id
            WHERE s.user_id = c.user_id AND b.role = 2 AND b.status = 1
         );
```

**为什么是 `SET` 而不是 `ADD`（对应调度条件②"幂等，重跑不得二次叠加"）**：
`SET` 是**绝对赋值** ⇒ **重跑时右侧值不变（同一批行）⇒ 写入也不变** ⇒ **天然幂等**，**不需要额外的"已补记"标记位**。
（若用 `ADD 差额`，就必须额外维护一个"补过没有"的状态，否则重跑即二次叠加 —— **那才是需要防的形态**。）

### R.2 四项条件 ↔ 落点

| 调度条件 | 落点 | 说明 |
|---|---|---|
| **① 独立迁移件（可审计、可单独回滚）+ **补记前先落快照** | `07-db/migration/51-custom-usdtnum-backfill.sql` ＋ `51-…-rollback.sql` | 快照件：补记前把 `SELECT id,user_id,usdt_num FROM custom` 导出到 `_fix_work/_wbe01a_custom_snapshot_<ts>.tsv`（**实测补记前全为 `'0'`**，见 R.4） |
| **② 单事务 + 幂等** | `START TRANSACTION; … COMMIT;` ＋ R.1 的 `SET` 语义 | **幂等由构造保证**（R.1） |
| **③ 范围严格限定**：修复时刻前已 `status=1` 且未累加的 role=2 行；与新逻辑**不交叠** | `WHERE b.role=2 AND b.status=1` | ★ **顺序保证不交叠**：**补记迁移先跑、实现改动后上**（§V 两阶段）。补记时刻**新逻辑尚不存在** ⇒ 不存在"新逻辑已累加行"被重复计入的可能 |
| **④ 补记后立即跑不变量** | 见 R.3；**不等即回滚**（回滚＝用快照恢复，见 R.4） | |

### R.3 补记后的不变量（**必须等于**，不等即回滚）

```sql
SELECT c.user_id,
       CAST(c.usdt_num AS DECIMAL(30,10)) AS accumulated,
       COALESCE(S.role2_status1, 0)       AS expect
  FROM custom c
  LEFT JOIN (SELECT s.user_id, SUM(CAST(b.usdt_num AS DECIMAL(30,10))) AS role2_status1
               FROM bill b JOIN settlement s ON s.id = b.settlement_id
              WHERE b.role = 2 AND b.status = 1
              GROUP BY s.user_id) S ON S.user_id = c.user_id
 WHERE CAST(c.usdt_num AS DECIMAL(30,10)) <> COALESCE(S.role2_status1, 0);
-- 期望：0 行（不等即回滚）
```

### R.4 快照（**实测**：补记前全为 `'0'`）

```
$ SELECT id, user_id, usdt_num FROM custom;
id  user_id  usdt_num
1   201      0            ← 只有 1 行；回滚件即 "UPDATE custom SET usdt_num='0' WHERE id=1;"
```
⇒ **回滚一条命令**即可（且不依赖导出件也能写死原值，导出件作双保险）。

### R.5 ★★ **顺序上的一个硬前提**（本件新发现，必须写进放行条件）

补记用的**只能**是 `settlement` 链（R.1 的 SQL）—— 因为 `packet.custom_user_id` **此刻还不存在**（实测：`SELECT custom_user_id FROM packet` → `ERROR 1054 Unknown column`）。
而裁定⑤ 定的**唯一事实源是 `wallet_id` 链**。⇒ 两条链**在补记时刻无法互相校验**（`wallet` 链需要 `custom_user_id`，而它全为未绑定/不存在）。

**⇒ 因此补记的前提是**：**"`settlement` 链在<补记时刻>是可信的"**。当前可支持该前提的实测事实是：
- `settlement.user_id = 201` 唯一且全部 14 条 role=2 bill 都指向它（单租户下**不存在歧义**）——**这正是 L.2 的实测**。
- **多租户之后**该前提才需要重新验证 ⇒ **裁定⑤ 的交叉校验断言在"存量绑定"建立之后才有意义**（§S.3）。

★ **若你要求"补记前必须先建立绑定并校验双链一致"**，则顺序要改为：`建列 → 绑定 → 双链校验 → 补记 → 上码`。
**我建议维持"先补记"**（单车可审计、且单租户下无歧义），但**请你确认**——这是本件唯一影响你放行顺序的点。

## §S · 裁定⑤ 落地：`wallet_id` 链为**唯一事实源**

### S.1 定义（唯一事实源）

```
bill 的归属客户  :=  packet.custom_user_id
                    其中 packet 由  bill.wallet_id → wallet → machine → agent → packet 解出
```
**理由（采纳）**：这是**因果链**（钱从哪台设备来 ⇒ 设备属谁的包 ⇒ 包属谁）；`settlement` 链是**目的链**（客户收款地址），**会随客户改地址而漂移**。

### S.2 `settlement` 链降为**交叉校验**

`customSettlementId` / `customSettlementAddr`（`collect_result.go`）与 `scan.go:78-81` 的 `CustomSettlement`
—— 三处仍需**按域解出客户**（否则分账付错人），但**不再作为"谁是这笔的客户"的事实源**，只作**交叉校验**。

### S.3 交叉校验断言（调度条件）

```sql
-- 两条链解析出的客户不一致 ⇒ 判红（不是静默取一条）
SELECT b.id,
       P.custom_user_id              AS by_wallet_chain,
       S.user_id                     AS by_settlement_chain
  FROM bill b
  JOIN settlement S ON S.id = b.settlement_id
  LEFT JOIN wallet  w ON b.wallet_id = w.id
  LEFT JOIN machine m ON w.machine_id = m.id
  LEFT JOIN agent   a ON m.agent_id = a.id
  LEFT JOIN packet  P ON a.packet_id = P.id
 WHERE b.role = 2
   AND COALESCE(P.custom_user_id, 0) <> 0           -- 未绑定(0) 不参与比对
   AND P.custom_user_id <> S.user_id;
-- 期望：0 行
```
★ **登记要求（调度条件）**：把它登记为**已知的、被监控的偏差来源** —— 即：**未绑定（`custom_user_id=0`）的行暂不参与比对**，其数量须**随绑定进度单调下降**，并作为本卡的**收口指标**。

## §T · ★★ **范围遗漏提醒**：`agent.usdt_num` 有**完全相同的缺口**（请裁是否并入裁定④）

**实测**（与 L.2 同法）：

```
$ SELECT a.id, a.user_id, a.usdt_num, (SELECT SUM(b.usdt_num) FROM bill b JOIN settlement s …WHERE s.user_id=a.user_id AND b.role=3 AND b.status=1)
agent id=1  user_id=101  accumulated=0   sum_role3_status1=175190   ← 缺口 100%
agent id=5  user_id=9    accumulated=0   sum_role3_status1=0
$ role=3 的 bill：14 条，**全部 status=1**，合计 175190
```

⇒ **与客户侧同因同形**：14 条 role=3 bill 全 `status=1`（B 路径形状）⇒ **从未被 `status=0` 查询选中 ⇒ 从未累加**。
**裁定④ 只圈了 role=2** ⇒ **代理侧 175190 的缺口不会被补**。

**请裁**：(a) 并入同一补记迁移（**同一件、同一事务、同时 SET**，成本几乎为零）；(b) 另开一件；(c) 有意不补（需说明理由）。
★ **我建议 (a)** —— 同因同形、同一时刻、同一幂等语义；**分开做只会多两次审核轮次，不增加任何安全性**。
