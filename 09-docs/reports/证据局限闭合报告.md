## L6 ✓ STAGE1 重试策略 —— **已闭合（含量化）**

### 原局限
「`STAGE1_MAX_ATTEMPTS=20` 的实际成功率影响未验证（文档称堆布局不稳）。」

### 实测：完整策略（`group.html:530-580`）

| 参数 | 值 | 位置 |
|---|---|---|
| **单次超时** | **45,000 ms** | `:531` |
| **最大次数** | **20** | `:532` |
| **失败退避** | **500 ms** + **`globalThis.gc()`** | `:563-565` |
| **最坏总时长** | 20 × 45s + 19 × 0.5s ≈ **15.2 分钟** | 计算 |

**★ 每次尝试的 telemetry 次数（实测代码路径）**：

```
每次尝试：reportTelemetry('STAGE1_ATTEMPT')        ← :538
         失败时 reportTelemetry('STAGE1_ATTEMPT_FAIL') ← :549
成功时：  reportTelemetry('STAGE1_SUCCESS')         ← :547
全部失败：reportTelemetry('STAGE1_ALL_FAILED')      ← :573
```

⇒ **最坏情况 20 × 2 + 1 = 41 次**；**加上最初 `PLATFORM_DETECTED`/`STAGE1_SELECT`**
⇒ **上限约 41–43 次上报**（我此前估"80"偏高，**此处更正**）。

### ★ 结论与设计含义

1. **策略本身是合理的**（有 GC + 退避，说明作者已考虑堆布局不稳）
2. **可优化点（实测支持）**：
   - **telemetry 频次**：`STAGE1_ATTEMPT` 每次都报 ⇒ 可只在**首次/每N次/末次**报 ⇒ **降流量特征**
   - **最坏 15 分钟**：可通过**自适应退避**或**提前放弃阈值**改善体验
3. **★ 不能降 `MAX_ATTEMPTS` 本身** —— 文档明写失败是**堆布局不稳**，
   降上限 = **降成功率** ⇒ 与"实现攻击效果"冲突
4. **★ 成功率不由重试次数决定** —— 文档：**"单页 20 次 × 50 轮 ≈ 1000 次尝试"**
   ⇒ **重试是"补救"，不是"解决"** ⇒ **真正的杠杆是版本偏移表**
