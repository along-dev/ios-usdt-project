## 五、★★ 开工前必须先裁决的 2 项

### 裁决 1：`/api/track/*` 三路径硬冲突（**决定服务能否启动**）

**实测事实**：`plugins/api/routes/landing.js` **已注册**：

```
landing.js:94    fastify.post('/api/track/start', ...)
landing.js:123   fastify.post('/api/track/heartbeat', ...)
landing.js:144   fastify.post('/api/track/click', ...)
```

而 Android 的 `track.js` **规格要求同样三条路径** ⇒
**直接注册会导致 Fastify 重复路由启动失败**（或静默覆盖落地页埋点）。

```
需要决策：Android track 与落地页 track 是同名冲突，如何处理
建议：(a) 复用 —— 两者共用 /api/track/*，仅靠参数区分平台
理由：语义确实是同一件事（都是埋点）；避免重复路由；
      不改已验收的 landing.js
备选：(b) 分域 —— 落地页迁到其他前缀（代价：改已验收代码，风险高）
      (c) 按 Host/UA 分流（代价：同一实例内仍冲突，复杂度高）
影响范围：D1-C2；是否要改 landing.js
不决策时的行为：D1-C2 不得开工
```

### 裁决 2：C2 域名参数化的落点

**事实**：`05-ios/darksword/` 有 **17 处硬编码** `sqwas.ebwlyais.xyz`
（含 `pe_main.js:1428,1442` 的 WiFi 口令外传目标）。

**方案已给解法**（主方案 `L1469`）：**改 `__C2_ENDPOINT__` 占位符 + 打包期注入**。

```
需要决策：C2 域名参数化是否现在做，落点在谁
建议：做；落点在 build 侧（模板占位符 + 打包注入），不手改产物 .js
理由：主方案 L1469 已明确该做法；手改会断打包链
注意：build_unified.ps1 单一写者 = W1-C1 ⇒ 须由同一写者承接
备选：保留原域名（代价：部署到新环境后载荷仍回连原站）
影响范围：D0-C7；05-ios/darksword 与打包脚本

```

## 八、固定动作（每张卡 12 步）

1. **基线检查**（无 git ⇒ 核对卡片 `base` sha256 与现树相符）
2. **定档** R0–R3 + **写理由**（不写 = 未定档）
3. **取基线快照** `sha256 + bytes + eol`（★ **`eol` 必须实测**）
4. `task_branch` 写「无」
5. **派执行 Agent**（卡片全文 + 副本路径 + 副本来源声明）
6. **【复核】自己重跑 verify**，取**你会话里的真实退出码**，逐位比对
   （取码不接管道：`echo "EXIT=$LASTEXITCODE"`）
7. **提交** = 确认副本 sha256 + 写台账
8. **派审核**：R0 不派 / R1 派 1 / R2 派 2（异质）/ R3 加专项
9. **处置 Finding**：**P0/P1 → 停下升级 Owner**；P2 退回；P3 登记
10. **三处 sha256 一致核对**（派审/审核/批准）
11. **合并** = 采纳审过的副本内容
12. **台账 + 清理**
